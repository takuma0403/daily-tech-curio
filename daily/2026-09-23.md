### <a id="card-1"></a>🆕 タップごとに変わるURLの中身は、二度と同じにならない——NTAG 424 DNAのSUN機能 〔move: 仕様の目的外利用 / 領域: 無線/組み込み/ハードウェア〕

**事実**: NFCタグの多くは、何度読んでも同じURLをただ返すだけの静的なメモリチップにすぎない。だがNXPのNTAG 424 DNAは「SUN(Secure Unique NFC)」を生成するSDM(Secure Dynamic Messaging)という機能を持ち、タップのたびにチップ内部のカウンタをAES-128で暗号化し、CMAC署名を添えてURLのパラメータに焼き込んで返す。同じタグを2回タップしても、URLの暗号化部分は毎回別の文字列になる。秘密鍵はチップの外に一度も出ない。

**何ができる**: この「タップ1回=1回限りの使い捨てトークン」という性質を使うと、通信もアプリインストールも要らない使い捨て認証が作れる。同じ鍵を持つ検証専用リーダーさえあれば、ネットに繋がずオフラインのまま「このタグは本物か」「このタップは初めて使われたものか」を即座に判定できる——リプレイされたURLはカウンタの巻き戻りとして一発でバレる。電池もディスプレイも持たない1枚のシールが、そのまま物理的なワンタイムパスワード生成器になる。

**技術の魅力**: 本来「偽造品を掴まされないための消費者向け認証」として設計された機能が、タップという物理行為そのものをワンタイムトークン発行イベントに変えてしまう点が効いている。チャレンジ・レスポンス認証なのに、チャレンジを送る通信すら要らない——タグ内部のカウンタという状態だけが暗黙のナンスになっている。サーバーなしで「使い捨て」を実現する数少ない物理デバイスの一つ。

**本来どこで使われてるか**: 高級ブランド品や医薬品パッケージの模造品対策シールとして実用化されている。NTAG 424 DNAはタンパーエビデント(開封検知)ラベルに組み込まれ、消費者がスマホでタップするだけでAES-128暗号化されたSUNメッセージを読み取り、正規品かどうかをリアルタイム検証する仕組みとして医薬品・高級品・電子機器のブランド保護に使われている。

### <a id="card-2"></a>🔍 広告の切れ目を告げる合図が、映像の中に隠しコマンド経路を作る——SCTE-35スプライスキュー 〔move: サイドチャネル/副作用の利用 / 領域: AI/メディア処理〕

**事実**: テレビやストリーミングの裏側では、番組と広告の継ぎ目を自動で切り替えるために「SCTE-35」という信号が常時流れている。MPEG-TSの中に専用PID(パケット識別子)で埋め込まれた小さなメッセージが「ここでCMに差し替えていい」「ここで戻していい」を秒単位で告げ、HLSでは`#EXT-X-CUE-OUT`、DASHでは`EventStream`という形に翻訳されて配信網の隅々まで伝わる。重要なのは、この信号が映像・音声そのものとは独立したメタデータ層として、何段ものトランスコーダ・CDN・プレーヤーをそのまま素通りしていくこと。

**何ができる**: 広告切り替え以外の意味を持たせたカスタムのセグメンテーションタイプやupidを流用すれば、視聴者には気づかれないまま「この瞬間に照明を切り替えろ」「セカンドスクリーンのアプリを同期しろ」「録画を止めろ」といった任意のコマンドを、映像コンテンツそのものの中に埋め込んで配信網の先まで運べる。地上波・ケーブル・ストリーミングを問わず動く、放送インフラに寄生した低遅延の制御チャンネルになる。

**技術の魅力**: 誰もSCTE-35を「汎用の隠しコマンド経路」として設計していないのに、広告ビジネスに信頼された配管だからこそ途中の機材がまるごと素通りさせてくれるという非対称性が効いている。映像のピクセルをいじる透かしと違い、圧縮やフォーマット変換をまたいでも壊れにくい——業界が広告のために敷いてくれた「誰も疑わない裏道」にそのまま乗るという発想。

**本来どこで使われてるか**: ケーブル・放送業界の広告差し替え(Dynamic Ad Insertion)とブラックアウト制御の標準規格。米SCTEが策定した本規格は、配信事業者がライブ配信中の番組にローカル広告を挿し込んだり、スポーツ中継の地域ブラックアウトを自動切り替えたりする際の合図として、放送局・CDN・ストリーミングプラットフォームで日常的に使われている。

### <a id="card-3"></a>💡 ブラウザに殺されたTLSの"紐付け"が、HTTPヘッダ1本で生き返った——DPoPというToken Bindingの転生 〔move: レガシー/廃止予定機能の蘇生 / 領域: セキュリティ/認証〕

**事実**: 2018年、ChromeはHTTP Token Binding(RFC 8471)への対応を削除した。これはCookieやOAuthトークンをTLSコネクション自体に暗号学的に紐付け、盗まれたトークンを別の接続で使い回せなくする仕組みだったが、他の主要ブラウザが誰も追随せず、TLS層でトークンを縛るという発想はブラウザの世界では事実上死んだ。ところが「盗まれたトークンを無効化する」という狙いそのものは消えず、2023年にRFC 9449として標準化されたDPoP(Demonstrating Proof of Possession)という形でアプリケーション層に生まれ変わった。

**何ができる**: DPoPでは、クライアントが公開鍵ペアを生成し、トークンをリクエストするたびにその秘密鍵で署名した使い捨てのJWT(DPoP proof)をHTTPヘッダに添付する。サーバーはアクセストークンとこの証明が同じ鍵ペアに紐付いているかを毎回検証するので、TLS終端の改造やPKIの構築を一切せずに、盗まれたトークン単体では使えない仕組みを既存のOAuth/OIDCフローへ後付けできる。Web Cryptoが使えるブラウザ・ネイティブアプリ・モバイルアプリのどこにでも組み込める。

**技術の魅力**: Token Bindingは「通信路(TLS)そのものを紐付けの土台にする」という筋の良い設計だったのに、ブラウザベンダーの足並みが揃わなかっただけで潰えた。DPoPは同じ「トークンの所有証明」という核の思想を、通信路より一段上の署名付きJWTという誰でも実装できるレイヤーに移し替えることで蘇らせている。インフラ層で失敗した仕様が、アプリ層でヘッダ1本に縮小されて生き返るという再利用のされ方が面白い。

**本来どこで使われてるか**: OAuth 2.0のアクセストークン・リフレッシュトークンをトークン盗難から守るための業界標準として、Auth0やOktaなど主要なID基盤が2023〜2024年にかけて相次いでDPoP対応を追加し、モバイルアプリやSPAで「漏れたトークンをそのまま使い回されない」認可フローの実装に使われ始めている。
