### <a id="card-1"></a>🆕 同期サーバーを持たず、「変更の差分」だけをUSBメモリで運ぶ——SQLite Session Extensionのchangeset 〔move: 仕様の目的外利用 / 領域: データ/同期/ストレージ〕

**事実**: SQLite には公式の拡張 Session Extension があり、あるテーブル群への変更を記録して、`changeset` というバイナリの塊として取り出せる。中身は「主キーXの行が、旧値AからBに変わった」という行単位の差分で、別のSQLiteファイルに `sqlite3changeset_apply()` で適用できる。適用時に「旧値が今の行と一致しない」などのずれが起きると、呼び出し側が書いた競合ハンドラが呼ばれ、OMIT（飛ばす）・REPLACE（上書き）・ABORT（全部巻き戻す）を選べる。同期の道具として語られることが少なく、多くの人は存在を知らない。

**何ができる**: 通信網のない現場（圏外の畑、船内、工場の隔離ネットワーク）にあるSQLiteのDBを、サーバーなしで同期できる。現場側は変更をchangesetにして数KBのファイルとして吐き出し、USBメモリやQRコード連打、あるいはLoRaの小さなパケット列で運ぶ。本部側は `apply` するだけで、DBまるごとのコピーを往復させずに済む。ESP32/Raspberry Pi の記録DBと、手元のPCのDBが「差分便」で揃っていく。

**技術の魅力**: 競合検出が“旧値の一致”という楽観的並行制御として最初から組み込まれている点。DATA競合（行はあるが旧値が違う）、CONFLICT（同じ主キーのINSERT）、NOTFOUND（消す行がない）と、ずれの種類が名前付きで分類され、ポリシーを関数1つで差し込める。CRDTのような自動収束ではなく「ずれたら人間か関数が決める」割り切りなので、小さく、枯れていて、依存が増えない。

**本来どこで使われてるか**: SQLite自身の拡張として、アプリの変更履歴の記録・取り消し・複数DB間の変更伝搬に使うために用意されている。公式ドキュメントが `sqlite3changeset_apply` の競合ハンドラの戻り値（OMIT / REPLACE / ABORT）と、DATA・CONFLICT 等の競合コードの意味を規定している。
出典: https://sqlite.org/session/sqlite3changeset_apply.html

### <a id="card-2"></a>🔍 FFTを捨てて、たった1本の周波数だけを聴く——Goertzelで口笛を鍵にする 〔move: 制約の極端化 / 領域: AI/メディア処理〕

**事実**: 周波数を調べる定番はFFTだが、知りたい周波数が決まっている場合、Goertzel（ゲルツェル）アルゴリズムのほうが軽い。2次のIIRフィルタ1個を回すだけで、FFTの1ビンと同じ値が O(N) で出る。必要なビン数が log2(N) 程度より少なければFFTより速い、とされる。電話のプッシュ音（DTMF）の復号が代表例で、8本の周波数だけを見ればよい。

**何ができる**: ATtiny85のような数KBのマイコンにマイクとADCを付け、2種類の決まった音（例: 1.0kHzの後に1.5kHz）が順に鳴ったときだけ出力を立てる「音の合言葉」錠ができる。スマホから特定の2音を鳴らすか口笛で吹くと開く、赤外線も電波も使わない鍵。たとえば8kHzサンプリングで、205サンプルのブロックごとに目的の数本だけを計算する。ブロック長Nは、N×(目的周波数)÷(サンプリング周波数)が整数に近くなるよう選ぶと漏れが少ない（DTMFの8kHz・N=205が定番）。

**技術の魅力**: 「全部の周波数を調べる」のが当たり前の世界で、1本だけ聴くと決めた途端に、メモリは状態変数2つ、計算は積和だけに落ちる。非対称性は“何を聴かないか”を決めた側が勝つこと。反対に、ビンを増やしすぎるとFFTのほうが得になるという交差点も明確で、道具の使いどころが数字で言える。

**本来どこで使われてるか**: 電話交換機やVoIPのDTMF検出。ほかに、特定のトーンだけを監視する用途（警報音・ビープ音の検出）で、リソースの小さい組み込みDSPが使う。
出典: https://link.springer.com/article/10.1186/1687-6180-2012-56 / https://metricgate.com/docs/goertzel-tone-detection/

### <a id="card-3"></a>💡 1930年代のテレックスが仕込んだ「お前は誰だ」が、いまもシリアルポートの名乗りに使える——WRUとENQ 〔move: レガシー/廃止予定機能の蘇生 / 領域: ワイルドカード(テレタイプ史×組み込み)〕

**事実**: テレックスには「answerback」という仕組みがあった。送信側がWRU（Who aRe yoU）の符号を送ると、受信側の機械が自動で自分の名前（最大22文字ほどを、ペグの付いた回転ドラムに記録）を打ち返す。これで、つないだ相手が本当に目的の相手かを機械同士で確かめられた。メッセージ末尾にもWRUを送り、途中で回線が切れていないことも確認した。この符号はASCIIにENQ（0x05、Enquiry）として引き継がれ、DEC VT100端末（1978年）にもユーザー設定可能なanswerbackとして残った。

**何ができる**: マイコンのファームウェアに「0x05を受けたら1行の名乗りを返す」だけの規則を入れる。USBシリアルが10本ささったPCやラズパイで、各ポートに0x05を1バイト撃てば、どのポートがどの基板か、ファームのバージョンが何かを、設定ファイルなしで一覧にできる。名乗りは“ドラム”にならって22文字に制限すれば、短く機械可読な識別子として安定する。

**技術の魅力**: 90年前の「物理的に回るドラム」の発想が、1バイトのコマンドと1行の返事という最小のサービス発見になっている。“Hello”も“スキャン”も“登録サーバー”も要らない。しかも古い端末エミュレータはすでにENQに答える実装を持つので、プロトコルが体に染み付いている。

**本来どこで使われてるか**: 本来は世界的な電報網テレックスで、機械が相手を確認するための仕組み。ASCIIのENQ（U+0005）は今も、一部の古い端末エミュレータや特殊なシリアルプロトコルに残っている。
出典: https://en.wikipedia.org/wiki/Telex / https://en.wikipedia.org/wiki/Enquiry_character
