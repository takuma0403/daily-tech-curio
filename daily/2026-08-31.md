### <a id="card-1"></a>🆕 二枚の映像が黒く消えるとき、そこに侵入者が浮かび上がる〔move: 仕様の目的外利用 / 領域: フロントエンド/グラフィックス〕

**事実**: CSS Compositing and Blending仕様の `mix-blend-mode: difference` は、重なった2枚のレイヤーの各カラーチャンネル値を引き算し、その絶対値だけを描画する合成モード。同じ色同士は差が0になり真っ黒になる。本来はPhotoshopなど画像編集ソフトの「差の絶対値」表示を再現するための地味な機能で、写真家が2枚の露出をピクセル単位でぴったり位置合わせ（レジストレーション）するときに使う。ブラウザでは単なるCSSプロパティ1個として誰でも使えるが、たいていは前衛的なテキスト演出止まりで終わる。

**何ができる**: 部屋が無人のときに撮った1枚の静止画の上に、ライブの`<video>`映像を`mix-blend-mode: difference`で重ねるだけで、変化のない背景ピクセルは自動的に相殺されて真っ黒になり、人や物が動いた領域だけが明るく浮き上がる。`getImageData`もCanvasのピクセルループもWebGLシェーダも一切書かず、GPUのコンポジタが毎フレーム差分を取ってくれる——ブラウザの標準機能だけで動く「モーションディテクタ」ができる。閾値を付けたければ後段に`contrast()`や`brightness()`フィルタを足すだけでいい。

**技術の魅力**: 本来「画像を重ねて見た目を作る」ための装飾機能が、数学的には「2つの信号の差分を取る」計算そのものだと気づくと、CGペイント屋の道具が信号処理の道具に反転する。しかもJSのメインスレッドを一切使わずGPU側の合成パイプラインだけで完結するので、Canvas 2Dで1ピクセルずつ引き算するより低コストで高フレームレートに動く。「装飾」と「演算」がまったく同じ1命令だったという非対称性が効いている。

**本来どこで使われてるか**: Photoshopなど写真編集ソフトの標準機能として、2枚のカット（HDR合成前の露出違い、パノラマの継ぎ目、天体写真のスタック）をピクセル単位で正確に位置合わせする定番テクニックとして使われている。差分結果が真っ黒になるまでレイヤーをずらせば、目視では分からない1px未満のズレまで検出できる。

### <a id="card-2"></a>🔍 タブが死んだ瞬間だけ、隣のタブが仕事を引き継ぐ——Web Locks APIという心臓モニター〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: Web Locks API（`navigator.locks`）は、同一オリジンの複数タブ・ワーカー間で名前付きの排他/共有ロックを取り合うための仕様。特徴的なのは、ロックを保持したままタブが閉じられたりクラッシュしたりページ遷移したりした場合、明示的な解放処理を一切書かなくても、ブラウザのプロセス自身がロックを強制解放し、待機中の別タブの`request()`コールバックが即座に呼ばれること。これはハートビートもBroadcastChannelでの生存確認メッセージも要らない、OSレベルの「保持者が本当に死んだ」通知になっている。

**何ができる**: 複数タブで動くジョブキューを、サーバーもハートビート送信も使わずに作れる。あるタブが`"task-42"`という名前のロックを取ってから重い処理を始め、途中でタブごとクラッシュすると、他のタブでブロックされていた`request('task-42')`のコールバックがその瞬間に発火し、そこから処理を引き継げる。ハートビート送信も、タイムアウト判定も、"生きているふり"をするタブの誤検知も存在しない。ロック機構を排他制御ではなく「死んだことだけを教えてくれるセンサー」として使う発想。

**技術の魅力**: 通常、生存監視は「一定間隔で信号を送り、途切れたら死んだとみなす」という推測ベースの仕組みになりがちで、ネットワーク遅延やタブのバックグラウンド抑制のせいで誤検知が付きまとう。Web Locksはブラウザ自身がプロセスの生死を握っているので、推測ではなく確定情報として「今まさに死んだ」が伝わる。ロックAPIの本質は「排他制御」ではなく「保持者の生存期間の告知」だったと捉え直すと、用途が丸ごと反転する。

**本来どこで使われてるか**: OAuthのトークンリフレッシュを複数タブが同時に叩いてリフレッシュトークンを消費し合う"multi-tab token race"を防ぐために使われている。1つのタブだけが`'auth_token_refresh_lock'`を取得してリフレッシュAPIを叩き、他のタブはロック解放を待ってから最新トークンをlocalStorageなどから読み直す、という実装がSPA認証まわりで定番化しつつある。
出典: https://openillumi.com/en/en-oauth2-refresh-token-multitab-locks-race/ / https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API

### <a id="card-3"></a>💡 黒く塗りつぶした顔の下に、消し忘れた"縮小コピー"が隠れている——EXIFサムネイルという編集の証人〔move: サイドチャネル/副作用の利用 / 領域: AI/メディア処理〕

**事実**: JPEGファイルのExifメタデータには、IFD1と呼ばれる領域に本体画像とは別に埋め込まれた小さなサムネイル画像（多くは160×120px程度のJPEG）が入っている。これはカメラや古いソフトが、ファイル一覧のプレビュー表示を高速化するために撮影・保存時に一度だけ生成して埋め込んだもの。問題は、後から別の簡易な編集ソフトで本体画像だけをトリミング・黒塗り・モザイク加工しても、このサムネイルを再生成する処理をすべてのソフトが律儀にやってくれるとは限らない点にある。

**何ができる**: 見た目には完全にトリミング済み・黒塗り済みの画像でも、Exifのサムネイル領域だけを抜き出すと、加工前のオリジナルがそのまま残っていることがある。ExifToolのようなツールで埋め込みサムネイルを抜き出すだけで、本人が「消した」つもりの範囲——顔、背景の人物、モザイク前の文字——が縮小版とはいえ丸ごと復元できてしまう。編集履歴を一切残さないはずの単純な画像編集が、実は"未編集の証拠品"を静かに同梱していたことになる。

**技術の魅力**: 暗号もタイムスタンプも使わない、ただの「キャッシュの更新漏れ」がそのままプライバシー漏洩経路になっている点が効いている。攻撃者は何かを注入する必要すらなく、ソフトウェアの実装が持つ"手抜き"（サムネイル再生成をスキップする）を待つだけでいい。しかも本体画像がどれだけ入念に加工されていても、サムネイルは別バイト列として独立に存在するので、本体だけを画像解析しても絶対に気づけない。

**本来どこで使われてるか**: 2003年、あるタレントがトリミングした自撮り写真をブログに投稿したところ、使用していたPhotoshopのバージョンがサムネイルを再生成しない仕様だったため、Exifサムネイルにトリミング前の写真がそのまま残っており第三者に発見された、という初期の代表的な流出事例がある。以降もこの種の"サムネイル不一致"は、黒塗り・ぼかし・ウォーターマークを施した画像全般に共通する編集ソフトの実装漏れとして、デジタルフォレンジックの定番チェック項目になっている。
