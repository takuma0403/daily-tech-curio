### <a id="card-1"></a>🆕 本物と見分けがつかない、という約束が密輸経路になる——GREASE ECHという擬態乱数 〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: TLS 1.3のEncrypted Client Hello（ECH、RFC 9849）は、接続先ドメイン名(SNI)を暗号化して検閲や中間者による選別ブロックから守る仕組み。厄介なのは、クライアントがまだそのサーバーのECH設定を知らない初回接続で、ECH拡張そのものが欠けると「この接続はECH未対応」と一目で分かってしまうこと。これを防ぐため仕様は"GREASE ECH"を義務付けている——本物のECH設定がなくても、サーバー側が黙って無視するランダムなダミーバイト列を、本物と統計的に区別できない形式で毎回のClientHelloに詰めておく。そのECH設定自体も、DNSのHTTPS/SVCBレコード（RFC 9460・RFC 9848）の"ech"パラメータとして、ふつうにキャッシュされ世界中に伝播するDNS応答の中に乗っている。

**何ができる**: GREASE ECHの中身は「本物のECHと見分けがつかない乱数であること」が仕様上要求されているので、そこに自分の任意データを埋め込んでも、途中のミドルボックスやDPI装置には単なるダミーにしか見えない。さらにSVCBレコードのSvcParamKeyには65280〜65534の"Private Use"領域がまるごと予約されていて、IANA登録なしに誰でも独自パラメータを名乗れる。この2つを組み合わせれば、①DNSキャッシュに乗せるだけで自前サーバー不要の一方向データ配布網（private-use SvcParamKey）と、②検閲装置が構造的にブロックできない双方向トンネル（GREASE ECHへの便乗）を、どちらも"仕様通りの動作"だけで作れる。

**技術の魅力**: 普通のステガノグラフィは「怪しく見えないよう偽装する」努力を自分でやる必要があるが、ここでは仕様書自身が「本物と統計的に区別できてはならない」と明記している。検閲耐性のために積まれた設計要求が、そのままステルス性の理論的な保証書になっている。もしミドルボックスがGREASEと本物のECHを見分ける手段を手に入れたら、それはECH自体の検閲耐性を壊す欠陥報告になってしまう——防御側がこの抜け道を塞ごうとすると、自分の首を絞める非対称性がここにある。

**本来どこで使われてるか**: 元々の目的はまったくの逆で、権威主義的なネットワークによるドメイン単位のブロッキングを防ぐためのプライバシー機能。CloudflareやFirefox・ChromeがECHの実運用を進めており、GREASE ECHは「ECH未対応環境でも観測者に何も気づかせない」ための必須のフォールバック動作として仕様に明記されている(RFC 9849)。DNS側のSVCB/HTTPSレコードはRFC 9460で標準化され、Cloudflareなど主要DNSプロバイダがすでに配信している。
出典: https://www.rfc-editor.org/rfc/rfc9849.html / https://www.rfc-editor.org/rfc/rfc9460.html / https://blog.apnic.net/2023/12/18/use-of-https-resource-records/

### <a id="card-2"></a>🔍 ぼかしのための行列が、JS抜きでライブ映像のエッジ検出カメラになる——feConvolveMatrixという宣言的畳み込み器 〔move: 制約の極端化 / 領域: フロントエンド・グラフィックス〕

**事実**: SVGの`<feConvolveMatrix>`は、ぼかし・シャープ・エンボスを作るための地味なフィルタプリミティブで、n×mの「カーネル行列」を1つ書くだけで各ピクセルを周辺ピクセルとの重み付き和に置き換える。CSSの`filter: url(#id)`経由でHTML要素に直接適用できる。重要なのは、これが単なるプリセットのぼかしではなく、任意のカーネル行列・除数・オフセット・端の処理まで自由に書ける「宣言的な汎用畳み込み演算器」だという点。

**何ができる**: `kernelMatrix="0 -1 0 -1 4 -1 0 -1 0"`のようなラプラシアン核や、Sobel/Prewitt核をそのまま渡せば、画像だけでなく`<video>`要素にもJSを1行も書かずにフィルタを適用できる。ブラウザは映像の毎フレームの描画のたびにこの畳み込みを自動で再計算するので、`<video autoplay>`にCSSの`filter`プロパティを1個当てるだけで、ライブカメラ映像がリアルタイムのエッジ検出映像に変わる。WebGLシェーダーもCanvasの`getImageData`ループも要らず、`<video>`タグと数行のCSS/SVGだけで完結する。

**技術の魅力**: 普通、画像処理の畳み込みはWebGLかCanvasのピクセル操作で書くもので、「JS禁止」という制約を課すと実現不能になるのが常識。ところがSVGフィルタは表示パイプラインの一部として最初から"毎フレーム再計算される汎用畳み込み器"を仕込んでいるので、制約を極端化した瞬間に逆に一番シンプルな実装になるという逆転が起きる。CPU/GPUどちらでリソルブするかはブラウザ任せで、実装によってはハードウェアアクセラレーションも効く。

**本来どこで使われてるか**: 元々はPhotoshop的な画像編集効果——エンボス、ベベル、シャープ化——をSVG/CSSの世界に持ち込むためのW3C仕様(SVG Filter Effects)。Webデザインの世界ではロゴやアイコンの立体感表現、写真加工のデモに使われてきた。FirefoxはHTMLコンテンツへのSVGフィルタ適用を全面サポートしており、一方Safari/WebKitはfeConvolveMatrixを含む一部フィルタのみ限定サポートという実装差も残っている。
出典: https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/Applying_SVG_effects_to_HTML_content / https://blog.logrocket.com/complete-guide-using-css-filters-svgs/

### <a id="card-3"></a>💡 圧縮の癖が、誰がエンコードしたかを勝手に自白する——LAME/Xingヘッダというエンコーダの指紋 〔move: サイドチャネル・副作用の利用 / 領域: AI・メディア処理 / レンズ: オフライン完結〕

**事実**: MP3にはXingヘッダという、可変ビットレート(VBR)ファイルの総フレーム数・総バイト数をプレイヤーに教えるための拡張ブロックがある。定番エンコーダLAMEはこれをさらに拡張し、自分のバージョン番号・エンコード設定・エンコーダディレイ(先頭に足された無音サンプル数)まで書き込む「LAMEタグ」を仕込む。加えて規格書には実装の自由度が大きく残っている箇所(丸め方・心理音響モデルの近似・パディングの入れ方)があるため、エンコーダごとに"完全準拠"ではない微妙な癖がビットストリームそのものに残る。

**何ができる**: `mp3guessenc`のようなツールは、ID3タグを全部剥がされた"素のMP3データ"だけを見て、Xing/LAMEタグの有無・バージョン文字列・エンコーダディレイの値・フレームの微妙な癖から、そのファイルが「どのエンコーダの、どのバージョン・設定で」作られたかを高確率で言い当てる。これを使えば、「320kbpsの高音質リップ」を名乗るファイルが実は128kbpsのMP3を後からトランスコードして水増ししただけの偽物かどうかを、参照データベースにもネットにも一切繋がず、そのファイル単体だけを見て判定できる。

**技術の魅力**: 誰も「エンコーダを特定されるように」設計していないのに、規格の曖昧さと最適化のクセが結果的に指紋になる。しかも電子透かしのように能動的に埋め込む必要すらなく、エンコーダは自分の仕事をしているだけで正体を漏らしてしまう。改竄検出が「後から証拠を足す」のではなく「最初から勝手に残っている証拠を読むだけ」で成立する非対称性が効いている。

**本来どこで使われてるか**: 音楽の違法配布・リッピングを追う趣味的なコミュニティ(Hydrogenaudioなど)で、"偽の高音質リップ"を見抜くための定番手法として使われてきた。スペクトログラムを目視して高域が不自然にカットされていないか調べる文化と並んで、mp3guessencのようなツールでエンコーダ・バージョンまで機械的に特定し、リリースの由来を推測する材料にも使われている。
出典: https://wiki.hydrogenaudio.org/index.php?title=MP3 / https://mp3guessenc.sourceforge.io/
