### <a id="card-1"></a>🆕 スマホカメラの"欠陥"がLEDの点滅を受信機に変える——ローリングシャッターVLC 〔move: 物理現象へのピギーバック / 領域: AI/メディア処理〕

**事実**: CMOSイメージセンサーの大半は「ローリングシャッター」方式で、画面を上から下へ1行ずつ順番に露光していく。全画素を同時に読み出すグローバルシャッターに対する低コストな代替方式で、動く被写体を撮ると斜めに歪む「ジェロー効果」という欠陥として知られている。ところがこの「1行ごとに露光タイミングがずれる」性質は、LEDが人の目には見えない速さ(数百Hz〜数kHz)で明滅していると、その位相差が画面上に明暗の縞模様として写り込むことを意味する——センサー自体が高速なストロボスコープになる。

**何ができる**: LED照明やディスプレイ側をその明滅パターンでビットを乗せて光らせておけば、普通のスマホカメラで1枚撮影するだけで(専用の受光素子は不要)、写り込んだ縞の幅と位置から元のビット列を復調できる。天井のLED照明が位置情報や店内ナビゲーション信号をWi-Fi不要で"放送"し、来店客のカメラがそれを一瞬で受信する、といった可視光通信(VLC)が追加ハードウェアゼロで成立する。至近距離でディスプレイ同士をかざし合い、画面のちらつきだけでデータをやり取りする機器間通信も同じ原理で作れる。

**技術の魅力**: ローリングシャッターは長年「直すべき欠陥」として扱われてきたアーティファクトで、通信路として使えるとは誰も意図していなかった。画像の見た目を歪ませるだけの副作用が、時間軸の情報を空間軸(縞の位置)へ変換する天然のアナログ-デジタル変換器として働く非対称性が効いている。受信側のカメラは何も変える必要がなく、送信側のLEDが明滅を工夫するだけで通信が成立する。

**本来どこで使われてるか**: ワシントン大学などが提案したDisCo(Display-Camera Communication, SIGGRAPH Asia/ACM TOG 2016)はディスプレイ同士のローリングシャッター通信を実証し、車両のテールライトLEDと車載カメラ間の可視光通信(V2V)、IoT向け屋内測位や光カメラ通信(OCC)の標準化(IEEE 802.15.7)でも同じ原理が採用されている。
出典: https://dl.acm.org/doi/10.1145/2896818 / https://www.mdpi.com/1424-8220/20/12/3361

### <a id="card-2"></a>🔍 デバイスを一緒に振るだけで鍵が生まれる——Shake Well Before Use 〔move: 人間/身体をプロトコルの一部にする / 領域: セキュリティ/認証〕

**事実**: Bluetoothヘッドセットのような、画面もキーボードも持たない小型デバイス同士を安全にペアリングするのは長年の課題だった。PINを打たせることもQRコードを見せることもできない。2007年、Lancaster大学のMayrhofer・Gellersenは、2台のデバイスを片手に持って一緒に振るだけで、両方の加速度計が拾う"ほぼ同じだが微妙に違う"揺れの波形から暗号鍵を導出できることを示した(Shake Well Before Use)。

**何ができる**: 両デバイスの加速度計データを一定時間サンプリングし、量子化と誤り訂正を経て同じビット列に収束させる。第三者が同じタイミング・強さ・方向で振ることは物理的にほぼ不可能なので、通信を盗聴されても鍵は再現できない。ShaVe/ShaCKという2方式が提案され、鍵交換後にセンサーデータの一致度で相手が本当に"一緒に振られた"デバイスかを検証する。ユーザーは説明書なしで「振ればペアリングされる」と直感的に理解できる。

**技術の魅力**: 認証の"秘密"を暗号学的な計算ではなく、人間の腕の動きという物理現象に押し込んでいる点が新しい。パスワードのように記憶する必要も、公開鍵基盤のように事前の信頼関係も要らず、「その場で偶発的に生まれた身体運動の再現不可能性」がそのままセキュリティ強度になる。歩数計程度の安物センサーである加速度計と、鍵合意プロトコルという畑違いの技術を組み合わせたところが効いている。

**本来どこで使われてるか**: この発想は近接デバイスの直感的ペアリング研究として本格化し、後継研究ShakeMe(2015)などにも引き継がれた。同様の"身体の動きで機器同士を結びつける"着想は、モバイル端末の近接連携機能やスマートウォッチの歩容認証にも波及しており、画面なしIoTデバイスのセキュアペアリング手法の基礎研究として今も引用され続けている。
出典: https://www.mayrhofer.eu.org/downloads/publications/Pervasive2007-Shake-Well-Before-Use.pdf / https://arxiv.org/pdf/1507.06353

### <a id="card-3"></a>💡 ブロックチェーンの"因果順序"だけを借りる——Merkle-CRDT 〔move: 異分野の手法移植 / 領域: データ/同期/ストレージ〕

**事実**: CRDT(Conflict-free Replicated Data Type)は複数ノードが同時に同じデータを編集しても矛盾なく収束する仕組みだが、実装によっては「誰が何をいつ書いたか」という因果関係の管理コストが膨らみがちだった。2020年、IPFSの開発元Protocol Labsは、Bitcoinやgitが使う「各データブロックが前のブロックのハッシュを持つ」というMerkle-DAG構造をCRDTの土台に据える"Merkle-CRDTs"を提案した。

**何ができる**: 各書き込みをMerkle-DAGのノードとして親ハッシュ付きで連結すると、DAGの形そのものが「どの変更がどの変更より後か」という因果順序を勝手に表現してくれる(Merkle-Clock)。全員の合意(コンセンサス)を必要とするブロックチェーンと違い、各ノードは自分が知っている最新のDAGを持ち寄ってマージするだけで収束する。実装のOrbitDBはこれを使ってIPFS上にサーバー0のP2Pデータベースを構築しており、ノードが増減したりオフラインで編集したりしても、あとで合流すれば矛盾なく1つの状態にまとまる。

**技術の魅力**: 「参加者全員の合意を取る」という重い仕組みを持つブロックチェーンから、合意抜きで"改竄検知・因果順序"の部分(Merkle構造)だけを剥ぎ取ってCRDTへ移植した点が新しい。畑違いの技術(コンセンサスアルゴリズムと一体化していたMerkle木)から、都合のいい半分だけを持ち去るという"つまみ食い"の発想が効いている。

**本来どこで使われてるか**: MerkleツリーはBitcoinのブロック検証やgitのコミット履歴管理で使われる、分散台帳・バージョン管理の基礎技術。Protocol Labsはこれをそのまま転用し、IPFS上のP2Pデータベースフレームワーク`orbitdb/orbitdb`のCRDT実装として実運用に載せている。
出典: https://arxiv.org/pdf/2004.00107 / https://github.com/orbitdb/orbitdb
