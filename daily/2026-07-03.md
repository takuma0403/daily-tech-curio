### <a id="card-1"></a>🆕 ノードIDを一つも決めずに"どちらが先か"を追跡する——Interval Tree Clocks 〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: 分散システムで「どのイベントがどのイベントより先に起きたか」を追跡する定番はベクタークロックだが、これは参加ノードの数をあらかじめ固定し、各ノードに背番号を配っておく必要がある。ノードが勝手に増減するP2Pや、オフライン端末が気まぐれに参加・離脱するローカルファーストアプリでは、この背番号の事前配布自体が破綻する。2008年にAlmeida・Baquero・FonteがOPODISで提案したInterval Tree Clocksは、この背番号をそもそも配らないことで解決した。

**何ができる**: 全体を1つの「区間」として扱い、新しいノードが参加するたびにその区間を二分木のように半分に割って渡す(fork)。ノードが離脱すれば区間を親に返して合体させる(join)。これだけで、誰も参加者リストを把握していない状態でも「このデータはどちらが新しいか」「これは同時編集で衝突しているか」を判定できる。CRDTやレプリケーションシステムの土台であるバージョンベクタを、事前登録なしでそのまま置き換えられる。

**技術の魅力**: 「IDを配る」という分散システムの大前提そのものを疑い、IDの代わりに「まだ誰にも渡していない区間」を配るという発想の転換が効いている。区間を割って渡し、使い終わったら返す——在庫管理や周波数割り当てに近い考え方を因果追跡に持ち込み、管理対象を"名前"から"空間"にすり替えた点が新しい。

**本来どこで使われてるか**: 発端は分散システムの学術研究（Almeida, Baquero, Fonte, "Interval Tree Clocks: A Logical Clock for Dynamic Systems", OPODIS 2008）で、著者自身によるErlang実装が公開され、以降のCRDT・delta-state同期フレームワークの設計議論で継続的に参照される基礎技術になっている。Version VectorはAmazon DynamoやApache Cassandraのようなレプリケーションシステムの標準装備だが、ITCはその"ノード数固定"という弱点だけをピンポイントで解消する後継として位置づけられている。
出典: https://gsd.di.uminho.pt/members/cbm/ps/itc2008.pdf / https://github.com/ricardobcl/Interval-Tree-Clocks

### <a id="card-2"></a>🔍 GPUの「見えない圧縮」がピクセルを漏らす——GPU.zip 〔move: サイドチャネル/副作用の利用 / 領域: フロントエンド/グラフィックス〕

**事実**: 現代のGPUはほぼ例外なく、画面に描く前のフレームバッファをこっそり圧縮している。ソフトウェアからは一切見えない、ベンダーが電力とメモリ帯域を節約するために勝手にやっているシリコン上の最適化で、開発者もブラウザもその存在を意識しない。ところがこの圧縮は中身のデータによって処理時間が変わる——単色に近い領域ほど速く圧縮できる。2023年、テキサス大学オースティン校などの研究チームは、この処理時間差がSVGフィルタのレンダリング時間としてJavaScriptから測定できることを示した。これがGPU.zip。

**何ができる**: 悪意あるページに、被害者が開いている別オリジンのiframe(例: ログイン中のWikipediaページ)を透明なSVGフィルタ越しに重ねて描画させ、ピクセルごとの描画時間を測り続けると、圧縮の効きやすさの差から元の色——ひいては表示中のユーザー名などの文字列——を1ピクセルずつ復元できる。研究では、WikipediaのiframeからユーザーIDをRyzen機で30分・Intel機で215分、それぞれ97%・98.3%の精度で読み取れることを実証した。CPUを一切使わず、GPU合成パイプラインの物理的な副作用だけでSame-Origin Policyの前提を突破する。

**技術の魅力**: ソフトウェアが明示的に有効化したわけではない、ハードウェアが勝手にやる"透過的な"最適化がサイドチャネルになる点が新しい。従来の圧縮系サイドチャネルはソフトウェア側で機能を無効化すれば防げたが、GPU.zipはシリコンの配線そのものに焼き込まれた挙動なので、ブラウザの描画経路を制限する形でしか塞げない。ソフトウェアの世界の攻撃が、目に見えない物理回路の振る舞いにそのまま接地している非対称性が効いている。

**本来どこで使われてるか**: フレームバッファ圧縮(Delta Color Compression等)は、AMD・NVIDIA・Intel・Apple・Arm・Qualcomm各社のGPUがバッテリー消費とメモリ帯域を削るために標準搭載している純然たる省電力技術で、モバイル機器の電池持ちや高解像度ディスプレイの描画性能に日々貢献している。研究チームはこの攻撃がChromeで成立しFirefox/Safariでは成立しないことを示し、各GPUベンダーとブラウザベンダーに事前開示した。
出典: https://www.hertzbleed.com/gpu.zip/ / https://www.bleepingcomputer.com/news/security/modern-gpus-vulnerable-to-new-gpuzip-side-channel-attack/

### <a id="card-3"></a>💡 "どうでもいい"はずの大文字小文字を鍵に変える——DNS 0x20 〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: DNSの名前解決は昔から「大文字小文字を区別しない」と決められている(`Example.com`も`EXAMPLE.COM`も同一として扱われる)。これは人間が入力しやすくするための、意味を持たない仕様上の緩さに過ぎなかった。2008年、Dan Kaminskyが「偽の応答を大量に送りつけ、正規の応答より先に届けばキャッシュに毒を盛れる」というDNSキャッシュポイズニング手法を実証し、業界は追加の防御策を迫られた。そこで実装者らは、この"どうでもいい"はずの1ビット(0x20)を逆手に取った。

**何ができる**: 問い合わせ側がドメイン名の各文字の大文字/小文字をランダムに決めてクエリを送る。仕様上、権威サーバーは大文字小文字を無視して答えるはずだが、多くの実装は受け取った名前をそのまま応答にコピーする。応答が返ってきた際に「自分が送った大文字小文字パターンと一致しているか」を照合するだけで、攻撃者が偽の応答を当てるために推測しなければならない情報量が文字数分だけ(1文字=1ビット)増える。ソースポートのランダム化と合わせ、プロトコル変更ゼロで事実上の追加チャレンジトークンをねじ込んだ形になる。

**技術の魅力**: 新しい暗号もフィールドも足していない。「意味を持たないはずの自由度(大文字小文字)」を見つけ出し、そこに乱数を仕込んで秘密のチャレンジに変換しただけ、という点が効いている。DNSのワイヤーフォーマットも権威サーバーの実装も変更不要で、送信側だけの工夫でセキュリティが底上げされる非対称性が美しい。

**本来どこで使われてるか**: 現在Google Public DNS(8.8.8.8)やCloudflareなど主要なパブリックDNSリゾルバがデフォルトで有効化しており、日常のDNSクエリのほとんどに気づかないうちにランダムな大文字小文字が乗っている。元々は2008年のKaminsky脆弱性公表を受けてIETFドラフトとして提案され、キャッシュポイズニング対策の「タダで効く」追加防御として広く実装が進んだ。
出典: https://www.theregister.com/2023/01/19/google_dns_queries/ / https://astrolavos.gatech.edu/articles/increased_dns_resistance.pdf
