### <a id="card-1"></a>🆕 サーバーもAPIも要らない、SQLiteの"差分だけ"を運ぶ拡張機能——Session Extensionのchangeset 〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: SQLiteにはあまり知られていない公式拡張として「Session拡張」(sqlite3session) があり、通常のSQLite操作(INSERT/UPDATE/DELETE)を監視して、変更内容だけをバイナリの「changeset」としてまるごと取り出せる。これは行の全データではなく「何がどう変わったか」という差分そのもので、送信側と受信側が同じスキーマでさえあれば、apply APIで別のSQLiteファイルにそのまま当てられる。サーバーもネットワークプロトコルも、専用の同期ロジックすら要らない。

**何ができる**: 1ファイルのSQLite DBを2台の端末に置き、片方でオフライン中に自由に編集し、生成されたchangesetバイナリを(USBメモリでもBluetoothでもメールでも)物理的に運んで他方に`sqlite3changeset_apply`するだけで、ネットワーク接続なし・サーバーなし・同期プロトコル実装なしで2つのDBを一致させられる。競合が起きた場合はコンフリクトハンドラのコールバックに委ねられ、"最後に勝つ"から"手動マージ"まで自分で決められる。

**技術の魅力**: 通常の差分同期は「サーバーが仲裁する」か「CRDTのように可換な操作にする」かのどちらかに倒れがちだが、Session拡張は「差分を抽出して後で当てる」というただそれだけの原始的な機能に極限まで削ぎ落としている。ネットワークもサーバーも同期アルゴリズムの複雑さも、全部「あとで誰かが運んでapplyする」という物理的な行為に押し付けてしまう非対称性が効いている。

**本来どこで使われてるか**: モバイルアプリの断続的接続環境での同期(例: フィールドワーク用アプリ)や、複数プロセス間でのDB変更のレプリケーション、監査ログ生成などに使われる。SQLite公式ドキュメントでも「efficient synchronization between different applications over a network」の用途が明記されている。iOSアプリ開発コミュニティ(GRDBなど)でもオフラインファースト同期の実装基盤として利用例がある。
出典: https://sqlite.org/sessionintro.html / https://sqlite.org/session.html

### <a id="card-2"></a>🔍 ISPの請求のための1オプションが、オフィスのどのLANポートに挿さっているかを言い当てる——DHCP Option 82という"配線のGPS" 〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: DHCPには「Relay Agent Information」という拡張オプション(Option 82, RFC 3046)があり、DHCPリレー(スイッチやONU)がクライアントのリクエストを転送する際、自分がどの物理ポート・回線から受け取ったかを示す「Circuit ID」と「Remote ID」というサブオプションを勝手に埋め込む。本来の目的はケーブル事業者やISPが、契約者ごとの物理回線を突き止めて課金・帯域制御・不正接続防止を行うための"配線の住所"だった。

**何ができる**: これを企業LANやキャンパスネットワークのエッジスイッチに設定すると、DHCPサーバー側のログにIPアドレスと一緒に「どのスイッチのどのポート番号から来たか」が残る。GPSも無線測位も一切使わず、有線LANに挿しただけの機器が"この建物のこのポートにいる"という物理的位置情報を自己申告してしまう。NAC(ネットワークアクセス制御)製品はこれを使って「持ち込みPCを検知したらそのポートだけ自動で隔離VLANに落とす」ような、位置ベースの自動アクセス制御を組んでいる。

**技術の魅力**: 本来は「回線ごとの課金を間違えない」ための会計上のメタデータに過ぎないのに、物理トポロジという地理情報がおまけで付いてくる非対称性が効いている。GPSのように偽装するには電波をエミュレートする必要があるが、Option 82はスイッチ自身が挿入するので末端の端末からは偽装も無効化もできない(スイッチの設定次第)。会計のための几帳面さが、そのままセキュリティの土台に化ける。

**本来どこで使われてるか**: ケーブルモデム・PPPoE契約者管理を行うISP/キャリアの設備で広く使われ、契約者ごとの帯域制御や不正DHCPサーバー対策(DHCP Snooping)に組み込まれている。企業向けではCisco・JuniperなどのスイッチがOption 82挿入をサポートし、802.1XなしでもポートベースのIP払い出し制御や資産管理に使われている。
出典: https://www.rfc-editor.org/rfc/rfc3046.html / https://www.juniper.net/documentation/us/en/software/junos/security-services/topics/concept/port-security-dhcp-option-82.html

### <a id="card-3"></a>💡 推論中のチップが漏らす電磁波のさざ波だけで、モデルの中身を透視する——CSI NNという電磁側チャネル 〔move: サイドチャネル/副作用の利用 / 領域: AI/メディア処理〕

**事実**: ニューラルネットワークをCPU/マイコン上で推論させると、畳み込み・全結合・活性化関数といった演算の種類ごとに消費電力や電磁放射(EM)のパターンが微妙に異なる。これはCPUの分岐やメモリアクセスパターンの違いが電気的な"クセ"として漏れる、暗号解読で使われてきたサイドチャネル解析と同じ原理。2019年のUSENIX Securityで発表された「CSI NN」という研究は、この電磁波の波形だけを近接プローブで観測し、モデルファイルに一切触れずに層の数・種類・活性化関数といったアーキテクチャを高精度で復元できることを示した。

**何ができる**: モデルの重みファイルへのアクセスもAPIレスポンスの観測も不要で、推論実行中のデバイスの近くにEMプローブを1本置くだけで、企業が非公開にしている独自ニューラルネットの構造(レイヤー構成・活性化関数の種類など)を盗み出せる。エッジAIチップやIoTデバイスに焼き込まれた"企業秘密のモデル"は、ソフトウェア的に完全に保護されていても、チップが電気で動いている限り物理層からの漏洩を防げない。

**技術の魅力**: モデルを守るための暗号化・難読化はすべてソフトウェアのレイヤーで完結するが、CSI NNが突くのはその一段下、「演算そのものが放つ物理的な副作用」という誰も塞いでいない層。RSA秘密鍵を電磁波で盗む古典的なサイドチャネル攻撃の手法を、そのままニューラルネットの"設計図の盗聴"に横流ししている非対称性が効いていて、ソフトウェアの防御がどれだけ完璧でも意味を持たなくなる。

**本来どこで使われてるか**: 元々は暗号ハードウェアの安全性評価(スマートカードやセキュアエレメントの鍵漏洩の有無を調べる)分野で培われた電磁/電力サイドチャネル解析の手法。CSI NN以降、この手法はエッジAIチップやMLアクセラレータのIP保護・モデル抽出攻撃対策の評価基準としてハードウェアセキュリティ業界で使われるようになっている。
出典: https://www.usenix.org/conference/usenixsecurity19/presentation/batina
