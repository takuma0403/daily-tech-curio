### <a id="card-1"></a>🆕 宛名をCRCの中に隠した電波——Mode Sの「アドレス/パリティ」で、ADS-Bを出さない飛行機まで拾う 〔move: 仕様の目的外利用 / 領域: 無線/組み込み/ハードウェア〕

**事実**: 航空機のトランスポンダ（Mode S）の電文は、末尾24ビットの置き方が種類で違う。ADS-B（DF17）では末尾が普通のCRCそのもの。ところがレーダーの問い合わせへの返答（DF0, 4, 5, 20, 21など）では、末尾24ビットが「CRC XOR 機体のICAOアドレス」になっている。つまり宛名（機体の24ビット固有番号）は平文では載っておらず、誤り検出符号の中に溶かし込まれている。受信側は「CRCを計算してAP欄とXORする」ことで初めてアドレスを取り出せる。

**何ができる**: RTL-SDRなどで1090MHzを受けるとき、ADS-Bを自分から放送している機体だけでなく、地上レーダーに応答しているだけの機体の電文も入ってくる。ADS-Bで一度でも見えたICAOアドレスの表を持っておき、AP形式の電文のCRCとXORして「表の中のどれかに一致するか」で照合すれば、位置を放送しない間の機体でも「そこにいる」と分かる。一致しなければ雑音か未知の機体として捨てられるので、壊れた電文の足切りも兼ねる。さらに踏み込んで、一定時間の受信距離の最大値を毎日ログすれば、電波の飛びやすさ（空の機嫌）の指標にできる、はず——こちらは未検証の仮説で、まず自宅の窓で数日ためして見る使い方。

**技術の魅力**: 「誤り検出」と「宛名」を同じ24ビットで兼ねる、1ビットも無駄にしない設計。アドレスを別枠で持たない代わりに、受け手が「宛名の候補」を知っていないと読めないという非対称が生まれる。誤り検出符号が、そのまま宛先フィルタとして働いている。

**本来どこで使われてるか**: 航空管制の二次監視レーダーとTCAS（衝突防止装置）。地上局や他機の問い合わせに機体が返答し、受け手は自分の知るアドレスと照合して「自分宛か」を判定する。電文形式ごとのパリティの扱いは、オープンソースのADS-B/Mode Sデコーダのドキュメントや、ADS-Bのセキュリティ論文でも解説されている。

### <a id="card-2"></a>🔍 チェスAIの盤面ハッシュで、2台のフォルダの「同じ」を8バイトで確かめる——Zobristを同期に移植 〔move: 異分野の手法移植 / 領域: データ/同期/ストレージ〕

**事実**: チェスエンジンは盤面の同一性を素早く見るため、Zobristハッシュを使う。駒×マスの組み合わせごとに固定の64ビット乱数を割り当て、盤上にある組み合わせの乱数を全部XORしたものが盤面のキーになる。XORは自分自身が逆演算なので、駒を動かすときは「元のマスの乱数をXOR、移動先の乱数をXOR」の2回で更新でき、残りの62マスは再計算しなくていい。

**何ができる**: これをファイル同期に移す。各ファイルを「名前+内容のハッシュ」から作った64ビット値とみなし、フォルダ全体のキーをその全部のXORにする。ファイルを追加・削除・更新するたび、その1ファイル分をXORするだけでフォルダのキーが更新できる。2台の機器はキー8バイトを交換するだけで、「完全に同じか」をほぼ確実に判定できる。違うときは、ディレクトリを分割して部分ごとのキーを比べれば、差のある場所へ二分探索できる。ネットワークも読み書きも、全ファイルの一覧を送る方式よりずっと軽い。ただしXORは重複の扱いが弱く（同じ値を2回入れると消える）、衝突の可能性もゼロではないので、最終確認は別途ハッシュ全比較か、更新の連番を足す工夫が要る。

**技術の魅力**: 「盤面」と「フォルダ」という全く無関係な対象が、「要素の集合が1つの数に畳まれ、1要素の出入りがO(1)で反映できる」という同じ構造を持っていた点。チェスAIが探索中に何百万回も盤面を動かしても重くならない理由が、そのまま同期の差分検出の効率に化ける。

**本来どこで使われてるか**: チェスエンジンの置換表（同じ局面を二度計算しないためのキャッシュ）。Chess Programming Wikiに詳述があり、局面の更新がXOR数回で済むこと、衝突対策に置換表に完全キーを保存して照合することなどが説明されている。
出典: https://www.chessprogramming.org/Zobrist_Hashing / https://softwarebits.substack.com/p/involutions-the-license-to-update

### <a id="card-3"></a>💡 「11」が来たら区切り——フィボナッチ符号は、ビットが化けても勝手に立ち直る 〔move: 制約の極端化 / 領域: ワイルドカード(符号理論)〕

**事実**: フィボナッチ符号は、整数をフィボナッチ数の和（ゼッケンドルフ表現：連続するフィボナッチ数を使わない）で表し、その桁を並べて最後に1を足した符号。ゼッケンドルフ表現には「1が連続しない」性質があるので、足した最後の1が作る「11」は符号語の中でただ1か所、つまり終わりの合図になる。長さ情報を別に持たず、「11」を見たら区切り、というだけで可変長の数が流せる。

**何ができる**: 手で叩く、LEDを手でチカチカさせる、赤外線を雑に点滅させる——ビットが時々化ける粗い通信路で、小さい整数の列を送りたいとき。普通の可変長符号は1ビット化けるとその後が全部ずれるが、フィボナッチ符号は「0が来た時点で誤りの伝播が止まる」。単一ビットの誤りで壊れる範囲は限られ、元の列との編集距離は最大でも3程度に収まる。デモとしては、手元のボタンで長短を入力してフィボナッチ符号で数列を送り、わざと数ビット壊して受信側がどこから復帰するかを見せると、5分で動く。

**技術の魅力**: 「連続した1を使わない」という数論の性質が、そのまま通信の同期機構になっている。誤り訂正符号ほど重くなく、固定長ほど無駄でもない、ちょうど真ん中にある実用的な頑丈さが面白い。

**本来どこで使われてるか**: 主に理論と、一部のデータ圧縮や、小さな整数が多く出るデータの符号化で研究・利用される。Wikipediaなどに、符号語の構造と、誤りが起きたときの影響が限定される性質が整理されている。
