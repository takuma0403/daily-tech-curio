### <a id="card-1"></a>🆕 「生き続けろ」が来ない限り消える——Apoptotic Computingという死を前提にしたセキュリティ設計 〔move: 異分野の手法移植 / 領域: セキュリティ/認証〕

**事実**: 多細胞生物の細胞は、外から絶えず「生きていろ」という信号(生存シグナル)を受け取り続けない限り、自ら計画的に死ぬ——これがアポトーシス(プログラム細胞死)で、傷や病気で壊れる「壊死」とは違い、初期状態がそもそも「死」であるという点が特異だ。北アイルランドのUlster大学のRoy SterrittとMike Hincheyは2002年ごろから、この「デフォルトは死」という発想をそのまま計算機システムに輸入し、Apoptotic Computing(アポトーティック・コンピューティング)という研究領域を立ち上げた。核ミサイルの二重鍵になぞらえ、「死ね」という信号と「猶予(生かし続けろ)」という信号の2つが常にせめぎ合い、後者が途切れた瞬間に既定動作として自壊が始まる設計だ。

**何ができる**: 通常のセキュリティ設計は「まず正常(生存)を初期状態にし、侵害を検知したら例外的に殺す」という順序を取る。これを丸ごと逆転させ、IoT/センサーノードやエージェントの既定状態を「消滅する」にしておき、信頼できるコントローラから定期的に届く暗号署名付きの生存シグナルだけがそれを引き延ばす、という構成にできる。ノードが奪取される・通信が妨害される・物理的に盗まれる・マルウェアに乗っ取られる——原因を個別に検知するロジックを一切書かなくても、「生存シグナルが来なくなる」という一つの現象さえ捕まえれば、あらゆる侵害パターンを同じ既定動作(自壊)でカバーできてしまう。

**技術の魅力**: 普通、自己消去機能は「生きているのが当たり前」のシステムに後から足す特別モードとして実装される。Apoptotic Computingはこの極性を反転させ、「死んでいるのが当たり前で、生存の方が特別な許可を要る」という生物の細胞そのままの前提に立つ。攻撃の手口を先回りして列挙する代わりに、「猶予信号が来ない」という単一の失敗モードにあらゆる未知の攻撃経路を集約してしまう非対称性が効いている。

**本来どこで使われてるか**: Sterritt・Hinchey両氏の研究は自律コンピューティング(Autonomic Computing)の一分野として、NASA関連のワークショップにも論文が採録され(NASA Technical Reports Serverにアーカイブ)、宇宙探査用の群ロボティクスへの応用("Apoptotic Robotics: Programmed Death by Default")や、コンピューティング・ロボティクス・セキュリティ分野向けの特許(US8983882B2)にも発展した。より具体的な実装例として、2018年のワイヤレスセンサーネットワーク研究(arXiv:1808.01108)は、自己回帰予測とニューラル予測の両方から外れた値を出すノードを「悪意あり」と判定した際、実際にRAMと暗号鍵の消去・バッテリーの意図的放電・無線モジュールの物理破壊・近隣ノードリストからの削除までを自動実行する自壊手続きを提案している——ソフトウェアの統計判定が、そのまま物理的な破壊行動に直結する設計になっている。
出典: https://patents.google.com/patent/US8983882B2/en / https://arxiv.org/abs/1808.01108 / https://archive.org/details/nasa_techdoc_20050137699

### <a id="card-2"></a>🔍 CPUの"疲れ具合"だけを教えるAPIが、タブの壁を越えて喋る——Compute Pressure APIの隠しチャンネル 〔move: サイドチャネル/副作用の利用 / 領域: フロントエンド/グラフィックス〕

**事実**: Compute Pressure API(W3C草案、Chromium系ブラウザに実装済み)は、Webページが自分のCPU負荷状況を"nominal/fair/serious/critical"の4段階という粗い区分だけで受け取れるAPIだ。動画会議アプリが負荷が高いときだけ解像度を落とす、といった用途を想定して設計されており、指紋収集を防ぐためわざと生の周波数やコア数のような精密な数値は一切渡さず、アクティブなタブでも1秒に1回、非アクティブなタブなら10秒に1回までしか状態を読めないようレート制限もかけている。ところが、CPUという計算資源はブラウザ内の全タブが同じ1個の物理チップを共有しているため、この"粗い読み取り"であっても、他のオリジンが起こした負荷変化がそのままこのAPI越しに透けて見えてしまう。

**何ができる**: サードパーティのトラッキングスクリプトが、Cookie・localStorage・BroadcastChannelなど通常の通信手段を全てブロックされたSame-Origin Policy下の別タブ・別iframe同士でも、片方が意図的にCPUを高負荷にしたり待機させたりして"0/1"のビット列を作り出し(送信側)、もう片方がCompute Pressure APIでその変化パターンを読み取る(受信側)ことで、正規の通信路を一切使わないクロスサイトの隠しチャネルを組める。ストレージ分離(パーティショニング)が完璧に効いていても、CPUという物理的に共有された1つの資源がある限り、送受信の両端さえ用意すればビットは漏れる。W3Cの仕様Issueでもこの悪用シナリオがそのまま指摘されている。

**技術の魅力**: Cookieでもネットワークリクエストでもなく、シリコンチップの発熱そのものがAPI経由で覗ける、という点が新しい。仕様側は値を4段階に粗くし、読み取り頻度も制限することで対策したつもりだが、「自分のマシンの状態を知りたい」という機能の本質そのものが、「同じマシンの上にいる他人の存在も知れてしまう」という副作用と表裏一体になっている。粗くしても頻度を絞っても、帯域が細くなるだけで漏れる経路自体は塞げない、という非対称性がここでも効いている。

**本来どこで使われてるか**: 想定用途は適応型のWebアプリで、たとえばビデオ会議サービスがCPU負荷が"critical"になった瞬間にエンコード解像度やフレームレートを自動的に落とす、WASMを多用するWebゲームやアプリが背景処理を間引く、といった省負荷制御に使われる。ChromiumがIntent to Experimentとして実験導入し、現在W3Cで仕様策定が進められている。標準化の議論そのものの中で、クロスサイトの隠しチャネルとして悪用できるというプライバシー上の懸念(GitHub Issue #197)が提起され、レート制限は緩和策として盛り込まれたが、チャネル自体の完全な封鎖には至っていない。
出典: https://www.w3.org/TR/compute-pressure/ / https://github.com/w3c/compute-pressure/issues/197 / https://groups.google.com/a/chromium.org/g/blink-dev/c/HzVV-sM97T0

### <a id="card-3"></a>💡 過去のノードには二度と触らない、という一点だけで生まれた山脈——Merkle Mountain Range 〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: 普通のMerkle木は要素を1つ追加するたびに、根までの経路上のハッシュをすべて作り直す必要があり、木全体がバランスの取れた1本の二分木であることを前提にしている。Merkle Mountain Range(MMR)は、「一度書き込んだノードのハッシュには二度と手を触れない」という一点だけを極端に守るために設計を丸ごと変えた構造だ。木を1本にまとめず、サイズが2の冪乗になる「完全二分木」を複数並べた森として扱い、新しい葉は常に一番右側の山に足し、2つの子がちょうど揃った瞬間だけ新しい親ノードを1つ生やす。単一の根がないので、各"山の頂上(peak)"どうしをまとめてハッシュしたものを合成ルートとして使う。

**何ができる**: 台帳・監査証跡・コミット履歴のような、追記だけが起き続ける巨大なデータセットに対して、要素を1つ足すたびの追加コストを償却でおよそ2n回のハッシュ計算程度に抑えたまま、任意の過去の要素について「確かにこのデータセットに含まれていた」という所属証明を、標準的なMerkle証明とその時点の各"山の頂上"リストという軽量な形で発行できる。しかも過去に発行した証明は、その後どれだけ要素が追加されても古いまま有効であり続け、あとから発行される証明はむしろ以前の証明を包含するスーパーセットになる。ライトクライアントは全履歴をダウンロードすることなく、1件の記録の存在だけを検証できる。

**技術の魅力**: 普通の木構造の設計は、回転やマージのロジックを足しながら「バランスを保つ」ことを目標にする。MMRはその逆で、「過去には絶対に手を触れない」という不可侵の制約を先に置き、バランスの美しさそのものを差し出すことで初めて成立している。結果として生まれる形は、サイズの異なる完全二分木がいくつも並ぶでこぼこした"山脈"——教科書的にはお世辞にも美しくない構造だ。だが、この不揃いさこそが、過去のノードを不変に保ったまま追記だけを続けられるという性質の直接の代償であり原因でもある。最適化ではなく制約を先に極端化すると、構造そのものの見た目が変わる、という好例になっている。

**本来どこで使われてるか**: MimbleWimbleベースの暗号通貨Grinが、カーネル・アウトプット・レンジプルーフをそれぞれ専用のMMRとして保持し、ブロックチェーン全体の検証コストを抑えるために採用しているのが代表例。同様の構造はNervos CKB、Beam、一部のZcash提案など複数のチェーンに広がっており、あるチェーンの状態を別のチェーンから軽量に検証するFlyClient型のクロスチェーン・アンカリングにも使われている。ブロックチェーン以外でも、追記専用ログを扱う分散システム一般(監査証跡・透明性ログ)への応用として研究が続いている。
出典: https://docs.grin.mw/wiki/chain-state/merkle-mountain-range/ / https://github.com/zmitton/merkle-mountain-range / https://eprint.iacr.org/2025/234.pdf
