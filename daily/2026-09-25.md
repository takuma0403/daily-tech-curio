### <a id="card-1"></a>🆕 「今が何時か」を諦めない時計が、いつのまにか嘘発見器になる——Hybrid Logical Clockという因果性の物差し 〔move: サイドチャネル/副作用の利用 / 領域: データ/同期/ストレージ〕

**事実**: 分散システムの時刻には昔から二択しかなかった。因果関係は完璧に守るが「今何時か」には無関心なLamportの論理クロックか、実時間には忠実だがノード間のズレでイベント順序が壊れる物理クロックか。Hybrid Logical Clock（HLC）はこの2つを1つの64bit値に融合し、「物理時刻成分は実際の壁時計より絶対に遅れない」「かつ既知の許容誤差ε以内に収まる」「かつ因果関係も保つ」という三重の保証を同時に満たす。CockroachDBやMongoDB、YugabyteDBが、Google SpannerのTrueTimeのような専用原子時計を使わずに分散トランザクションを順序付けられるのはこの仕組みのおかげ。

**何ができる**: 「実時間から一定範囲εを超えて外れたHLCは無条件に不正とみなせる」という性質は、単なる順序付けの副産物のはずが、そのままオフラインでも効く改竄検知器に化ける。中央のNTPサーバーにもブロックチェーンにも問い合わせず、受け取った側のローカルな物理クロックと比べるだけで「このノードの時計は壊れているか、リプレイ攻撃で過去の書き込みを未来のふりをして再送してきたか」を判定できる。オフライン同期するローカルファーストアプリで、各端末のクロックが多少ズレていても正しい書き込み順序（LWW）を復元しつつ、同時にネットワークなしのメッシュ同期でも成り立つ不正ノード検出を無料で手に入れられる。

**技術の魅力**: 本来水と油の2つの時計思想を無理やり同じ整数に押し込めた結果、その融合が生む「実時間との許容ズレが数学的に有界」という副作用だけが独り歩きして、順序保証とは無関係などの検知用途に転用できてしまう。正しく同期された時計を持っていない限り、この境界条件を満たす偽のHLCを作ること自体が難しいという非対称性が効いている。

**本来どこで使われてるか**: CockroachDBはノード間で許容する最大オフセット（MaxOffset）を全ノードで静的に一致させ、心拍サービスがそれを強制する形でHLCを分散トランザクションの一貫したスナップショット生成に使っている。MongoDBのクラスタタイムやYugabyteDBも同様に、原子時計なしで因果一貫性を実現するためにHLCを採用している。
出典: https://www.cockroachlabs.com/glossary/distributed-db/hybrid-logical-clock-hlc-timestamps/ / http://muratbuffalo.blogspot.com/2014/07/hybrid-logical-clocks.html

### <a id="card-2"></a>🔍 流れ星の残り火に電波を跳ね返して、山奥の積雪データを50年運び続けた——Meteor Burst Communicationsという“ついで”の通信網 〔move: 物理現象へのピギーバック / 領域: ワイルドカード(電波伝搬・気象観測)〕

**事実**: 毎日、無数の流星が高度50〜75マイル付近の大気で燃え尽きており、その軌跡には一瞬〜数秒だけ電離したガスの筋が残る。この一時的な電離トレイルはVHF電波を鏡のように反射でき、最大約2,250km離れた2つの地上局の間に束の間の通信路を開く。人工衛星でも中継局でもなく、誰も打ち上げていない・誰にも止められない自然現象にただ便乗するだけの通信手段がMeteor Burst Communications（流星バースト通信）。

**何ができる**: 基地局が低出力の問い合わせ信号を送り続け、たまたま良い位置に流星が流れた瞬間だけ、順番待ちしていた遠隔局がその一瞬の窓（数百ミリ秒〜数秒）に溜め込んだセンサーデータを一気に送り返す store-and-forward 網が組める。USDAのSNOTELはまさにこれを使い、衛星アンテナが着氷し、携帯回線もない北米ロッキー山脈の500ヶ所以上の遠隔観測地点から積雪量データを50年近く収集し続けた。皿もアンテナの向きも要らず、次の流星を待つだけでいい。

**技術の魅力**: 「ノイズやランダム性は排除すべき」という工学の常識を逆手に取り、システムの稼働率そのものを「頭上を十分な頻度で流星が通過すること」に賭けている点が面白い。流星群の時期でなくても1分間に100個以上は自然発生するため、これが実際に成立してしまう——誰も所有せず、撃墜もできず、1秒ごとに"衛星"が生まれ変わる無料の中継網。

**本来どこで使われてるか**: 米農務省の自然資源保全局（NRCS）はSNOTEL網で40年以上この方式を運用し、11州500以上の雪盆(snow pillow)観測点から水資源予測・洪水予測用のデータを集め続けたが、2023年に衛星・セルラー通信への移行でこの用途を終了した。冷戦期には軍もジャミングに強い低帯域通信として同種の技術を利用していた。
出典: https://en.wikipedia.org/wiki/Meteor_burst_communications / https://en.wikipedia.org/wiki/SNOTEL

### <a id="card-3"></a>💡 デザインツールの色を吸い取るスポイトが、ブラウザの外まで覗き見る——EyeDropper APIというcanvas taintの抜け道 〔move: 仕様の目的外利用 / 領域: フロントエンド/グラフィックス / レンズ: 無関係な2技術の組み合わせ〕

**事実**: Webページは本来、他ドメインのピクセル色を絶対に読めない。他オリジンの画像を`<canvas>`に描くとそのcanvasは「汚染(tainted)」扱いになり、`getImageData`はセキュリティエラーを投げる——ブラウザが10年以上かけて固めてきたこの分離モデルを、EyeDropper APIはまるごと迂回する。ページの中には一切描画せず、OS純正のカラーピッカーカーソルへ制御を渡すだけの仕組みで、そのカーソルは画面上のどのピクセルでも——他タブ、他オリジン、ブラウザの外のウィンドウすら——サンプリングでき、結果のHex値だけがそのままスクリプトへ返る。

**何ができる**: `getDisplayMedia()`の画面キャプチャ許可プロンプトを一切要求せずに「今カーソルの下にある色」を正当に取得できてしまう。WICG仕様自身のSecurity章が名指しで警告しているのは、ユーザーをだましてスポイトが開いた状態のままダブルクリックさせ、カーソルの下にある機微な他オリジンのピクセル（例: 別サイトのログイン状態で色が変わる要素）の色を1クリックにつき1ビットだけ抜き取る攻撃シナリオで、サンプルを重ねれば情報量を積み増せる。

**技術の魅力**: 「デザイナー向けに色を拾わせるだけ」の地味で低ドラマなAPIが、バグではなく意図的な設計判断として、ブラウザが積み上げてきたクロスオリジン分離モデルの外側にすっぽり出てしまっている。「任意のピクセルをサンプリングする」という要件を素直に実装するとOSネイティブのピッカーに頼るのが一番簡単だった、というだけの理由で、何年もかけて固めたセキュリティ境界が2行の利便APIに素通りされる。

**本来どこで使われてるか**: Chromium系ブラウザ（Chrome, Edge）に実装済みで、Canvaのブラウザ版エディタやFigmaのようなブラウザ内デザインツールが、キャンバス上の色をピックする用途で正規に使っている。以前はスクリーンショットをアップロードして色を拾うしかなかった作業を、この1APIが置き換えた。
