### <a id="card-1"></a>🆕 LANケーブルの「どこで切れたか」をNICが勝手に測っている——ethtool --cable-testを“巻き尺”に使う 〔move: センサーの転用 / 領域: ネットワーク/プロトコル〕

**事実**: 一部のEthernet PHYチップは、ケーブルに短いパルスを送り出して反射が戻るまでの時間を測るTDR（Time Domain Reflectometry）を内蔵している。Linuxには`ethtool --cable-test eth0`というコマンドがあり、対応ドライバなら対ごとに「正常／断線(open)／ショート」を報告し、故障点までの距離も返す。カーネル側のAPIでは故障位置がセンチメートル単位の値で渡される。PHYによってはTDRとALCD（Active Link Cable Diagnostic）など複数方式を持ち、生のTDRデータを取り出す拡張も議論されている。つまり多くの人のパソコンやルーターの中に、使われないまま「ケーブル用の簡易レーダー」が眠っている。

**何ができる**: 壁の中や天井裏に這わせたLANケーブルの断線点を、脚立に登る前に数値で当てられる。さらに一歩踏み込むと、ケーブルの先を開放したまま定期的にテストを回して「反射までの距離」を記録する“巻き尺”にできる。たとえば長さ既知のケーブルを温室やベランダに張り、温度で変わる伝搬時間の微差をログに残す、ケーブルを踏まれた・曲げられた場所の特定に使う、といった物理世界の監視を、追加センサーなしでSBC（ラズパイ等）1枚で始められる。ただし精度はPHY依存で、数メートル単位の粗さのものも多いので、まず手持ちの機種で既知の長さを測って癖を確かめるのが前提。

**技術の魅力**: 「通信のための部品が、通信を止めて“線そのもの”を測っている」という視点の反転。NICは普段データしか見ないが、診断モードに入った瞬間だけ配線の物理（長さ・インピーダンス不整合）を見る眼になる。専用の測定器（数万円〜）が、すでに買ったハードの中に入っていたという非対称性が効いている。

**本来どこで使われてるか**: 施工後の配線チェックや、故障ケーブルの切り分けなどの保守用途。Linuxカーネルには`phy_cable_test_fault_length`のような専用のPHY APIがあり、ethtool netlinkから呼べる。TIのPHYドキュメントでも`ethtool --cable-test`によるopen回路検出の使用例が載っている。

### <a id="card-2"></a>🔍 電波の巻き尺は、周波数を飛ばして位相を読む——BLE Channel Soundingで「呼吸する壁」を測る 〔move: 異分野の手法移植 / 領域: 無線/組み込み/ハードウェア〕

**事実**: Bluetooth Core 6.0で追加されたChannel Sounding（旧称HADM）は、2台の接続済み機器がPBR（Phase-Based Ranging、位相ベース測距）とRTT（往復時間）の2方式で距離を測る機能。PBRでは一方（イニシエータ）が信号を送り、他方（リフレクタ）が返し、その位相を測る。これを多数の周波数チャネルで繰り返し、各周波数の波長は既知なので「全部の位相を同時に満たす距離」を逆算する。RTTは主にセキュリティ用で、粗い距離でPBRの結果を検算し、中継攻撃（リレーアタック）を弾く役割を持つ。NordicのnRF54L15やSilicon LabsのEFR32BG24などが対応チップを出している。

**何ができる**: 本来は「スマートキーの距離判定」だが、位相は波長（2.4GHz帯で約12cm）より細かい変位に敏感なので、2つのノードを部屋の対角に置いて周期的に測れば、人の動き・扉の開閉・大きな金属物のわずかな移動で距離推定が揺れるのを拾える、はず。ここでは「距離が絶対値でどれだけ正しいか」より、「同じ2点間の推定値が、何かに触れられた瞬間にだけ揺れる」ことを使い、壁際に置いたノード間で“誰かが通ったかどうか”だけを電波の揺れから読む。ベンダーが謳う精度は10〜50cm級と幅があり、実環境ではマルチパスで荒れるので、これは実験としての使い方。

**技術の魅力**: 位相を1回測っても、2πごとに同じ値になるので距離は曖昧。それを周波数を何十個も飛ばしながら測ることで「1つの周波数では分からない答えを、複数の周波数の食い違いで確定させる」点が、レーダーの周波数掃引（FMCW）や測量の干渉計と同じ発想。それをBluetoothの安いチップが、接続の裏で普通にやるようになった。

**本来どこで使われてるか**: 自動車のデジタルキー、スマホ-イヤホン探し、屋内の資産追跡など、「近くにいるか」を高精度に判定する用途。SIGは「中継攻撃対策に使える安全な測距」と位置づけ、RTTでPBRを検算する設計にしている。

### <a id="card-3"></a>💡 ブラウザの「席を立った」を、半田ごての主電源につなぐ——Idle Detection APIで消し忘れを許さない 〔move: 人間/身体をプロトコルの一部にする / 領域: フロントエンド/ブラウザAPI〕

**事実**: Idle Detection API（`IdleDetector`）は、ユーザーがキーボード・マウスを一定時間触っていないこと（`userState`: active/idle）と、画面がロックされているか（`screenState`: locked/unlocked）を、ページが通知を受け取れる仕組み。`start()`にミリ秒の閾値（MDNの例は60_000＝60秒）を渡す。利用には許可（permission）が必要で、トップレベルのフレームに限定される。Chromium系のChrome 94からで、FirefoxとSafariは未対応。ブラウザの外の全体の操作状況を見られるのが他のイベント（`visibilitychange`など）との違い。

**何ができる**: 机の上のスマートプラグ（HTTPで叩けるShellyやTasmota搭載品など）を半田ごての電源に噛ませ、作業用のブラウザタブで`IdleDetector`を動かす。画面がロックされた、または60秒以上操作がなかったら`fetch`でプラグをOFFにするだけ。「席を離れたら半田ごてが落ちる」物理のデッドマンスイッチが、マイコンもファームも書かずに半日で作れる。戻ってきて操作した瞬間は、勝手に通電せず、画面に「再通電しますか」と聞いて人間に最終判断を返す。

**技術の魅力**: 本来は「チャットアプリで在席ステータスを自動で変える」ための仕様だが、「人間が手を止めた」というのは、物理世界の安全装置にとって最良のトリガーになる。人を“センサー兼プロトコルの一部”として扱い、人間側が生存信号（操作）を送り続ける限り電気が流れる、という鉄道のデッドマン装置と同じ構造をブラウザAPIで再現するのが面白い。ただし許可UIがあるため、ページ側からこっそり使えない（＝逆にプライバシーに敏感な設計）点も含めての発想。

**本来どこで使われてるか**: WICGの提案の動機は、チャットや協働ツールでの在席表示、キオスク端末の「放置されたらセッションをリセット」など。仕様は「idle-detection」の権限を設け、粒度を制限できるようにしている。
