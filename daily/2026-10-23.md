### <a id="card-1"></a>🆕 「ある？」の問い合わせを、サーバーに送らずに済ませる——静的ファイルに畳んだ集合 Xor filter 〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: Xor filter は「この要素は集合に入っているか」を答える確率的データ構造で、Bloom filter や cuckoo filter の仲間。作り方が変わっていて、各キーを3か所のハッシュ位置に対応させ、3か所の値をXORしたものがキーの指紋（例: 8ビット）と一致するように配列を組む。問い合わせは3か所を読んでXORを比べるだけ。代わりに集合は作った時点で固定（後から追加できない）。Dietzfelbinger と Pagh が理論として記述していたものを、Graf と Lemire が初めて実測し、Bloom や cuckoo より小さく速くなり得ると示した。

**何ができる**: 「漏洩パスワード一覧」「悪性ドメイン一覧」「既知の単語集」のような、更新が日次〜週次で十分な巨大集合を、数MBの1ファイルにして静的ホスティングに置く。ブラウザやマイコンがそれを丸ごと落として手元で照合すれば、「このパスワードは漏洩済みか」という問い合わせ自体が誰にも送られない。応答は「たぶんある／確実にない」で、誤検出率は指紋のビット数で決まる。

**技術の魅力**: 「問い合わせをサーバーに投げる」前提を、「答えの方をクライアントに配る」に反転できるのが肝。Bloom filterは追加できる代わりに余分な領域が要るが、集合を固定すると決め切るだけで、理論下限により近い容量に収まる（論文では下限に対し約23%増。Bloomは約44%増）。続報の Binary fuse filter は約13%増まで詰めている。「あとから足せない」という不自由を、サイズと速度に交換している。

**本来どこで使われてるか**: 本来は大規模DBやキャッシュの手前で、ディスクを引く前に「存在しないこと」を安く確定するための前置きフィルタ。論文では静的集合向けに Bloom の約2倍の問い合わせ速度を報告している。ライブラリ実装（FastFilter系）が複数言語で公開されている。
出典: https://arxiv.org/abs/1912.08258 / https://arxiv.org/abs/2201.01174

### <a id="card-2"></a>🔍 乗算器のないマイコンで sin・cos・atan2 を出す——爆撃機のアナログ計算機を置き換えたCORDIC 〔move: レガシー/廃止予定機能の蘇生 / 領域: 無線/組み込み/ハードウェア〕

**事実**: CORDIC は、加算・減算・ビットシフトと小さな表だけで三角関数を出す反復法。ベクトルを「tan が 2 のべき乗になる角度」だけ少しずつ回し、回しすぎたら戻す。1ステップで約1ビットの精度が確定する。Jack Volder が Convair で考案し（1956年着想、1959年に公開）、B-58爆撃機の航法計算機でアナログのレゾルバを置き換えるのが目的だった。

**何ができる**: 乗算命令のない小型マイコンやFPGAで、角度から (cos, sin) を、逆に (x, y) から角度（atan2）を求められる。たとえば地磁気センサーの2軸値から方位角を出す場合、必要なのは atan(2^-i) を16個ほど並べた表と、ループ16回の加減算とシフトだけ。浮動小数点ライブラリも `atan2f` も要らず、コードは数十行。

**技術の魅力**: 「乗算を避ける」ためだけに、回転を“2のべき乗の刻みの探索”に作り替えている点。二分探索で角度を絞るのと同じ構造を、ベクトルの回転で実現している。しかも同じ回路が、入力の与え方を変えるだけで回転モードと角度算出モード（vectoring）の両方で動く。

**本来どこで使われてるか**: 当初は航法計算機。以降、Litton・Kearfott・Sperry・Collins などが航法用途に組み込み、手持ち電卓（HPのHP-35は十進版を採用）にも波及した。今も乗算器を省きたいFPGA/ASICの演算ブロックで定番。
出典: https://en.wikipedia.org/wiki/CORDIC / https://blog.flyingcoloursmaths.co.uk/dictionary-of-mathematical-eponymy-volders-algorithm

### <a id="card-3"></a>💡 黙るほど全員に行き渡る——Trickleタイマーは「もう聞いた」を数えて口を閉ざす 〔move: 異分野の手法移植 / 領域: ネットワーク/プロトコル〕

**事実**: Trickle は RFC 6206 で標準化された、低電力・ロスの多い無線網向けの配信タイマー。各ノードは区間 I の途中のランダムな時刻に「自分の持つバージョン」を1回ささやく。ただし、その区間で他ノードから同じ内容を k 回以上聞いていたら黙る。違うバージョンを聞いたら区間を最短（Imin）に戻して急いで直し、一致が続けば区間を倍々に伸ばして（上限 Imax）ほぼ無音になる。

**何ができる**: 中央サーバーも経路表もなしに、数十台のセンサーに設定やファームウェア世代を行き渡らせる。同じ版が揃っている間は電波をほとんど使わず、1台に新しい版を入れた瞬間だけ局所的にざわつく。BLE広告やサブGHz無線の素朴な送信ループに、このタイマーを被せるだけで実装できる。

**技術の魅力**: 送信を「全員が定期的にやる」から「聞こえなかったときだけ誰かがやる」に変えると、密度が上がっても通信量が増えない。RFC の要旨は、通信レートが密度に対して対数的にしか増えないという点で、各ノードの送信率は1/nになる。固定の k は密度が違う網では不公平になるという後続研究もあり、ここが調整の余地になっている。

**本来どこで使われてるか**: IoT向けの経路制御 RPL（RFC 6550）が経路情報の広告に、マルチキャスト配信の MPL（RFC 7731）がデータ再送の抑制に使う。起源はセンサーネットワークのコード配布の研究。
出典: https://www.rfc-editor.org/rfc/rfc6206 / https://arxiv.org/abs/1509.08664
