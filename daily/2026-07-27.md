### <a id="card-1"></a>🆕 クリックする指が「計算する」を担う——CSSだけのチューリング完全機械 〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: CSSの `:checked` 疑似クラスと一般兄弟結合子(`~`)を組み合わせると、あるチェックボックスの状態に応じて、DOM上で離れた位置にある別の要素のスタイルを分岐させられる。これを敷き詰めて重ねると、初等セルオートマトンの「ルール110」——それ自体がチューリング完全であることが証明済み——の1ステップぶんの遷移規則を、CSSセレクタの組み合わせだけで表現できる。JavaScriptは一行も使わない。ただしCSSには「今の盤面から次の盤面を自動計算して進める」機能はないので、次の一手を実際に押し進めるのは人間の指のクリックそのもの、というのが肝になる。

**何ができる**: この仕組みを積み上げれば、理論上どんなロジック(ブール回路・簡易パズルソルバー・簡易ゲーム)もJS禁止環境の中で実装できる証明可能な土台が手に入る。実際に「CSSだけで書かれたx86 CPUエミュレータ」まで話題になったことがある。ブラウザ拡張のCSP、HTMLメール、JSが根こそぎブロックされる場所でも、利用者にクリックを続けさせられさえすれば「計算」が成立してしまう。

**技術の魅力**: セレクタは本来「この見た目にこの装飾を当てる」ためのマッチング言語であり、条件分岐やジャンプ先を書く言語ではない。それなのに`:checked`という1ビットの状態と、兄弟結合子という空間的な参照だけで、if文とジャンプ先の役割を同時に肩代わりさせてしまう。人間のクリックを「クロック信号」に仕立てる発想が、装飾専用言語を演算装置へとひっくり返す非対称性になっている。

**本来どこで使われてるか**: `:checked`と兄弟結合子は、本来JSなしのタブ切り替えUIやアコーディオン、モーダルの開閉(いわゆる「checkbox hack」)を実現するためにCSS3で広まった地味なテクニックに過ぎない。それが積み上げに積み上げられて、Rule 110のシミュレーションやCSSのチューリング完全性そのものの証明にまで転用されている。
出典: https://notlaura.com/is-css-turing-complete/ / https://conwaylife.com/wiki/OCA:Rule_110

### <a id="card-2"></a>🔍 非同期しか許さないはずのpostMessageが、Atomics.waitで足止めを食らう——OPFSを本物のファイルシステムに変える 〔move: サイドチャネル/副作用の利用 / 領域: データ/同期/ストレージ〕

**事実**: ブラウザのWeb Workerはメインスレッドと`postMessage`でしか会話できず、これは常に非同期。ところがWASMマルチスレッド向けに追加された`Atomics.wait()`は、共有メモリ上のある値が変わるまで呼び出し元のスレッドを本当にブロックして待つという、JSの世界では異色の同期プリミティブを提供する。一方Origin Private File System(OPFS)の`createSyncAccessHandle()`は真の同期read/writeを提供するが、「メインスレッドを絶対にブロックしない」というブラウザの原則があるため、Web Worker内でしか呼び出せない制限が付いている。

**何ができる**: この2つを組み合わせると、メインスレッドから見て「あたかも同期呼び出しであるかのように」Workerにファイルの読み書きを依頼できてしまう。メインスレッドは`SharedArrayBuffer`越しにリクエストを書き込み、`Atomics.wait`で完了フラグが立つまで本当に停止する。裏でWorkerがOPFSに同期I/Oを行い、フラグを書き換えて起こす。SQLite WasmやDuckDB-wasmのVFS層は実際にこの「非同期プロキシWorker」方式で、ネイティブのCコードをほぼ無改造のままブラウザに移植している。

**技術の魅力**: `Atomics.wait`はもともとWebAssemblyのマルチスレッド計算(物理シミュレーションや動画エンコードの並列処理)向けに用意された低レベル同期プリミティブで、ストレージの話とは本来無関係。それをメインスレッドの「待たせ方」として転用することで、JS設計思想の核である「メインスレッドは絶対にブロックしない」という原則を、スペック違反なしにギリギリ迂回してしまう。非同期しか許さないはずの言語の中に、スレッド間の力ずくの同期をこっそり仕込む倒錯が効いている。

**本来どこで使われてるか**: OPFSの同期アクセスハンドルは、SQLite WasmやDuckDB-wasmのようにネイティブのCコードをそのまま移植したいWASMデータベースエンジンのために用意された機能。Atomics.waitはWebAssembly threadsプロポーザルの一部で、本来は計算量の多いWASMワーカー間の排他制御・同期待ちのために設計されている。Chrome for Developersのブログでも、SQLite WasmがOPFSと非同期プロキシWorkerの組み合わせで動く仕組みが解説されている。
出典: https://developer.chrome.com/blog/sqlite-wasm-in-the-browser-backed-by-the-origin-private-file-system / https://developer.mozilla.org/en-US/docs/Web/API/FileSystemSyncAccessHandle

### <a id="card-3"></a>💡 1983年の"匿名電子マネー"の理論が、CAPTCHAを黙らせる——ブラインド署名の転生 〔move: 異分野手法移植 / 領域: セキュリティ/認証〕

**事実**: 数学者David Chaumが1983年、銀行に使途を知られずに電子マネーを使うための「ブラインド署名」を考案した。銀行は中身を見ずに(盲目のまま)コインへ署名でき、後で使われた時もどのコインが誰に発行されたかを紐付けられない。2024年にIETFがRFC 9576として標準化したPrivacy Passは、この40年前の匿名電子マネー理論をそのまま「あなたはボットではない」という証明トークンの発行に横流ししている。

**何ができる**: 端末はあらかじめ、App Attest/DeviceCheckのようなハードウェアattestationなどで「私はボットではない」証明を発行者に見せ、盲目な状態でトークンに署名してもらう。後で別のサイトを訪れた際にそのトークンを提示するだけで、CAPTCHAを一切解かずに「正当なユーザーだ」と証明できる。しかも署名時の見た目と提示時の見た目が数学的に無関係になるため、発行者もサイトも「いつ・どこで発行されたトークンか」を突き合わせて追跡できない。Appleは2022年末以降、iOS 16以降の端末にPrivate Access Tokensとしてこれをすでに実装している。

**技術の魅力**: 匿名性の核心技術が、もともとマネーロンダリング対策とは真逆の「銀行に中身を見せずに署名させる」という金融犯罪寄りの発想だという点が捻れている。Web業界はCAPTCHAの精度を上げる方向(画像認識・行動分析)で戦い続けてきたが、Privacy Passは「本人確認はするが誰であるかは絶対に紐付けない」という真逆の設計で問題を解体する。40年間ほぼ理論のままだった暗号技術が、Cloudflare・Chrome・Firefoxが足並みを揃えて実装するインフラに化けた。

**本来どこで使われてるか**: ブラインド署名は本来、Chaumが設立したDigiCash社の電子マネー(ecash)のために考案された技術で、1990年代に実際に銀行と組んで実用化が試みられたが商業的には普及しなかった。その理論がRFC 9576としてPrivacy Passの基盤に採用され、hCaptchaやCloudflareのCAPTCHA代替、AppleのPrivate Access Tokensとして現在進行形で数十億デバイス規模に展開されている。
出典: https://www.rfc-editor.org/info/rfc9576/ / https://webdecoy.com/blog/private-access-tokens-pat-apple-captcha-killer/
