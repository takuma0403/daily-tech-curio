### <a id="card-1"></a>🆕 国際送金は今も、テレックスの35字グリッドに折り返されている〔move: レガシー/廃止予定機能の蘇生 / 領域: ワイルドカード(国際金融)〕

**事実**: SWIFTは1973年、当時の国際送金を支えていた電信テレックスの混乱(誤送信・二重送信・非標準フォーマット)を解消するために発足した銀行間ネットワークだが、皮肉にも自分が葬ったはずのテレックスの制約をフォーマット仕様として今も内蔵し続けている。基幹メッセージ規格MT(Message Type)は1行35文字までという桁数制限を持ち、使える文字も基本ラテン大文字・数字・一部記号の「Xキャラクタセット」に絞られている——これは1970年代のテレックス回線がそのまま運べた文字集合そのものだ。

**何ができる**: 2025年11月22日、SWIFTはMTとISO 20022(MX)の並行運用期間(coexistence)を正式終了させ、国際送金メッセージのMX一本化を宣言した。ところが完全移行できなかった金融機関のためにSWIFT自身がMT→MX変換のcontingencyサービスを提供し続けており、テレックス由来の35字グリッドと制限文字集合は「経過措置」という名の延命装置の中でなお生き続けている。しかも2026年11月には非構造化の住所欄(postal address)がCBPR+メッセージから正式に廃止される予定で、テレックス時代の亡霊は段階的にしか引導を渡されない。

**技術の魅力**: 標準化団体が自ら「もう要らない」と宣言して葬ったはずの技術が、仕様書の文字コード表という形で生き残り続けているのが面白い。誰もテレックス回線を運用していないのに、テレックスが敷いた物理的な制約だけが亡霊のように機能し続け、最新の即時決済システムの設計者でさえMT互換を保つ限りこの桁数と文字集合に縛られる。廃止したはずの制約が、廃止した本人の後継仕様の中に文字通り埋め込まれている。

**本来どこで使われてるか**: 現役の国際銀行間送金インフラそのもの。2025年時点でSWIFTは200以上の国・地域の11,500超の加盟機関を結び、1日平均約5,980万件のFINメッセージが行き交う(97%超は既にISO 20022形式だが、残りは今もMT変換を介する)。テレックス亡霊は数字の上ではもう少数派だが、金融機関の基幹システムの奥ではまだ現役で計算されている。
出典: https://www.paiementor.com/swift-formatting-rules-and-character-sets-of-mt-messages/ / https://www.swift.com/sites/default/files/files/iso20022-adoption-10-days-to-go-nov-2025-final.pdf / https://fintechprof.substack.com/p/the-swift-network-how-42-million

### <a id="card-2"></a>🔍 「届ける」ためのプロトコルで、届けない宣言をする——BGPブラックホールコミュニティ〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: BGP(Border Gateway Protocol)はインターネットの経路情報を交換し、「このIPアドレス群にはこう届けられる」という到達可能性を広告し合うためだけに存在するプロトコルだ。ところがRFC 7999は、この「届ける」ための仕組みを逆手に取り、`65535:666`という決め打ちの特別なコミュニティ値を1つ広告するだけで、隣接ASに「このIPプレフィックス宛のパケットは黙って全部捨ててくれ」と依頼できる標準化された作法を定義している。届けるための言語で、届けないことを宣言する。

**何ができる**: 大規模DDoS攻撃を受けた際、標的IPを`/32`のホストルートとしてこのBLACKHOLEコミュニティ付きで自分のアップストリームへ広告するだけで、攻撃トラフィックは自ネットワークに到達する前に、上流の巨大な帯域を持つISPやIXPのルータ群でまとめて捨てられる。専用の高価なDDoS防御アプライアンスがなくても、経路広告という1個のBGPメッセージが「世界中のルータへの遠隔一斉フィルタ命令」に化ける——これがRemote Triggered Black Hole(RTBH)フィルタリング。実装によっては次のホップをRFC 7999が指すディスカード用アドレス(IPv6ならRFC 6666の`100::/64`)へ書き換え、経路情報の「転送先」欄そのものを「捨て場」に変えてしまう。

**技術の魅力**: BGPは本来「善意の経路広告」しか想定しておらず、悪用への耐性が薄いプロトコルだと言われる。RTBHはその性質を逆用し、標準化されたコミュニティ値1つという最小の合図だけで、自分のネットワークの外——他社が運用する巨大なルータ群——を勝手にファイアウォールとして徴用する。攻撃者のパケットは自分のネットワークに来る前に、赤の他人のインフラの中で消える。実装コストはコミュニティタグ1個で済み、Ciscoの解説資料はこれを「シンプルで効果的、ほぼ全てのルータがサポートする」とまで言い切っている。

**本来どこで使われてるか**: 実務のDDoS対策として広く現役。Equinixのような大手IXPやInternet2のような研究教育ネットワークは、加盟者が自分でトリガーできるRTBHサービスを標準機能として提供しており、`65535:666`を付けて広告するだけで数秒〜数分でネットワーク全体にブラックホールが伝播する。IETFはこのコミュニティ値の下2桁「666」を選ぶにあたり、運用者の間で語呂合わせ的に定着していた数字をそのまま公式仕様に格上げした。
出典: https://www.rfc-editor.org/rfc/rfc7999.html / https://www.cisco.com/c/dam/en_us/about/security/intelligence/blackhole.pdf / https://docs.equinix.com/internet-exchange/ix-rtbh-guide/

### <a id="card-3"></a>💡 画像アセットを1個も読み込まずに、背景画像の中でゲームが動く——CSS Paint APIの越権〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: CSS Houdiniの一部であるPaint API(`CSS.paintWorklet`)は、本来「チェッカー柄やグラデーションのような装飾的な背景・枠線パターンを、画像アセットを読み込まずJavaScriptの`paint(ctx, geometry, properties)`関数でその場で描く」ための仕組みだ。渡されるのはCanvas 2D風の描画コンテキストと要素サイズ、CSSカスタムプロパティの値だけで、DOM要素は一切増えず、メインスレッドとは別のワークレットスレッドで実行される。

**何ができる**: この「サイズと数値だけ受け取って絵を返す」という制約を極限まで押すと、`background-image: paint(myPainter)`という1行のCSSプロパティの裏側で、任意の計算をピクセルとして描き切れることに気づく。実際に公開されているデモには、専用の`<canvas>`もDOM上のマス目も置かず、Conwayのライフゲームの盤面遷移をPaint API内部だけで計算し続けて背景として描くものがある。セル1つひとつがDOM要素になっているわけではなく、"CSSの背景プロパティの値"という体裁を保ったまま、内部では毎フレーム状態遷移のシミュレーションが回っている。

**技術の魅力**: 普通、動く絵を出すには`<canvas>`や`<img>`のような「絵のための場所」をDOMに用意する。Paint APIの越権は、既存の何の変哲もない`<div>`の背景プロパティという最も地味な場所に、計算エンジンをまるごと押し込んでしまうところにある。CSSカスタムプロパティが変わるたびに再描画がトリガーされるので、アニメーションの駆動すらCSSトランジション任せにでき、「JSの`requestAnimationFrame`を1行も書かずに動く絵を出す」という倒錯が成立する。

**本来どこで使われてるか**: 本来の狙いは画像アセットの削減とレスポンシブ対応で、Chrome開発者ブログはbase64画像で配っていたチェッカーパターンをPaint APIの数行のJSに置き換える例を紹介している。解像度非依存(Retinaでも自動的に高精細)かつ動的なCSSカスタムプロパティ連動という利点から、装飾的なパターン生成・アイコン生成に実務で使われている一方、GoogleChromeLabsのサンプル集や個人のデモギャラリーでは、波紋・ブロブ・ライフゲームまで「背景画像の中の小さな計算機」として公開されている。
