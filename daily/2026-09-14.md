### <a id="card-1"></a>🆕 点を並べるだけでバネものこぎり波も出せる——CSS `linear()` というJS抜きの波形合成器 〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: CSS Easing Level 2で2023年に追加された`linear()`は、`0, 0.25 20%, 1`のように任意個の(進捗, 出力)点を並べるだけで、`transition-timing-function`や`animation-timing-function`に区分線形の任意カーブを指定できる関数。従来の`cubic-bezier()`は4点で決まる単一カーブしか表現できなかったが、`linear()`は点数に事実上の上限がなく、数百点でも受け付ける。ブラウザは各点の間を線形補間し、その結果をメインスレッドではなくコンポジタスレッドで直接再生する。

**何ができる**: 質量・剛性・減衰で決まるバネ方程式を数十〜数百点にサンプリングして`linear()`に流し込めば、`requestAnimationFrame`でフレームごとに計算するJSコードを1行も書かずに、本物のバネ運動をCSSだけで再生できる。区分線形近似は「点さえ密に取れば任意の連続関数に収束する」という数学的事実そのものなので、理屈上は矩形波・のこぎり波・フーリエ級数の部分和のような任意波形も、この1個のtiming-functionの中に埋め込める。JS 0行、メインスレッドの計算0回、オフラインの静的HTML1枚で"波形ジェネレータ"が完結する。

**技術の魅力**: 本来「デザイナーがバネの弾みを手書きしたい」というニーズのために追加された1個のCSS関数が、区分線形近似の数学的な万能性のおかげで、事実上の任意関数プロッタに化けている。しかもこの補間計算はJSのアニメーションループが本来背負うはずの負荷を、ブラウザ内蔵の合成スレッド側の補間器へまるごと"密輸"して肩代わりさせているという非対称性が効いている。

**本来どこで使われてるか**: Material Design 3の"expressive motion"のような、`cubic-bezier()`では作れない多段階のバウンド・オーバーシュートを持つスプリングアニメーションを、JSライブラリなしで再現するためにChrome 113・Firefox 112・Safari 17.4などに実装された。Jake ArchibaldとAdam Argyleが公開した`linear-easing-generator`は、実際のバネ物理方程式やSVGカーブのイージングを読み込み、これを`linear()`の点列へ自動変換するツールとして、プロダクトの"バネアニメーションをCSSへ焼き直す"実務を支えている。
出典: https://developer.chrome.com/docs/css-ui/css-linear-easing-function / https://github.com/jakearchibald/linear-easing-generator

### <a id="card-2"></a>🔍 ZIPの目次だけを盗み見る——HTTP Range Requestsが巨大アーカイブをダウンロードなしで開く 〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: ZIP形式はストリーミング向けの設計ではなく、ファイル一覧と各エントリの正確なオフセットを記した"Central Directory"をアーカイブの末尾に置く。一方HTTP/1.1のRange Requests(RFC 7233)は、サーバーさえ対応していれば`Range: bytes=`ヘッダでファイルの任意のバイト範囲だけを取得できる。この2つを組み合わせると、数GBのZIPでも末尾の数十〜数百バイトだけRangeで取ってEnd of Central Directoryを読み、そこからCentral Directory全体をもう一度Rangeで取れば、ファイルを1バイトもダウンロードせずに中身の一覧と各ファイルの位置が丸ごとわかる。

**何ができる**: 欲しいファイルが決まれば、そのオフセットだけをさらにRangeで取得すればよく、S3やCDN上に置かれた数GB〜数十GBのZIPアーカイブから必要な1ファイルだけをピンポイントで抜き出せる。`remotezip`や`cloudzip`といったOSSツールは実際にこの手順を自動化しており、Pythonパッケージ(wheel)のMETADATAだけをPyPIから読み出す用途では帯域を70%以上削減できたという報告もある。アーカイブを一度も丸ごと展開せずに"目次だけ立ち読み"できるのが要点。

**技術の魅力**: ZIP側もHTTP側も、互いを意識して設計されたわけではない。ZIPが「末尾に目次を置く」という保存フォーマットの都合、HTTPが「一部だけ寄越せ」という転送効率化の都合、この2つの無関係な設計判断が偶然噛み合った結果、"巨大ファイルの中身を覗き見る"という機能がどちらの仕様にも明示的には存在しないのに成立してしまう。仕様同士の意図しない合成でしか生まれない抜け道という点が効いている。

**本来どこで使われてるか**: Range Requestsは元来、動画のシーク再生やダウンロードの再開・並列分割取得のために使われる地味な機能で、ZIPのCentral Directoryも単にアーカイブツールが高速に目次を読むための内部設計にすぎない。この組み合わせは今、機械学習モデルや大規模データセットをまとめたZIPアーカイブから必要なファイルだけをサーバーレス関数で抜き出す、といったクラウドの転送コスト削減の実務でも使われている。
出典: https://rhardih.io/2021/04/listing-the-contents-of-a-remote-zip-archive-without-downloading-the-entire-file/ / https://github.com/gtsystem/python-remotezip

### <a id="card-3"></a>💡 「壊れないで」の一言が、書き込み速度でストレージの正体を漏らす——Storage Buckets APIのdurability副作用 〔move: サイドチャネル/副作用の利用 / 領域: データ/同期/ストレージ〕

**事実**: WICGで仕様策定中のStorage Buckets APIは、IndexedDBやCache Storageのデータを"バケツ"単位に分け、ブラウザのストレージ逼迫時にバケツごとの退避優先度を制御できるようにする機能。各バケツには`durability`という設定があり、"strict"を選ぶと書き込みは実際にストレージ媒体へフラッシュされるまで完了扱いにならず、"relaxed"を選ぶとOSレベルのバッファに乗った時点で完了扱いになる。前者は電源断でもデータを守れる代わりに遅く、後者は速いが電源断で消えうる。

**何ができる**: 同じ書き込みを"strict"と"relaxed"の両方で実行し、その所要時間の差を測るだけで、実際に物理ディスクへのフラッシュが起きたかどうかという副作用がタイミングに漏れ出す。これを使えば、ユーザーの環境がSSDかHDDか、ローカルディスクかネットワークドライブ越しかをJSだけで大まかに推定できる。ストレージ性能に応じてキャッシュ戦略やプリフェッチ量を自動調整する、といったチューニングへの転用が利く。

**技術の魅力**: "durability"は本来、データの安全性という信頼性の話でしかない。だが「安全に書き込む」という約束を守るために発生する同期フラッシュという副作用が、意図せずハードウェアの正体を暴く物差しになる。信頼性のためのオプションが、そのまま性能プロファイリングのプローブに横流しできるという非対称性が効いている。

**本来どこで使われてるか**: Storage Buckets APIはChrome 122以降で試験提供され、Gmail・Figma・Notionのようなブラウザ上で大量のオフラインデータを扱うアプリが、ストレージ逼迫時に「送信前の下書きは絶対に消せないが古い受信メールは消えてもよい」といった優先度をバケツ単位で宣言するために設計された。durabilityはその中でも、書きかけの下書きのような致命的なデータにはstrictを、再取得可能なキャッシュにはrelaxedを、と使い分けるためのオプションとして提供されている。
