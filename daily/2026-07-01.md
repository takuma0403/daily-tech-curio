### <a id="card-1"></a>🎙️ 加速度計とジャイロが"盗み聞く"——マイク権限なしで音声を拾うGyrophone 〔move: センサーの転用 / 領域: 無線/組み込み/ハードウェア / レンズ: 物理世界とつながる〕

**事実**: スマートフォンのMEMSジャイロスコープは角速度を測るための部品で、サンプリングレートは最大でも200Hz程度しかない。ところがこの共振構造は、近くで発生した音圧(特に200Hz以下の低周波の発話成分)による筐体の微細な振動にも反応し、エイリアシングを起こしてその情報を拾ってしまう。2014年、StanfordのYan Michalevsky、Dan Boneh、Gabi NakiblyはUSENIX Securityで"Gyrophone"を発表し、ジャイロの生データだけから話者情報や発話内容の一部を復元できることを示した。決定的なのは、iOSもAndroidもマイクと違ってジャイロへのアクセスに特別な権限確認を要求してこなかった点だ。

**何ができる**: マイク権限を持たないアプリやブラウザ上のJavaScriptでも、モーションセンサーのAPIでジャイロの角速度データを読み取るだけで周囲の音の低周波成分を再構成できる。研究では、外部スピーカーから再生した音源に対してTIDigitsデータセット(0〜9の読み上げ)の数字認識で最大65%程度の精度を達成しており、"マイクは使っていない"という建前を保ったまま音を拾う経路が実際に機能することを実証した。

**技術の魅力**: 「回転を測る部品」と「音を測る部品」はOSの権限モデル上まったく別物として扱われてきたが、MEMSの共振構造という物理レベルでは両者の境界はそもそも存在しない。設計者が「モーションセンサーだから低リスク」と切り分けた前提そのものが、音という別の物理量の抜け穴になる。デジタルな権限の線引きが、アナログな物理現象の前では意味を失うという非対称性が核心にある。

**本来どこで使われてるか**: ジャイロスコープ本来の用途は画面の自動回転、歩数計、ゲームのモーション操作、手ぶれ補正など。この発表を受けてAppleとGoogleはモーションセンサーのサンプリングレート制限やアクセス許可プロンプトの強化を進めた。Gyrophoneはその後、加速度計でスマホスピーカーの振動から音声を拾う"Spearphone"など一連のモーションセンサー音響サイドチャネル研究の起点になった。
出典: https://www.usenix.org/conference/usenixsecurity14/technical-sessions/presentation/michalevsky / https://crypto.stanford.edu/gyrophone/

### <a id="card-2"></a>🧩 「回転する多項式のズレ」だけで同じバイト列を見つける——Rabin指紋が生んだ重複排除の系譜 〔move: レガシー/廃止予定機能の蘇生 / 領域: データ/同期/ストレージ〕

**事実**: 1981年にMichael RabinがHarvardで発表した「ランダム多項式によるフィンガープリンティング」は、大きなバイト列の中の任意のn-byte部分文字列を高速に指紋化する数論的な手法だった。2001年、MITのAthicha Muthitacharoen・Benjie ChenとNYUのDavid MazièresはこれをLBFS(Low-Bandwidth File System)というほぼ忘れられた研究用ネットワークファイルシステムに実装し、ファイルを固定サイズではなく「内容が変わった場所」を境界として分割するContent-Defined Chunking(CDC)を確立した。LBFS自体は実運用に広まらないまま終わったが、この境界決定アルゴリズムだけが生き延びた。

**何ができる**: CDCは、ファイルの先頭に1バイト挿入しただけで固定長分割なら全チャンクがズレる問題を解決する。ローリングハッシュ(Rabin指紋やBuzhashなど)がスライディングウィンドウ上でバイト列の中身に応じて境界を決めるため、挿入・削除があっても変更箇所の前後以外は境界が動かず、同一内容のチャンクは別ファイル・別バージョン間でも同じハッシュとして再検出される。これによりrsyncは差分だけを転送し、バックアップツールのrestic(Rabin指紋、64バイト窓)やBorgBackup(Buzhash、可変4095バイト窓)は同一内容のブロックを一度しか保存しない重複排除を実現している。

**技術の魅力**: 「同じデータかどうか」を判定するのに、ファイル全体を比較する必要も固定の境目を決め打ちする必要もなく、窓を1バイトずつスライドさせながら差分計算だけで更新できるローリングハッシュという数学的トリックだけで、内容そのものが境界を教えてくれる。しかもLBFSという実運用には失敗した2000年代初頭の学術プロジェクトのアイデアだけが、形を変えて今日のクラウドバックアップの標準技術として生き残っている――プロダクトは死んでもアルゴリズムは死ななかった、という転生が効いている。

**本来どこで使われてるか**: rsyncは1996年にAndrew Tridgellが考案したAdler-32ベースのローリングチェックサムで差分転送を実現し、これがCDCの直接の先駆けとなった。LBFSの論文はACM SOSP 2001で発表され、帯域を最大90%規模削減できると報告している。現在はrestic・BorgBackup・Syncthingから重複排除ストレージアプライアンスまで、ネットワーク帯域を絞る目的で生まれたこの数論トリックが、ローカルファースト同期やクラウドバックアップの重複排除エンジンとして広く採用されている。
出典: https://dl.acm.org/doi/10.1145/502034.502052 / https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html

### <a id="card-3"></a>📼 YouTubeの"動画圧縮"を無限のファイルストレージに変える 〔move: 仕様の目的外利用 / 領域: フロントエンド/グラフィックス〕

**事実**: YouTubeはアップロード数・総容量に事実上上限を設けておらず、動画である限り無料で無制限に保存・配信(Googleの世界規模CDN込み)できる。2023年、開発者DvorakDwarfが公開したRust製ツール"Infinite-Storage-Glitch"は、この「動画は無制限」という建前を逆手に取り、任意のファイルを白黒2値のピクセルブロックの並びとして映像フレームにエンコードし、それをただの動画としてYouTubeへアップロードする。複数の実ピクセルをまとめて1つの粗いブロックにすることで、YouTube側のH.264/VP9再エンコードを生き延びるだけの冗長性を持たせている。

**何ができる**: 元ファイルより動画サイズはおよそ4倍に膨らむが、その代わりYouTubeの無制限ストレージとCDNをタダで借りられる。動画の一部にはタイミング・メタデータ・誤り訂正用のビットも仕込まれており、再ダウンロード後に多少の圧縮劣化があってもデータの破損を検知・復元できる。限定公開動画としてアップロードしておけば、実質「個人用の巨大な無料クラウドストレージ」がブラウザ・動画エンコード技術の組み合わせだけで完成する。

**技術の魅力**: 動画コーデックは「人間の目に自然な絵を保つ」ために設計された非可逆圧縮であり、本来は"データを守る"どころか"どんどん劣化させる"技術だ。それを逆用し、コーデックが壊しにくい形(単純な白黒の大きなブロック)にあらかじめデータを変換しておくことで、非可逆圧縮の上に可逆に近い転送路を作り上げてしまう。「動画ホスティングという善意のインフラ」が「ファイルホスティング」に化けるのは、プラットフォーム側の規約とエンコーダが"中身が何か"ではなく"動画として再生できるか"しか見ていない設計の隙を突いた目的外利用だ。

**本来どこで使われてるか**: YouTubeの巨大なアップロード帯域・ストレージ・トランスコーディングパイプラインは、本来は一般ユーザーの動画共有と広告収益化のために作られたインフラだ。Infinite-Storage-GlitchはHacker NewsやHackadayで話題になったのち作者自身の手で2023年3月にリポジトリがアーカイブされたが、そのアイデアは"qStore"をはじめ複数のフォークに引き継がれている。同種の「動画=無料ストレージ」ハックはQRコード動画やbase64動画埋め込みという形で、それ以前から個人ブロガーの間でも繰り返し再発明されてきた。
