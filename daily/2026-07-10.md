### <a id="card-1"></a>🩹 「元に戻す」のために作られた機能が、DBの差分同期プロトコルになる——SQLiteセッション拡張 〔move: 仕様の目的外利用 / 領域: データ/同期/ストレージ / レンズ: 既存サービスの1機能だけを置換〕

**事実**: SQLite本体には「セッション拡張」(`sqlite3session`)という地味な追加モジュールがある。テーブルへのINSERT/UPDATE/DELETEを裏で記録し続け、それを"changeset"または"patchset"という1つのバイナリブロブにまとめて吐き出せる。changesetは変更前後の値を両方持つので逆再生(=アンドゥ)ができ、patchsetは適用に必要な最小限の値だけを持つ軽量版。もともとの用途は名前の通り地味で、アプリ内の「元に戻す」ボタンやローカルな変更履歴を録るためのものだった。

**何ができる**: このバイナリブロブは、変更のあった行だけを表す"パッチ"として、そのまま別のSQLiteファイルに`sqlite3changeset_apply()`で当てられる。DB全体を毎回コピーしたり、専用のCRDTライブラリを持ち込んだりしなくても、オフラインで編集されたSQLiteファイル同士を「差分だけ送って当てる」形で同期できる。同時編集で競合したら、コンフリクトハンドラのコールバックに「相手を勝たせる/自分を勝たせる/手動マージ」を返させるだけでいい。ローカルファーストのメモアプリなら、"クラウド同期"という1機能だけを、サーバー側の複雑な業務ロジックなしに、変更ログの受け渡しだけで代替できてしまう。

**技術の魅力**: 「アンドゥのために変更を記録する」という地味な仕組みが、そのまま「2つのレプリカ間で差分だけをやり取りする」プロトコルの土台になっている。凝った衝突解決理論を新しく持ち込まなくても、SQLiteという既存のファイル形式の中に、パッチ形式の同期プリミティブがずっと標準機能として同梱されていた——という気づかれにくさが効いている。

**本来どこで使われてるか**: SQLite公式ドキュメントは、この拡張の目的を「複数のデータベースのコピーを同期させること」と明記しており、Unixの`patch`コマンドやGit/Mercurialのマージ機能に相当する用途と自ら比較している。想定シナリオは、オフラインファーストのアプリ・複数デバイス間同期・データベースレプリケーションで、変更全体ではなく差分だけを記録・送信・適用する場面。
出典: https://sqlite.org/sessionintro.html / https://www.sqlite.org/session/sqlite3session_changeset.html

### <a id="card-2"></a>📌 ツールチップの位置指定APIが、DOM上どこにでも矢印を引く土台になる——CSS Anchor Positioning 〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: CSS Anchor Positioningは、ある要素を「アンカー」に指定し(`anchor-name`)、別の要素をそのアンカーを基準に配置する(`position-anchor`と`anchor()`関数)仕組み。2024年にChrome 125で実装され、2026年にはFirefox・SafariもBaseline入りした比較的新しい仕様で、本来はツールチップ・ポップオーバー・セレクトボックスのドロップダウンなど、「起点となる要素の近くに浮かせて出す」UIのために設計された。重要なのは、アンカーと配置対象の間にDOM上の親子関係が一切要求されない点で、ページのどこにあるどの要素同士でも、名前さえ紐付ければ位置関係を作れる。

**何ができる**: この「親子関係なしに位置を紐付ける」性質を使うと、これまでJSで座標をフレームごとに計算するライブラリが必要だった「離れた2要素を線でつなぐ図解」——組織図、脚注と本文の相互参照、グラフの動的ラベル——がCSSの`anchor()`だけで成立する。スクロールやリサイズで要素が動いても、ブラウザ側が自動で再配置してくれるので、位置を監視するJSの`ResizeObserver`地獄からも解放される。

**技術の魅力**: 「ツールチップを浮かせる」という地味な一機能のために作られた紐付けの仕組みが、実は"任意の要素Aから任意の要素Bへの参照"という、本来もっと汎用的な問題(結線図・相互参照)の解として効いてしまうところが面白い。DOM構造(親子関係)と視覚的な位置関係をあえて分離した設計判断が、結果的に「JSゼロで結線図が引ける」という、誰も名指しでは意図していなかった副産物を生んでいる。

**本来どこで使われてるか**: Chrome for Developersのブログが挙げる想定用途は、ツールチップ・ポップオーバー・カスタムセレクトのドロップダウン・サイドノートなど、いずれも「近くに浮かせるUI」の域を出ない。ただし同じブログや実装者コミュニティは、グラフの動的ラベル付けやコネクタ線、脚注の視覚的な相互参照といった応用例もすでに紹介しており、"アンカー"という名前が示す通り、本来の主戦場はあくまで小さなオーバーレイUIの位置決めにある。
出典: https://developer.chrome.com/docs/css-ui/anchor-positioning-api / https://developer.chrome.com/blog/tether-elements-to-each-other-with-css-anchor-positioning

### <a id="card-3"></a>🪪 NATを越えても消えない接続の名札が、追跡トークンになりうる——QUICコネクションID 〔move: サイドチャネル/副作用の利用 / 領域: ネットワーク/プロトコル〕

**事実**: QUIC(RFC 9000)のコネクションIDは、TCPが送信元/宛先IP・ポートの4-tupleだけでコネクションを識別するのと違い、各エンドポイントが自由に選べる不透明な(opaque)バイト列——最大20バイト——をコネクションの識別子として使う。狙いは、WiFiからモバイル回線への切り替えのようにIPアドレスが変わる「コネクションマイグレーション」を、再接続なしで乗り切ること。中身は文字通り「相手が好きな値を入れてよい」空欄で、ルーティング目的以外の意味を持たせてはいけないという制約以外、仕様上ほぼ白紙になっている。

**何ができる**: コネクションIDの中身はサーバー側が自由に生成できるので、ここに実質的な識別子を(ルーティング用の値を装って)埋め込んでおけば、Cookieなしでもクライアントをネットワークを跨いで追い続けられる。WiFiからテザリングに切り替わろうが、キャリアがIPを再割り当てしようが、コネクションが生きている(あるいは0-RTTで再開される)限り、サーバーは同じ識別子の系譜を追える。アプリ層のCookieを消しても、トランスポート層のこの"名札"には触れない。

**技術の魅力**: RFC自身が「コネクションIDだけから、同一コネクションだと第三者に相関されてはならない」と念を押しているのは、あくまで経路上の"観測者"に対する話であって、そのコネクションIDを発行した張本人であるサーバーには当てはまらない、という非対称性が効いている。プライバシー配慮のために「値を推測されないように」と作られた不透明フィールドが、発行者から見れば逆に"匿名の器に許可された任意の情報"という、追跡にちょうどよい形になってしまっている。

**本来どこで使われてるか**: RFC 9000の第5.1節・第9節が定義する本来の用途は、NATの再割り当てやWiFi→セルラーの切り替えでIPが変わっても、ロードバランサやサーバーが「同じコネクションの続き」だと判別してパケットを正しいエンドポイントに届けるためのルーティング機構。仕様が要求するのは「経路上の観測者に相関されない値であること」までで、発行者自身による情報の埋め込みまでは禁じておらず、Chromeなど一部の実装がコネクションIDを頻繁にローテーションするのも、この抜け穴を意識した防御側の対策として知られている。
出典: https://www.rfc-editor.org/rfc/rfc9000.html
