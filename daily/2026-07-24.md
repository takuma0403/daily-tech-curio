### <a id="card-1"></a>🆕 「同じ一瞬」を複数プロセスに配って回る——PostgreSQLの同期スナップショット 〔move: 仕様の目的外利用 / 領域: データ/同期/ストレージ〕

**事実**: PostgreSQLは各トランザクションがMVCCで「自分が始まった瞬間のDBの見え方（スナップショット）」を持つ。`pg_export_snapshot()` を呼ぶとその見え方を文字列IDとしてエクスポートでき、別の接続が `SET TRANSACTION SNAPSHOT '...'` でそれをインポートすれば、別コネクション・別プロセスであっても寸分違わぬ同じ一瞬のDBを見られる。PostgreSQL 9.2で追加された地味な機能で、素性は「`pg_dump -j` の並列ダンプを一貫させるため」という一点にほぼ限定されており、それ以外の使い道はドキュメント上でもほとんど語られない。

**何ができる**: 複数の独立ワーカープロセスを、ロックを一切かけずに「まったく同じ瞬間のスナップショット」から同時に読み始めさせられる。集計バッチを10並列に割っても全員が同じ時点のデータを見るので突き合わせがズレない、巨大テーブルをオフセットで分割並列コピーしても行の二重取得・欠落が起きない、微妙にタイミングのずれる複数サービスのキャッシュウォームアップを「同じ瞬間」基準で揃えられる。エクスポート元のトランザクションが生きている間だけ有効という制約はあるが、その間は何個でもインポートできる。

**技術の魅力**: 普通、複数プロセス間で「同じ時点のデータ」を保証しようとするとロックやレプリケーションスロットなど重い仕組みに頼る。ところがPostgreSQLはMVCCが元々内部に持っていた「スナップショットオブジェクト」に、ただIDを振って外に出しただけ。新しい仕組みを組んだのではなく、たまたま存在した内部データ構造をトランザクション境界の外へ受け渡せるようにした軽さが効いている。

**本来どこで使われてるか**: `pg_dump --jobs` の並列バックアップと、Greenplum由来の `gpbackup` など、まさに「並列ダンプの一貫性」のためだけに使われている。PostgreSQL 9.2でプライマリに、10でスタンバイにも対応が広がったが、公式ドキュメントでもこの用途以外への言及はほとんどない。
出典: https://www.postgresql.org/docs/current/app-pgdump.html / https://pgpedia.info/p/pg_export_snapshot.html

### <a id="card-2"></a>🔍 電話網の"つなぎ役"だったプロトコルが、ブラウザのDataChannelの土台に潜んでいる——SCTP 〔move: レガシー/廃止予定機能の蘇生 / 領域: ネットワーク/プロトコル〕

**事実**: SCTP（Stream Control Transmission Protocol）は2000年代初頭、電話網のシグナリング（SS7）をIPネットワークへ移すSIGTRANの一部として設計されたトランスポート層プロトコル。TCPともUDPとも違う独自設計で、1本の「アソシエーション」の中に複数の独立した論理ストリームを多重化できる機能と、1つのアソシエーションに複数のIPアドレスを結び付けられるマルチホーミングという、当時の電話網の要求から生まれた機能を持つ。一般のアプリ開発者にはほぼ縁がないまま存在してきた。

**何ができる**: WebRTCのRTCDataChannelは、実はこのSCTPをDTLSの上でそのまま使っている。複数ストリームのおかげで、1つのメッセージが詰まっても他のストリームの配信はブロックされない（TCPが抱えるhead-of-line blocking問題の回避）。さらに本来の目玉機能であるマルチホーミングは、ブラウザの外で自前のSCTP実装（usrsctpなど）を使えば生かせる。1つのアソシエーションに端末のWiFiとセルラー、2つのローカルIPを結び付けておけば、片方の経路が落ちてもアプリ側は再接続コードを一切書かずに通信が生き続ける。

**技術の魅力**: TCPを改良するのではなく、電話網というまったく畑違いの世界の要求からゼロ設計されたトランスポート層が、20年後にブラウザのリアルタイム通信をこっそり支えているという回り道が効いている。しかもブラウザは多重化（ストリーム）だけをつまみ食いし、看板機能だったマルチホーミングは使っていない——枯れた実装が「部分的に」再利用されるという、消費のされ方自体が面白い。

**本来どこで使われてるか**: SIGTRANの本来の用途である電話網シグナリング（SS7/Diameterのトランスポート）に、SCTPは今も使われている。WebRTC文脈ではRFC 8831がSCTPをDataChannelの標準トランスポートに指定しており、ビデオ会議アプリの画面共有やファイル転送機能は、気づかれないままこの上で動いている。
出典: https://www.rfc-editor.org/rfc/rfc8831 / https://webrtcforthecurious.com/docs/07-data-communication/

### <a id="card-3"></a>💡 CPUの"電気代メーター"を覗くだけで、暗号鍵が漏れる——RAPLという合法な覗き穴 〔move: サイドチャネル/副作用の利用 / 領域: 無線・組み込み・ハードウェア〕

**事実**: Intel CPUのRAPL（Running Average Power Limit）は、サーバーやノートPCの電力管理・発熱対策のために2011年から搭載されているインターフェースで、CPUパッケージやDRAMがいま何ワット消費しているかをソフトウェアから読める。本来は電力上限を設定してスロットリングを制御するための地味な管理用レジスタだが、長らく一般ユーザー権限のプロセスからでも `/sys` や専用命令経由で読めてしまっていた。

**何ができる**: 2020年のPLATYPUS攻撃は、この電力値の細かな揺れを暗号処理の最中に統計的に観測するだけで、実行中の命令やオペランドのビット構成（ハミング重み）を推定できることを示した。専用の計測器もオシロスコープも要らず、ソフトウェアだけでmbedTLSのRSA秘密鍵やSGXエンクレーブ内のAES-NI鍵を抜き出し、KASLRのアドレス空間配置まで破れる。関連するHertzbleedは、電力そのものではなくRAPLが引き起こす周波数スロットリングのタイミング差を遠隔から観測するだけで同種の鍵漏洩を成立させた。

**技術の魅力**: キャッシュタイミング攻撃などの"サイドチャネル"は普通、CPU内部の微細な挙動を精密に測る難しさがある。RAPLの怖さは、OSがわざわざ親切に公開している「消費電力」という一段抽象化された数値を、ただ読むだけで同じことができてしまう点。攻撃者が触れているのはメモリでもキャッシュでもなく、電気代メーターの針の揺れだけという非対称性が効いている——デジタルな秘密が、そのまま物理的な電力の揺らぎとして外に漏れ出す。

**本来どこで使われてるか**: サーバーの電力予算管理やノートPCの発熱制御、クラウド事業者のデータセンター電力最適化にRAPLは日常的に使われている。IntelはPLATYPUS公表後、RAPLの読み取り権限をroot限定に絞るファームウェア・OSパッチ（CVE-2020-8694/8695）を出し、Linuxカーネルも同様にアクセス制限を強化した。
出典: https://cispa.de/en/platypus-vulnerabilities-discovered / https://www.hertzbleed.com/hertzbleed.pdf
