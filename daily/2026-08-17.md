### <a id="card-1"></a>🆕 描いて、また描くと消える——Canvasの"xor"合成モードで論理回路を組む 〔move: レガシー/廃止予定機能の蘇生 / 領域: フロントエンド/グラフィックス〕

**事実**: Canvas 2Dの`globalCompositeOperation`には`multiply`や`screen`のような見慣れた合成モードに混じって、`xor`という異質な値がある。他のモードが色をブレンドするのに対し、`xor`は文字通りアルファのビット単位XORで、2つの不透明な図形が重なった部分はブレンドされた色ではなく透明に戻る。これはWindows GDIの`R2_XORPEN`やXerox Alto以来のGUIが使ってきた「XOR描画」の直系の子孫だ。バックバッファもダブルバッファリングも存在しなかった時代、同じ図形を同じ場所にもう一度描くだけで元の背景がそのまま復元される(A XOR A = 0)という性質を利用し、画面全体を再描画せずにドラッグ中のラバーバンド選択矩形やマウスカーソルを消せる唯一の実用的な方法だった。

**何ができる**: この性質を使うと、JSの数値演算もシェーダも使わずに画像の重ね描きだけでブール演算が組める。図形Aを描き、続けて`globalCompositeOperation = 'xor'`で図形Bを描けば、重なった領域だけが透明になる=A XOR Bがそのままキャンバス上に描かれる。`source-in`(AND相当)や`source-over`(OR相当)と組み合わせれば任意の組み合わせ論理を積み木のように構築でき、最後に`getImageData()`を1回呼ぶだけで答えのビットが読み取れる。実用的には、2枚の画像を`xor`(または`difference`)で重ねて透明でないピクセルだけを拾えば、ピクセル単位の比較ループを1行も書かずにGPUアクセラレーションされた画像差分検出が手に入る。

**技術の魅力**: `xor`が面白いのは、それが「論理回路のために追加された機能」では全くない点だ。1970〜80年代のハードウェア制約(フレームバッファを保持する余裕がない)が生んだ自己相殺トリックが、40年以上経った今もモダンなJSのenumの中に一語だけ生き残っていて、しかも`source-over`しか使ったことのない開発者のほとんどがその存在に気づいていない。GDIやXlibの互換性維持のためだけに保存された遺物が、たまたまブール完全という性質を持っていたという偶然の非対称性が効いている。

**本来どこで使われてるか**: XOR描画モード(Win32の`R2_XORPEN`、X11のGCの`GXxor`など)は、ダブルバッファリングが一般化する以前のGUIで、ドラッグ中の選択矩形やキャレット・カーソルのオーバーレイを「描いて消す」ためだけに標準的に使われていた技法で、Microsoft自身が互換性維持のためR2_XORPENを今もGDIに残している。Canvas 2Dの`xor`合成モードもこの系譜のまま標準化されたが、WHATWGの議論ではOperaが実装を一度間違え修正した記録が残るなど、実装者の関心が薄い隅の機能であることがうかがえる。
出典: https://www.interact-sw.co.uk/graphics/xorconsideredharmful/ / https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/Graphics/Gdi/constant.R2_XORPEN.html / https://lists.whatwg.org/pipermail/whatwg-whatwg.org/2007-March/010608.html

### <a id="card-2"></a>🔍 証明書は誰の署名も要らない——WebTransportがCAを飛ばしてデバイスと直結する抜け道 〔move: 制約の極端化 / 領域: ネットワーク/プロトコル〕

**事実**: QUIC上の新しい双方向通信API・WebTransportは通常、HTTPS同様に公的な認証局(CA)が署名した証明書を持つサーバーにしか接続できない。ところが接続オプションに`serverCertificateHashes`という項目があり、これを使うと相手が自己署名証明書しか持っていなくても、その証明書のSHA-256ハッシュ値さえ事前に知っていれば接続を確立できる。ただしW3C仕様はこの抜け道を無制限には開けておらず、対象の証明書はECDSA(P-256)鍵限定でRSA鍵は拒否、かつ有効期間は最長14日間までという厳しい制約を課している。

**何ができる**: ブラウザのタブから、DNSにも登録されておらずCAの署名も持たない同一LAN上のデバイス(Raspberry Piや自作のIoT機器、他のP2Pノードなど)に対して、証明書のハッシュ値さえBluetoothのペアリングコードのように何らかの方法(QRコードや手入力)で渡せば、暗号化・認証済みのQUIC接続をサーバー仲介なしに直結できる。デバイス側は起動のたびに新しい自己署名証明書を発行するだけでよく、CA登録もDNS登録も一切不要になる。ブラウザは渡されたハッシュと一致する証明書以外は問答無用で拒否するため、CAという第三者を信頼の起点にしない、SSHの`known_hosts`とほぼ同じ信頼モデルがブラウザの中に持ち込まれる。

**技術の魅力**: 面白いのは、この仕組みが証明書失効の仕組み(CRLやOCSP)を一切実装していないことだ。その代わりに「鍵の種類をECDSAだけに絞り、有効期間を14日という極端な短さに制限する」という、失効インフラそのものを丸ごと不要にする力技で安全性を担保している。失効させたければ、ただ新しい証明書に生まれ変わるのを14日待てばいい——複雑な信頼基盤を作る代わりに、寿命を極端に縮めることで問題自体を消し去る発想が効いている。

**本来どこで使われてるか**: この仕組みはまさに、CA署名証明書を持てないノード同士が直接つながる必要のある分散ネットワーク向けに設計された。長年ブラウザのWebSocketはCA署名証明書を要求するため普及できなかったlibp2p(IPFSを支えるP2Pネットワークスタック)は、このserverCertificateHashesを使うWebTransportトランスポートによって、ブラウザ上のノードが他のlibp2pノードへCAなし・DNSなしで直結できるようになった。libp2pの実装は起動時に14日有効の証明書を2つ(現在分と次期分)重ねて生成し、切れ目なくローテーションし続ける運用になっている。
出典: https://github.com/libp2p/specs/blob/master/webtransport/README.md / https://github.com/w3c/webtransport/pull/375 / https://github.com/ipfs/in-web-browsers/issues/190

### <a id="card-3"></a>💡 モデルを1つもダウンロードせずに顔を検出する——OSの"目"を借りるShape Detection API 〔move: 仕様の目的外利用 / 領域: AI/メディア処理〕

**事実**: `FaceDetector`・`BarcodeDetector`・`TextDetector`という3つのクラスからなるShape Detection APIは、画像を渡して`detect()`を呼ぶだけで顔の座標やバーコードの中身、画像中の文字が返ってくるJS APIだ。奇妙なのは、ブラウザ自身は推論用のニューラルネットを一切バンドルしていないこと。実装はただの取り次ぎ役で、画像をそのままOSのネイティブなビジョンエンジン——Androidなら端末のカメラアプリやGoogleレンズを裏で支えているGoogle Play ServicesのVision(ML Kit)、macOS/iOS系のWebKitならApple純正のVisionフレームワーク——に丸投げし、結果だけを受け取ってJSに返している。

**何ができる**: TensorFlow.jsもONNX Runtime Webも一切使わず、ネットワーク通信ゼロ・モデルダウンロード0MBの完全な静的HTMLファイルの中で`new FaceDetector().detect(img)`を呼ぶだけで、スマホの標準カメラアプリが内部で使っているのと全く同じ、OSがプライベートに保持しているニューラルネットによる顔検出・バーコード読み取り・OCRが、端末のハードウェアアクセラレーションつきでオフラインのまま手に入る。画像へのアクセス以上の特別な許可ダイアログも出ない、実質ゼロフットプリントのコンピュータビジョン導入経路になる。

**技術の魅力**: WebNNやTF.jsなど他のブラウザ内MLの話は「モデルをどうブラウザに運び込むか」を主題にしているが、Shape Detection APIはその逆で、Web標準の小さな窓口を通してOSが囲い込んでいる非公開のニューラルネットをそのまま借りてくる。Google・Appleが自社の膨大なデータで訓練し、外部に公開もオープンソース化もしていないモデルの推論結果を、たった数行のJSでウェブページという本来サンドボックス化されたはずの環境から直接引き出せてしまう非対称性が効いている。

**本来どこで使われてるか**: 元々はeBayのようなECサイトがチェックアウトやチケット読み取りでバーコード・QRコードを重いJSライブラリなしにスキャンできるようにする、地味な実用目的で提案された仕様だ。現在`BarcodeDetector`はAndroidおよびAndroid WebView上で、システムのカメラのバーコード読み取り機能と同じGoogle Play Services Visionライブラリを裏で使う形で出荷されている一方、`FaceDetector`と`TextDetector`はより限定的でFirefoxや非Chromium系Safariでは未対応のため、サイト側はJSポリフィルへのフォールバックを今も用意する必要がある。
出典: https://github.com/WICG/shape-detection-api / https://wicg.github.io/shape-detection-api/ / https://developer.mozilla.org/en-US/docs/Web/API/Barcode_Detection_API
