### <a id="card-1"></a>🆕 TLS 1.3が自ら封印した"あとから認証"の裏口——Post-Handshake Authenticationという片肺の機能 〔move: 仕様の目的外利用 / 領域: セキュリティ/認証〕

**事実**: TLS 1.3は長年脆弱性の温床だったrenegotiationを廃止し、代わりに"post-handshake authentication"という機能（RFC 8446 §4.6.2）を新設した。これはサーバーが接続確立後の任意のタイミングで新たにCertificateRequestを送り、クライアント証明書だけを"あとから"要求できる仕組み。日常ではほぼ意識されないが、Apache mod_sslは`<Location>`ディレクティブ単位で`SSLVerifyClient require`を書くと、同じTLS1.3コネクションの中でこの機能を暗黙に使い、特定のパスにアクセスされた瞬間だけ裏側でクライアント証明書を要求する。

**何ができる**: 常時mTLSを強制せず普段は無認証で応答しつつ、`/admin`のような特定パスへのリクエストが来た瞬間だけ、新しいTCP接続もリダイレクトも挟まずにその場でクライアント証明書を要求する"サイレントな段階的昇格認証"が組める。ブラウザ側の実装はほぼ未対応・無効化されているため使い道はサービス間通信やCLIクライアントに限られるが、1本の長寿命コネクションの中で権限レベルを動的に切り替えられるのは他の認証方式にない芸当。

**技術の魅力**: 面白いのは、この機能がHTTP/2では明示的に禁止されていること（RFC 8740）。複数リクエストが1本の接続を多重化するh2では「どのリクエストが証明書要求を引き起こしたか」が曖昧になるため、IETFはh2だけこの機能を殺した。つまりpost-handshake authenticationは、モダンなプロトコル（h2/h3）では使えず、あえてHTTP/1.1に留まることでしか機能しない——進化の枝分かれで片方にだけ生き残った機能になっている。

**本来どこで使われてるか**: 元々はTLS 1.2の再ネゴシエーション（過去に複数の深刻な脆弱性を抱えていた）を安全に置き換える目的でTLS 1.3に導入された。Apache httpdのmod_sslはディレクトリ単位のクライアント証明書要求の実装にこれを使っており、公式ドキュメントにも明記されている。一方でOpenSSLやブラウザ各社（Chrome/Firefoxなど）は長年互換性問題を抱え、対応は限定的なままである。
出典: https://datatracker.ietf.org/doc/html/rfc8446#section-4.6.2 / https://www.rfc-editor.org/rfc/rfc8740.html / https://httpd.apache.org/docs/current/mod/mod_ssl.html

### <a id="card-2"></a>🔍 `<img>`タグ1本が生きたビデオになる——multipart/x-mixed-replaceという1995年の亡霊 〔move: レガシー/廃止予定機能の蘇生 / 領域: フロントエンド/グラフィックス〕

**事実**: 1995年、JavaScriptが世に出るより1年早く、Netscape 1.1は"Server Push"という機能を実装した。HTTPレスポンスのContent-Typeを`multipart/x-mixed-replace; boundary=...`にし、1本のコネクションの中に複数のパートを区切りながら延々と流し込むと、ブラウザは新しいパートが届くたびに直前の内容を"置き換えて"表示する。標準化されずNetscape独自拡張のまま今日に至るが、Firefox・Safari・Operaは今も実装を残している。

**何ができる**: サーバー側で「JPEGフレームを境界文字列付きで書き込み続けるだけ」のスクリプトを1本書けば、クライアント側はHTMLに`<img src="/stream">`と書くだけで生きた映像が流れる。WebSocketのハンドシェイクもService WorkerもCanvasの再描画ループも要らず、JS 0行で完結する。fetch()でReadableStreamとして読めば、画像に限らず任意のJSON断片を境界区切りで流し込む「WS不要のサーバープッシュ」としても転用でき、WebSocketをブロックする一部の企業プロキシやロードバランサをすり抜けやすいという副次効果もある。

**技術の魅力**: WebSocketやServer-Sent Eventsという"正規の"サーバープッシュ手段が確立するおよそ15年も前に、たった1つのMIMEタイプの約束事だけで同じことを実現していた点が効いている。しかも標準化されずベンダー拡張のまま忘れられたのに、実装は消えるどころか今なお主要ブラウザに残り続け、世界中の監視カメラ・産業用IPカメラのほぼすべてがこの"忘れられた1995年の機能"に無自覚に依存している。

**本来どこで使われてるか**: NetscapeがJavaScriptに先駆けて用意した「動的文書」実験機能の一つ。今日では主にIPカメラのMJPEGストリーミングで生き残っており、Axis CommunicationsのVAPIX APIをはじめ、Panasonic・Linksysなど多くの監視カメラベンダーが公式にこのContent-Typeでライブ映像を配信している。
出典: http://marc.merlins.org/htmlearn/netscape/pushpull.html / https://developer.axis.com/vapix/network-video/video-streaming/

### <a id="card-3"></a>💡 MP3が"聞こえない"と判定した帯域に、AIだけへの命令を仕込む——心理音響マスキングモデルの密輸 〔move: 異分野の手法移植 / 領域: AI/メディア処理〕

**事実**: MP3やAACのようなロッシー音声コーデックは、ファイルを小さくするために「人間の耳が実際には知覚できない周波数成分」を精密に計算して削っている。これを支えるのが心理音響マスキングモデルで、ある周波数・音量の音が鳴っているとき、その近傍のどの周波数帯がどれだけの音量まで"聞こえなくなる"かをISO/IEC 11172-3（MPEG-1 Layer III）などの仕様が数式・閾値テーブルとして定義している。

**何ができる**: このマスキング閾値を「削ってよい音」の計算ではなく「足してよい音」の計算に転用すると、人間の耳には元の曲そのままにしか聞こえない音声ファイルの中に、音声認識モデル（ASR）だけが拾える別の"命令"を仕込める。マスキング閾値ぎりぎりの振幅で敵対的摂動を注入すれば、スピーカーから普通の曲を流しているだけなのに、近くのスマートスピーカーが隠された命令を実行してしまう——人間には検知不能な形での音声コマンド密輸が成立する。

**技術の魅力**: 攻撃者が新しい"隠す技術"を発明したのではなく、コーデック開発者が「人間の聴覚の弱点」をすでに精密に数式化して仕様書に公開していたという非対称性が効いている。圧縮のために聴覚の穴を塞ごうとした努力の副産物が、そのままAIモデルと人間の知覚のズレを突く攻撃者向けの"設計図"として横流しできてしまう。

**本来どこで使われてるか**: 本来はMP3/AAC/Opusなど非可逆音声コーデックのビット配分最適化のためのアルゴリズムで、限られたデータ量でいかに"聞こえる劣化"を最小化するかを支える基盤技術。CommanderSong（2018）やAdversarial Attacks via Psychoacoustic Hiding（2018）などの研究は、この同じ心理音響モデルを直接流用し、既存の楽曲に埋め込んだ状態でKaldiベースの音声認識システムへの標的型コマンド注入を実証している。
出典: https://arxiv.org/pdf/1801.08535 / https://arxiv.org/pdf/1808.05665
