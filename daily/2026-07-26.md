### <a id="card-1"></a>🆕 「指のクセ」が、暗号より先に正体を割る——電信の「フィスト」 〔move: 人間/身体をプロトコルの一部にする / 領域: ワイルドカード(通信史/SIGINT)〕

**事実**: モールス電信の送信者には「フィスト（fist）」と呼ばれる個人固有の打鍵リズム・くせがある。同じ符号表・同じ暗号文・同じ回線を使っていても、点と線の長さの配分や間の取り方は指の運び方に依存し、筆跡のように人によって違う。第二次世界大戦下、傍受員たちは暗号そのものは解けなくても、この「フィスト」だけを手がかりに特定の送信者（特定の艦・潜水艦・部隊）を継続的に識別し、部隊の移動を追う「トラフィック解析」を行っていた。誰も「認証情報」として設計していないのに、送信という行為そのものから勝手ににじみ出る癖だった。

**何ができる**: 中身が完全に暗号化された通信路でも、「打ち方のリズム」という別レイヤーの生体情報を使えば「本当に本人が送っているか」を継続的に見張れる。この発想を現代の無線ネットワークに持ち込むと、正規の暗号鍵や証明書を盗まれて“正しい”パケットを送られてしまっても、送信間隔やタイミングの癖がいつもと違えば異常として弾ける、乗っ取り検知の層が作れる。実際、無線機のハードウェア個体差（電源投入直後の過渡応答の波形など）を暗号なしの物理層認証として使う「RFフィンガープリンティング」研究が、IoT機器のなりすまし対策として今も続いている。鍵は盗めても、"打ち方"までは盗めない。

**技術の魅力**: 暗号は「中身」を守るが、「中身をどう生成したか」というメタな層まではカバーできない。人間の運動野が無意識に作り出すリズムは、意識して他人を真似ようとしても再現しづらく、原理的になりすましが難しい認証情報が、通信するたびに勝手ににじみ出ている——という非対称性がそのまま効いている。

**本来どこで使われてるか**: 第二次世界大戦下のSIGINT（信号諜報）における古典的な技術で、暗号解読とは独立に敵味方の識別や部隊追跡に使われた。現代ではこの発想は「RFフィンガープリンティング」として、電波の物理的な個体差を暗号を使わない物理層認証に転用する研究に受け継がれている。
出典: https://en.wikipedia.org/wiki/Morse_code / https://arxiv.org/html/2506.09807v1

### <a id="card-2"></a>🔍 文字ごとに姿を変えるフォントが、キー入力をJSなしで盗み見る 〔move: サイドチャネル/副作用の利用 / 領域: フロントエンド/グラフィックス〕

**事実**: CSSの `@font-face` には `unicode-range` という記述子があり、「この Unicode 範囲の文字がページ内で実際に使われている場合だけ」そのフォントファイルをダウンロードさせられる。多言語サイトで不要な文字集合の読み込みを避け、表示を軽くするための最適化機能だが、「読み込むかどうか」の判定を JavaScript 抜きにブラウザのレンダリングエンジン自身が黙って実行してくれる、という点が見落とされがちな仕様の急所になっている。

**何ができる**: 1文字に1つずつ対応する `unicode-range` を持つ `@font-face` ルールを大量に用意し、それぞれ攻撃者管理下の異なる URL を指すフォントファイルにしておけば、どの URL にリクエストが来たかを観測するだけで、ページ内にどの文字が実際に存在するかを JavaScript なし・CSS だけで漏らせる。入力欄の中身をCSSセレクタ経由で反映させる実装と組み合わせれば、パスワードやワンタイムコードをキー入力のたびに1文字ずつ外部サーバーへの通信という形で読み出せる——マイクロコントローラ並みに機能を削ぎ落とした“計算資源ゼロ”のオラクルが、フォント読み込みという地味な最適化だけで組み上がる。

**技術の魅力**: 「JavaScript 禁止のサンドボックス（CSPで script-src を絞った環境や HTML メールなど）は安全」という思い込みを裏切るのが効いている。CSSだけでも「条件に応じて外部リソースを取得する」という分岐＋通信の能力を持っており、見た目を整えるための最適化ロジックが、そのまま1文字ずつ答えを教えてくれる装置に化ける。

**本来どこで使われてるか**: 本来はCJK圏など巨大な文字集合を持つWebフォントを、実際にページで使う文字だけに絞って部分的に読み込むための帯域節約機能で、Google Fonts のような大規模Webフォント配信サービスが日常的にこの仕組みで転送量を減らしている。一方でこの「使われている文字だけ読み込む」という挙動自体が2015年頃からCSSインジェクション攻撃のPoCとして報告され、CSPの `style-src` 制限の議論のきっかけの一つになった。
出典: https://mksben.l0.cm/2015/10/css-based-attack-abusing-unicode-range.html / https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/unicode-range

### <a id="card-3"></a>💡 発電した分だけ叫んで死ぬ——電池を要らないZigbeeの野良センサー 〔move: 制約の極端化 / 領域: 無線/組み込み/ハードウェア〕

**事実**: Zigbee 3.0 の拡張仕様「Zigbee Green Power（ZGP）」は、電池すら載せない前提で設計されている。スイッチを押す指の力や、太陽電池・熱電素子で得たわずかな発電量だけを電源に、圧縮された最短12バイトのフレームを一瞬だけ送信する。送り終えたら電源は即座に尽き、機器は次に押されるまで文字通り“存在しない”。ペアリングの往復すら電力的に贅沢なので、送信は基本一方向・使い捨てにし、ネットワークへの参加は常時電源のある「プロキシ」ノードにまるごと肩代わりさせる。

**何ができる**: この「マイコン1個分の電気すら自前調達し、それを送信という形でそのまま使い切る」という極端な制約を逆手に取ると、電源管理を一切気にしないセンサー網が作れる。橋やトンネルの継ぎ目、屋根裏の断熱材の中など、電池交換どころか配線すら不可能な場所に、「振動や温度差が一定以上になった瞬間だけ勝手に発電して1フレームだけ叫ぶ」検知器をばら撒ける。個体には電池切れという概念がなく、壊れるまで“生きて”いるメンテナンスフリーの群れになる。

**技術の魅力**: 「常時起きていて双方向にやり取りする」という無線ネットワークの当たり前の前提を、"起きた瞬間にはもう喋り終わっている"レベルまで切り詰めているのが面白い。認証やACKのための余分な往復を全部プロキシに押し付けることで、末端デバイス自体は本当に「発電した分の電気を送信という形でそのまま捨てるだけの存在」になっている。

**本来どこで使われてるか**: スマートホームの電池レス・配線レス壁スイッチ（押した力だけで発電して照明を操作するペダル型スイッチなど）がGreen Powerの主戦場。EnOceanベースの製品なども含め、住宅・オフィスのライトスイッチやドアセンサーとして既に普及しており、Connectivity Standards Allianceが2024年にも仕様改定（1.1.2）を続けている現役の規格。
出典: https://csa-iot.org/all-solutions/green-power/ / https://docs.silabs.com/zigbee/latest/green-power-fundamentals/01-overview
