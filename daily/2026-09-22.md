### <a id="card-1"></a>🆕 大文字小文字のゆらぎが、DNS偽造対策にも密輸経路にもなる——DNS 0x20という気付かれない自由度 〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: DNSのドメイン名は本来大文字小文字を区別しない(case-insensitive)。だが実装上、権威DNSサーバーの多くは受け取ったクエリ文字列の大文字小文字パターンをそのまま応答にコピーして返す。この"どうでもいいはずの"性質を逆手に取り、送信側がクエリのアルファベット部分の大文字小文字をランダムに振ることで、16bitのトランザクションIDと16bitのソースポートに加えて追加のエントロピーを稼ぎ、キャッシュポイズニング攻撃への耐性を上げる——これが「DNS 0x20」符号化。2008年に提案され正式なIETF標準にはなっていないが、Google Public DNSをはじめ主要リゾルバに実装されている。

**何ができる**: 0x20エントロピーはセキュリティのために"乱数"として振られるが、乱数である必要はどこにもない——大文字小文字の並び自体を送信側が自由に選べる、低帯域だが正規の1本のチャネルとして使える。`EnGiNe.example.com` のように大文字/小文字パターンへ任意のビット列(1文字=1bit)をエンコードして送出すれば、それを受け取る権威サーバー(=自分で管理しているサーバー)がパターンをそのまま復元し、TXTレコードでも何でもない"ただの正規のAクエリ"の中にメッセージを密輸できる。ファイアウォールやDNSフィルタの大半はドメイン名をcase-insensitiveに正規化してから検査するため、このビット列は監視ログにすら残らない。

**技術の魅力**: 元は「セキュリティのために意味のない乱雑さを足す」という発想の機能なのに、その乱雑さの"選び方"を自分で握れる時点で、乱数ではなく信号になる。しかもこの機能は攻撃者ではなく防御側(リゾルバ)が能動的にオンにしている正規機能なので、フィルタリング側には最初から"疑うべき通信"のリストに入れる理由がない。安全のための仕組みの根拠(「予測不能であること」)と、悪用のための要件(「送信側だけが再現可能であること」)がちょうど同じ場所で両立している非対称性が効いている。

**本来どこで使われてるか**: DNS 0x20はD. Dagon, M. Antonakakisらの"Increased DNS Forgery Resistance Through 0x20 Bit Encoding"が出典。Googleは2023年、Google Public DNS(8.8.8.8)の権威サーバーへの問い合わせで大文字小文字ランダム化をデフォルト有効化したと発表しており、Sophosは「意図的なタイポがDNSのセキュリティを上げる」として報じている。
出典: https://news.sophos.com/en-us/2023/01/23/serious-security-how-deliberate-typos-might-improve-dns-security/ / https://www.theregister.com/2023/01/19/google_dns_queries/

### <a id="card-2"></a>🔍 読み飛ばすための数字が、誰も検算しない隠し場所になる——Parquetのzone mapという信頼されすぎたメタデータ 〔move: サイドチャネル/副作用の利用 / 領域: データ/同期/ストレージ〕

**事実**: Parquet(やORC)のような列指向ファイルは、ファイル末尾のフッターに各"row group"(数万〜数十万行のかたまり)ごとの各列のmin/max統計値("zone map")を持っている。これは実データとは完全に別領域のメタデータで、目的はクエリエンジンがWHERE句を見て「この行グループには該当行がありえない」と判断し、そのブロックを一切デコードせずスキップする「述語プッシュダウン(predicate pushdown)」を高速化すること。重要なのは、このmin/maxを信じるかどうかはエンジン側の一存で、実データとの整合性チェックは基本的に一切行われない点だ。

**何ができる**: この非対称性(統計はチェックされずに信頼される)を使うと、"データそのもの"とは別チャネルとして、誰も見ないカラムのmin/max値に任意のビット列を仕込める。ファイルは正規のParquetとしてどのエンジンでも普通に開け、行データは一切壊れていないのに、フッターだけを解析すれば隠しフラグや世代番号、透かし的な情報を読み出せる。実際、row groupのpruningロジックが統計を検証なしに信頼する設計のせいで「嘘のzone mapが、本来ヒットするはずの行を丸ごと隠してしまう」という不具合が公開バグ報告として上がっている——それだけ、この"読まれない側のメタデータ"は無防備な入口だということ。

**技術の魅力**: 本来"読まなくていい理由"を高速化のために教えてくれるはずの領域が、逆に"誰も読み合わせをしない領域"としてそのまま隠し場所になる。データを暗号化したりファイルを隠したりせず、正規のファイル構造の中で「みんなが信頼するが誰も検証しない部分」だけを狙い撃ちする発想が効いている。画素や音の劣化を心配する通常のステガノグラフィと違い、ビットはメタデータとしてバイト単位で厳密に保存される。

**本来どこで使われてるか**: Spark、DuckDB、Trino/Presto、AWS AthenaなどほぼすべてのモダンなSQL-on-Parquetエンジンが、フッターの統計情報だけを読んでスキャン対象のrow groupを絞り込む「predicate pushdown / row group pruning」に使っている。この信頼関係の危うさは実装バグとしても表面化しており、file統計だけを信頼するpruningロジックが嘘のzone mapによって正しい行を丸ごと隠してしまう、という指摘がGitHub issueとして報告されている。
出典: https://github.com/rtkelly13/Parquet.SourceGenerator/issues/378 / https://datalakehousehub.com/blog/2024-10-all-about-parquet-part-07/

### <a id="card-3"></a>💡 掴まずに、掴まなくていい場所だけを作る——フェーズドアレイ音響浮遊という配線レスの治具 〔move: 物理現象へのピギーバック / 領域: ワイルドカード(音響物理学) / レンズ: オフライン完結〕

**事実**: 空気中で音の定在波を作ると、波長の半分間隔で並ぶ「節」(圧力の谷)に、周囲の空気より重く/圧縮されにくい小さな物体が引き寄せられて浮く。これが音響浮遊(acoustic levitation)で、原理自体は1933年のBücksとMullerによる、水晶振動子と反射板の間でアルコール液滴を浮かせた実験まで遡る。近年はスピーカー1個や対向2枚の板ではなく、多数の超音波トランスデューサを格子状に並べた「フェーズドアレイ」にし、各素子の位相をソフトウェアでずらすことで、節の位置(=物体の位置)を配線もモーターも一切動かさず"波の足並み"だけで自在に動かせるようになった。

**何ができる**: これを使うと、専用の治具やロボットアームを使わずに、微小部品を非接触のまま宙に固定・移動させる"配線レスの組み立てベンチ"が作れる。位相パターンを切り替えるだけで複数の浮遊点を同時に生成・移動できるので、静電気やパーティクル汚染を嫌うMEMS部品や、接触自体がダメージになる脆い試料の位置決めに使える。ネットワークもクラウド制御も不要で、トランスデューサ基板とドライバ回路だけで完結する——文字通りオフラインの卓上装置として動く。

**技術の魅力**: 「物をどう掴むか」ではなく「空間のどこに"掴まなくていい場所"を作るか」に問題を作り替えているのが面白い。アクチュエータが物体を動かすのではなく、空間の圧力地図そのものを位相操作で書き換え、物体は「そこにしかいられない」という物理法則に従って勝手に移動する。接触型の治具が抱える摩耗・静電気・汚染のリスクをまるごと消しながら、可動する機構部品はゼロで済むという裏技的な非対称性がある。

**本来どこで使われてるか**: NASAやESAは微小重力環境下での容器なし材料処理(containerless processing)に音響浮遊を使っており、溶融合金や反応性の高い試料を壁面に触れさせずに扱うことで、容器由来の不純物混入や不均一核生成を避けている。近年は浮遊させた液滴内でクリックケミストリーや酵素反応を進める"容器なし反応器"としての研究も報告されており、フェーズドアレイ式の音響ピンセットは粉体リサイクルや微粒子操作の研究プラットフォームとしても実装が進んでいる。
出典: https://en.wikipedia.org/wiki/Acoustic_levitation / https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7856899/
