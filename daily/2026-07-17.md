### <a id="card-1"></a>🆕 ゲノム解読用の圧縮法が、伸ばさずに検索できる索引に化ける——FM-index 〔move: 異分野の手法移植 / 領域: データ/同期/ストレージ〕

**事実**: Burrows-Wheeler変換(BWT)は1994年、Burrows と Wheeler がデータ圧縮のためだけに考案した文字列の並べ替え手法で、同じ文脈の文字を近くに集めてrun-length符号化を効かせやすくする。2000年、Ferragina と Manzini はこのBWTを転用し、「圧縮したまま伸長せずに任意の部分文字列を検索できる」自己索引(self-index)であるFM-indexを作った。本来ぶつかり合うはずの"小さくする"と"検索しやすくする"を、同じバイト列の中で両立させたのが肝。

**何ができる**: 巨大なテキストやログをFM-indexに変換すると、圧縮ファイルと検索インデックスが同一の1個のバイト列になる。展開して別にBツリー索引を作る必要がなく、その場でパターン検索・出現位置特定がサブ線形の時間でできる。ローカルファーストのノートアプリや静的サイトの全文検索エンジンをこの発想で作れば、「同期して配る1個の圧縮ファイル」がそのまま検索エンジン本体になり、別建てのインデックスファイルを持ち歩かずに済む。

**技術の魅力**: 普通、圧縮率と検索性能はトレードオフの関係にある(圧縮すれば構造が壊れて探しにくくなる)。FM-indexはこの対立を「並べ替えてから数える」という一手で無効化してしまう非対称性が効いている。索引とデータを分けて持つのが当たり前という発想の外に出た、地味だが強い転用。

**本来どこで使われてるか**: 本来はDNA/RNA配列の解析用。BWA(Burrows-Wheeler Aligner)やBowtieといったゲノムアラインメントツールは、ヒトゲノム(約30億塩基対)をまるごとFM-indexに変換し、次世代シーケンサーが吐き出す数億本のショートリードをそこに高速マッピングする。ゲノム医療・NGS解析パイプラインの心臓部として、圧縮と検索を同時にこなしている。
出典: https://en.wikipedia.org/wiki/FM-index / https://pmc.ncbi.nlm.nih.gov/articles/PMC2828108/ / https://bio-bwa.sourceforge.net/bwa.shtml

### <a id="card-2"></a>🔍 誰も真面目に実装しなかった緊急信号が、OSの正体を漏らす——TCP緊急ポインタ 〔move: 仕様の目的外利用 / 領域: ネットワーク/プロトコル〕

**事実**: TCPヘッダのUrgent Pointer(URGフラグ)は、Telnetの「Ctrl-Cで今すぐ処理を中断させる」ような緊急データの位置を伝えるためにRFC 793で規定された。ところがRFC 793自身が「ポインタは緊急データの最後のバイトを指す」のか「その次のバイトを指す」のかで自己矛盾しており、この曖昧さは10年以上放置された末、2010年のRFC 6093でようやく明文化された。結果、OSごとのTCPスタック実装がこの2バイトのフィールドをそれぞれ微妙に違う癖で扱うようになった。

**何ができる**: この「誰も気にしないフィールドの実装差」を逆手に取り、通信内容には一切触れずに1パケットの応答だけで相手のOSを言い当てられる。実際にnmapのOS検出エンジンは、URGフラグを立てていないのにUrgent Pointerフィールドに非ゼロ値を混ぜたECNプローブパケットを送り、応答でその値がどう扱われるか(クリアされるか、そのまま返るか)を見て「Q」テストの結果に組み込み、OS指紋の一部として使っている。

**技術の魅力**: セキュリティは普通ペイロードや暗号方式を疑うが、ここで漏れているのは「本文が空のヘッダの隅」でしかない。仕様が自己矛盾したまま10年以上放置されたことで生まれた実装ゆらぎが、そのまま個体識別子になってしまうという非対称性が効いている。緊急性を伝えるための仕組みが、緊急でも何でもない"素性バレ"の道具に化ける。

**本来どこで使われてるか**: 本来はTelnetのInterrupt Process/Synchシグナルのような「今読んでいるデータより先に、割り込んで処理してほしいデータがある」ことを伝えるための仕組みだった。今日的にはこの目的で使われることはほとんどなく、Palo AltoやCheck Pointなどのファイアウォールはデフォルトでこのフラグ自体を黙って剥がしてしまう。皮肉にも、その"誰も真面目に使わない"という扱いのされ方の違いこそが、nmapのようなツールにとってのOS判別材料になっている。
出典: https://datatracker.ietf.org/doc/html/rfc6093 / https://nmap.org/book/osdetect-methods.html

### <a id="card-3"></a>💡 気圧計が、権限なしのマイクになる——バロメーター盗聴 〔move: センサーの転用 / 領域: 無線・組み込み・ハードウェア〕

**事実**: スマートフォンの気圧センサー(バロメーター)は本来、高度計や天気予報、GPSの高度精度補正のために積まれている地味なセンサーで、マイクと違ってAndroidでは特別なパーミッションなしにどのアプリからでも読み取れる。ところが2020年の研究"Barometers Can Hear"は、スピーカーが鳴らす低周波の音が生む微小な空気圧の揺れを、この気圧センサーがサンプリングレートの範囲内で実際に拾ってしまうことを実証した。画面をタップする指が起こすわずかな圧力変化さえ検知できるという。

**何ができる**: マイク権限を一切持たない悪意アプリが、同じ端末上の別アプリ(スピーカーだけ鳴らせればいい)と結託すれば、気圧センサー経由で低ビットレートのデータをやり取りするアプリ間の隠しチャンネルが成立する。OSのパーミッションダイアログには一度も表示されない経路で、"聞こえないはずの音"を使った端末内通信や、タップの圧力パターンからの入力推測までできてしまう。

**技術の魅力**: OSのパーミッションモデルは「音を録る=マイクへのアクセス」という直感的な境界線で権限を切っている。しかし"音"を物理的には"空気圧の微小な振動"と定義し直した瞬間、権限のかかっていない別のセンサーで代替できてしまう。守るべき境界の引き方がハードウェアの物理法則とズレている、という盲点そのものが攻撃面になっている。

**本来どこで使われてるか**: 本来は屋内外判定(ドアの開閉やエレベーターの移動で気圧が変わることを利用)や、GPSの高度精度を補う用途で静かに働いている実用センサー。研究チームはこれが意図せず高感度な"隠しマイク"として機能しうることを実証し、Androidのパーミッションモデルにおけるセンサー間の抜け穴として報告した。
出典: https://arxiv.org/abs/2008.03872 / https://arxiv.org/pdf/2110.06363
