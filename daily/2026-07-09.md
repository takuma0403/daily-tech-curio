### <a id="card-1"></a>🆕 ブラウザに殺された認証仕様が、JWTの皮を被って蘇る 〔move: レガシー/廃止予定機能の蘇生 / 領域: セキュリティ/認証〕

**事実**: HTTPの世界には2011年頃からToken Binding（RFC 8471）という仕様があった。トークンをTLSコネクション自体の暗号鍵に結びつけ、盗まれたトークンを別の接続で使い回せなくする発想。しかしTLS層への実装依存が重く、Chromeは2018年に実装を削除、他の主要ブラウザも追随せず、事実上死んだ規格になった。

**何ができる**: この「トークンを鍵に結びつけて盗用を無効化する」というアイデアそのものを、TLS層ではなくHTTPリクエストのヘッダーに載るJWTとして作り直したのが2023年制定のRFC 9449、DPoP（Demonstrating Proof-of-Possession）だ。クライアントは使い捨ての鍵ペアを生成し、リクエストのたびに「今このURLに、この方法で送る」と主張する短命な署名付きJWT（DPoP proof）を添付する。アクセストークン側にはその公開鍵のSHA-256サムプリント（`cnf.jkt`）が埋め込まれ、サーバーはリクエストごとに proof の署名・宛先（`htm`/`htu`）・トークン本体のハッシュ（`ath`）をすべて突き合わせる。トークンだけ盗んでも、対応する秘密鍵ごと盗まれない限り再利用できない。

**技術の魅力**: 「鍵に紐付ける」という同じアイデアを、葬られた場所（TLSコネクション）から一段上のレイヤ（アプリケーション層のJWT）へそのまま移植しただけで、ブラウザベンダー全員の合意という詰んでいた条件を回避して息を吹き返した点が効いている。仕様が死んでも、そこに宿っていた設計思想は死なない——葬式の後、別の体を借りて歩き出す標準化の話。

**本来どこで使われてるか**: OAuth 2.0のアクセストークン盗難対策として、Auth0・Okta・IBM Verify・Cloudflareなどが2024年以降相次いでDPoPを実装。金融API標準のFAPI 2.0でも必須要件に組み込まれている。
出典: https://datatracker.ietf.org/doc/html/rfc9449 / https://oauth.net/2/dpop/

### <a id="card-2"></a>🔍 光センサーがスクリーンの中身を"覗き見"する 〔move: サイドチャネル/副作用の利用 / 領域: フロントエンド/センサー〕

**事実**: W3CのAmbient Light Sensor APIは、スマホやノートPCの周囲光センサーの値をJavaScriptから読める仕様で、本来は画面の自動輝度調整のような省電力機能のために作られた。しかし2017年、研究者Lukasz OlejnikとArtur Jancは、この「周囲の明るさ」の値が実は画面自体の発光が顔・手・机などの近くの面で反射して回り込んだものまで拾ってしまうことを示した。画面の色を変えると、センサー値がわずかに揺れる。

**何ができる**: ページ側から見た目には気づかれない形で対象リンクを一瞬「訪問済み色」と「未訪問色」で塗り分け、その瞬間のセンサー値の揺れを見るだけで、ユーザーがそのURLを訪問済みかを外部から推定できる（`:visited` CSSのプライバシー保護をセンサー経由で迂回する）。同じ原理を拡張し、画面に文字列やQRコードを一瞬だけ明滅させてその反射光パターンだけで内容を復元することにも成功しており、条件が良ければ1ビットを500ミリ秒で確実に読み取れる。実証実験では16文字の文字列復元に48秒、QRコード1枚の読み取りに3分20秒を要した。

**技術の魅力**: センサー権限もカメラ権限も要らない。周囲光センサーはもともと許可ダイアログなしで誰でも読めるpermission-less APIとして設計されていたため、画面という「送信機」とセンサーという「受信機」がブラウザの中に無許可で同居してしまっていた。攻撃者は自分の書いたJSだけで送受信の両端を握っているので、外から見れば無害なページが、自分自身の発光を自分自身で盗み見る自己完結型のサイドチャネルになる。

**本来どこで使われてるか**: 本来はスマホ・ノートPCの自動輝度調整やカメラアプリの露出補正など、省電力・UX向上のための地味なセンサー機能。この研究を受けてW3C仕様は2022年に改訂され、サンプリング頻度の上限設定と照度値を50lux単位に丸める量子化が導入され、Chrome・Firefoxは既定で機能を制限した。
出典: https://blog.lukaszolejnik.com/stealing-sensitive-browser-data-with-the-w3c-ambient-light-sensor-api/ / https://www.theregister.com/2022/08/13/ambient_light_security/

### <a id="card-3"></a>💡 流れ星の尾を"電波の鏡"にして積雪データを40年送り続けた 〔move: 物理現象へのピギーバック / 領域: ワイルドカード(通信史)〕

**事実**: 毎日大量の砂粒サイズの流星が高度80〜120km付近の大気で燃え尽き、幅数百m・長さ数十kmの電離した尾を数秒だけ残す。この一瞬の電離柱はVHF帯の電波をかなり効率よく反射する。これを利用した「メテオバースト通信」は、衛星もケーブルも使わず、常に降り注いでいる流れ星そのものを電波の中継鏡として借りる通信方式だ。

**何ができる**: 送信局は特定の受信局宛の呼び出し信号を空へ繰り返し打ち続け（probe-and-wait）、ちょうど良い流星痕が現れて反射が成立した一瞬だけ両局が同期し、データを一気にバースト送信する。米国防総省の資料によれば、100ミリ秒級の通信窓は17秒に1回、200ミリ秒級は35秒に1回、400ミリ秒級は2分半に1回という頻度でしか訪れないため、メッセージは極めて短く圧縮しておく必要がある。米農務省（USDA）はこの方式で西部11州・500カ所以上の山岳無人観測所（SNOTEL）から積雪水量データを2023年まで40年以上にわたり収集し続けた。

**技術の魅力**: 誰も打ち上げていない、勝手に燃え尽きる砂粒という自然現象そのものを通信インフラとして無償で借りる発想が効いている。衛星は撃墜でき、光ファイバーは切断できるが、流れ星は毎秒どこかで必ず降っており、送受信局の位置を知らない限り傍受も妨害もほぼ不可能。この「壊しようがない」という非対称性ゆえに、核攻撃後の電離層攪乱にも強い通信手段として軍でも研究されてきた。

**本来どこで使われてるか**: SNOTELのような無人環境観測網のほか、冷戦期から米軍が電離層の乱れやすい高緯度地域向けの通信手段として研究・運用してきた。SNOTELは2023年に他方式へ更新され現役を退いたが、傍受耐性・耐障害性の高さから軍事用途では今も研究が続いている。
出典: https://en.wikipedia.org/wiki/Meteor_burst_communications / https://en.wikipedia.org/wiki/SNOTEL / https://hackaday.com/2025/05/12/radio-apocalypse-meteor-burst-communications/
