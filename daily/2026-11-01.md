### <a id="card-1"></a>🆕 窓辺に「腕」を生やして、電波ゼロの光通信塔を建てる 〔move: レガシー/廃止予定機能の蘇生 / 領域: ワイルドカード(歴史×光学通信)〕

**事実**: 18世紀末にフランスで実用化されたシャップ式腕木通信は、太い梁（レギュレーター）の両端に可動の腕（インジケーター）を付けた塔で、梁が2通り、腕が各7通りの角度を取り、2×7×7=98通りの形を作った。うち6つは「メッセージ終了」「誤り」などの制御用に取り置かれ、内容に使えるのは92通り。塔の係員は制御信号しか知らず、意味を引く符号表は別に保管されていた。見落とされがちなのは、これが「形」をシンボルとする立派な低速デジタル回線で、中継ごとに受信確認と誤りの再送という手続きまで持っていた点。

**何ができる**: マイコン1個とサーボ3つで「梁と2本の腕」を作り、窓辺に置いて角度で情報を出す。向かいのビルや隣家のスマホ（カメラ＋OpenCVかブラウザのCanvas）が腕の角度を読み取り、1形=約6.5bit（log2 92）で受け取る。電波も配線も使わないので、無線禁止の場所や、電波が信用できない現場で見通し線だけの片方向掲示板になる。中継の塔を並べて、各塔が見えた形をそのまま自分のサーボで再現すれば、実際に塔から塔へのバケツリレー通信が再現できる。

**技術の魅力**: 98通りという数字は、符号を作る人が「腕の角度を人が見分けられる最小の刻み」から決めた設計になっている。つまり受信機（人の目）の分解能が符号の大きさを決めた。今回はそれがカメラ＋画像処理に置き換わるので、刻みを細かくすれば符号がそのまま増える。「見える」ことだけが通信路の条件で、電波法も帯域も関係ない非対称さが面白い。

**本来どこで使われてるか**: 1790年代にクロード・シャップが発明し、フランスは革命・ナポレオン期に軍事・政府通信網として塔を全国に展開した。塔には制御符号しか知らない2人の係員が詰め、実際の文言は符号表（1795年の表は8,940項目）にあった。誤りは塔から塔へ再送するしかなく、確実に消す仕組みは無かったとされる。
出典: https://en.wikipedia.org/wiki/Chappe_telegraph / https://en.wikipedia.org/wiki/Telegraph_code / https://www.historyofinformation.com/detail.php?entryid=496

### <a id="card-2"></a>🔍 一番乗りを選ばず、遅らせてから全部走らせる——Happy Eyeballsを“最寄りミラー探し”に転用する 〔move: 異分野の手法移植 / 領域: ネットワーク/プロトコル〕

**事実**: IPv6とIPv4の両方で繋がれる相手に、ブラウザなどは先にIPv6を試し、少しの猶予（RFC 8305では接続試行の遅延は約250ms、DNS応答待ちのResolution Delayは推奨50ms）が過ぎても繋がらなければ、前の試行を止めずに次のアドレスで並行して試す。最初に接続が確立した方を採用し、残りは捨てる。これが Happy Eyeballs v2。ポイントは「順番に試す」と「全部同時に試す」の中間にある、時間差のレース（stagger）だという点。

**何ができる**: この「遅らせて走らせ、勝者だけ残す」を、アドレスファミリでなく“ミラーの候補”に流用する。たとえば自前のダウンロードスクリプトで、同じファイルを持つ複数のミラーに数百msずつ時間差でHTTP接続を始め、最初にTLSまで終わった1つを使う。地理DBも遅延測定サーバーも要らず、その瞬間に一番速い経路が勝手に選ばれ、壊れたミラーは猶予の間に自然に降りる。

**技術の魅力**: 「どれが速いか」を事前に測らず、レースそのものを測定にしている。時間差を付けることで、本命（優先順位の高い候補）に先に走るチャンスを与えつつ、本命が転んだ時の待ち時間を猶予の長さに抑える。同時発射だと帯域を無駄にし、順次だと遅い。両者の間の一つの定数（250ms）に設計の肝が詰まっている。

**本来どこで使われてるか**: ブラウザやOSの接続処理。IPv6が経路上で壊れていると、昔のブラウザは数十秒待たされることがあり、それを避けるためにRFC 6555が生まれ、RFC 8305（2017年12月）でv2へ。DNSの応答を並行して扱い、複数アドレスを時間差で試す仕様になっている。
出典: https://datatracker.ietf.org/doc/draft-ietf-v6ops-rfc6555bis/03/ / https://pike.lysator.liu.se/docs/ietf/rfc/83/rfc8305.xml

### <a id="card-3"></a>💡 ブラウザは、USBのジョイスティックしか知らない——マイコンを「コントローラ」と偽って8軸センサー入力にする 〔move: 仕様の目的外利用 / 領域: フロントエンド/グラフィックス〕

**事実**: ブラウザのGamepad APIは、繋がったゲームコントローラの軸（0.0〜1.0 に正規化されたアナログ値）とボタンを、`navigator.getGamepads()` で毎フレーム読めるようにする。つまりブラウザにとって「アナログ値が並んだUSB機器」は、中身がジョイスティックでもポテンショメータでも区別がつかない。出力側にも `vibrationActuator.playEffect('dual-rumble')` があり、強弱2つの強さ（0〜1）を送れる。

**何ができる**: USB HIDを話せるマイコン（RP2040や32u4など）を“ゲームパッド”として名乗らせ、光センサー・ひずみゲージ・可変抵抗などのアナログ値を軸に載せれば、WebUSBも専用ドライバも使わずにHTTPSのページがセンサー値を毎フレーム読める。ペアリング操作も権限ダイアログも不要で、取り出して挿せば動く。ページ側は`requestAnimationFrame`で読んでWebAudioのシンセやCanvasに繋ぐだけで、自作の楽器やインスタレーションになる。

**技術の魅力**: 「センサーをWebに繋ぐ」ための道具は、Web Serial・WebUSB・WebHIDと権限ダイアログ付きのものが並ぶが、ゲームパッドだけは“ただ見えてしまう”枠。ゲームのためだけに用意された入口を、全然ゲームではない入力の裏口として借りるのが効いている。

**本来どこで使われてるか**: ブラウザゲームやクラウドゲーミングでのコントローラ入力。`vibrationActuator`は対応ハードごとに挙動が変わり、ブラウザによって対応状況が異なる。MDNは安全なコンテキスト（HTTPS）でのみ利用可能で、主要ブラウザ全てでは動かない点を注記している。
出典: https://developer.mozilla.org/en-US/docs/Web/API/GamepadHapticActuator/playEffect / https://developer.mozilla.org/docs/Web/API/Gamepad/vibrationActuator

🔎 検索ワード: `Gamepad API getGamepads axes polling` / `RP2040 USB HID gamepad descriptor axes` / `vibrationActuator playEffect dual-rumble` / 「Gamepad API 自作 センサー」
