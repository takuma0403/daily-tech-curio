### <a id="card-1"></a>🔭 損失を待たず「管」を測る——BBR が TCP 輻輳制御に持ち込んだ物理モデル 〔move: 異分野の手法移植 / 領域: ネットワーク/プロトコル〕

**事実**: TCP の伝統的な輻輳制御（CUBIC、Reno）は「パケットが落ちてから」速度を下げる——ブレーキを踏むのは事故の後だ。Google が2016年に発表した BBR（Bottleneck Bandwidth and Round-trip time）はアプローチを根本から変えた。ネットワークを「ボトルネック帯域幅（BtlBw）」と「往復伝播時間（RTprop）」という2つのパラメータで定義される物理的な「管」としてモデル化し、その管を「空でもなく、溢れてもない」最適状態に保つよう送信レートを制御する。これは制御理論のフィードバックループ設計そのものを輸入した発想だ。

**何ができる**: BBR は Probe Bandwidth → Drain → Probe RTT という3フェーズのサイクルで管の実状を継続的に推定し、送信レートを調整し続ける。その結果、CUBIC が苦手とする「高帯域幅×高遅延」リンク（衛星回線、大陸間光ファイバー）でも管を常に充填できる。Google の測定では CUBIC 比でスループットが最大133倍改善した事例もある（中央値は2〜25倍）。Linux 5.4以降は `tcp_bbr` モジュールとして利用可能で、`sysctl net.ipv4.tcp_congestion_control=bbr` の1行で有効化できる。

**技術の魅力**: 「パケットロスは輻輳の証拠ではなく、輻輳の結果だ」というパラダイムシフトが核心にある。ロスが起きる頃には管はすでに溢れており対処が遅い。BBR は管の内径（帯域幅）と長さ（RTT）を先に測り、管が溢れる前に送信量を調整する。この「反応型→予測型」の転換は、プラントをモデル化してからフィードバック制御する古典制御工学の手法を、そのままネットワーク層に移植したものだ。

**本来どこで使われてるか**: 2016年にGoogleの社内バックボーンB4ネットワーク全TCPトラフィックへ展開開始し、以降YouTubeとgoogle.comのWebサーバーにも導入された。全5大陸でレイテンシが大幅改善し、特に発展途上地域でスループット14%超向上と報告されている。BBRv3はIETF 117（2023年7月）とIETF 119（2024年3月）でGoogleの公開インターネット向け展開が発表され、Linuxカーネルへの取り込みを経てCloudflareやFastly等の主要CDNにも採用が広がっている。
出典: https://queue.acm.org/detail.cfm?id=3022184 / https://cacm.acm.org/practice/bbr-congestion-based-congestion-control/

### <a id="card-2"></a>🔐 製造ばらつきが秘密鍵になる——SRAM PUF はチップ自身をパスポートにする 〔move: 制約の極端化 / 領域: セキュリティ/認証〕

**事実**: どんなシリコンチップの製造工程にも原子スケールの不均一性がある。SRAM セルは2つのインバータが互いにラッチする構造だが、製造ばらつきでどちらか一方がほんの少し電気的に強い。電源投入直後、まだ外部から何も書き込まれていない瞬間に、SRAM は確率論的にではなく「そのチップ固有のビットパターン」に収束する——これが SRAM PUF（Physical Unclonable Function）だ。同一設計・同一ロットのチップでもこのパターンは一致せず、製造後に変更も複製もできない。

**何ができる**: 電源投入時に SRAM の初期値を読み取り、ファジー抽出器（Fuzzy Extractor）でノイズを補正すれば、チップ固有の安定した秘密鍵が生成できる。EEPROM への鍵書き込みも、Secure Element も不要。電源を切れば鍵は消え、次回起動で同じ鍵が「再生成」される。Arduino UNO（ATMega328P）で特別なハードウェアなしに SRAM PUF を実装した PoC が IEEE SECON 2019 で発表されており、マイコン1個だけで完結する。

**技術の魅力**: 「鍵を持つな、チップ自体が鍵になれ」という極端な制約から生まれた解だ。EEPROM や eFuse に鍵を焼けば、デバッガや電磁サイドチャネル攻撃で読み出されるリスクがある。SRAM PUF は「攻撃者が鍵を読もうとしてチップを物理的に操作した瞬間、製造ばらつきの微妙なバランスが崩れて別の値になる」という不可侵性を持つ。秘密が「保存された場所」にあるのではなく「物質そのもの」の構造の中にあるという反転が、従来のセキュリティモデルと根本的に違うところだ。

**本来どこで使われてるか**: NXP Semiconductors（LPC54S0xxシリーズ）、Xilinx（Zynq UltraScale+）、Microchip（ATECC608）などの商用チップに実装されており、ISO/IEC 20897がIoT向けPUFの標準規格として発行されている。軍事・航空宇宙分野では半導体偽造品の真贋確認、クラウドIoTプラットフォームではゼロタッチプロビジョニング（出荷時に鍵を書き込まず、初回起動のPUFベースIDを製造者がクラウドに登録する方式）に使われている。
出典: https://arxiv.org/abs/1907.12144 / https://pmc.ncbi.nlm.nih.gov/articles/PMC7472131/

### <a id="card-3"></a>📦 「ダウンロード再開」のヘッダが SQLite を CDN 化する——sql.js-httpvfs が開けた穴 〔move: 仕様の目的外利用 / 領域: データ/同期/ストレージ〕

**事実**: HTTP/1.1 の `Range` ヘッダ（RFC 7233）は、大きなファイルのダウンロードが中断したときに続きから再開するために設計されたものだ。しかし SQLite のファイル構造はすべてのデータを固定サイズのページ（デフォルト4096バイト）で構成された B-Tree であり、インデックスを使うクエリは B-Tree 経路上のページだけを読めば完結する。phireskyの `sql.js-httpvfs`（2021年公開）はこの偶然の適合を突いた：ブラウザ内 SQLite（sql.js）に独自の仮想ファイルシステムを差し込み、「ページ読み取り = Range リクエスト」に変換する。

**何ができる**: 100MB の SQLite ファイルを GitHub Pages / S3 / Cloudflare Pages に置くだけで、ブラウザから SQL クエリを実行できる。インデックス付きクエリ1本あたりに発行される Range リクエストは通常数回、転送量は数KB〜数十KB で済む。API サーバーなし、バックエンドなし、DB サーバーなし。静的ファイルホスティングが Read-Only SQL データベースサーバーとして機能するため、数千万行規模のデータセットをゼロ円で公開検索可能にできる。同じ発想は Parquet ファイルにも展開されており、DuckDB WASM + HTTP Range で列指向クエリもブラウザで実現されている。

**技術の魅力**: Range リクエストが「任意のバイト範囲を取得できる」ことは、ディスクのランダムリードと同義だ。SQLite の B-Tree traversal はランダムリードの連鎖そのものだから、HTTP がそのまま B-Tree のストレージ層になれる。「ファイル再開」という地味な機能が「ランダムアクセス可能なリモートブロックデバイス」として機能してしまうという、設計者が想定しなかった完成度の高い転用だ。CDN のキャッシュ効率も良い——クエリが特定のページに集中するほど（ホットなインデックスノード）そこだけが CDN にキャッシュされ、2回目以降は実質オフライン動作に近くなる。

**本来どこで使われてるか**: RFC 7233 が想定していたのは、ビデオストリーミング（シーク操作でその時刻のバイト範囲を要求）、ダウンロードマネージャーの並列分割ダウンロード、CDN の部分キャッシュ更新などだ。実際 Range リクエストはブラウザの `<video>` タグが内部で常時発行している。sql.js-httpvfs は Observable の公開データ可視化や、datasette-lite（Python 製 Datasette の Pyodide ブラウザポートがこの VFS を採用）で実際に稼働しており、国勢調査データ・GitHubアクティビティ分析・個人ログデータベースを CDN だけで公開検索する事例が多数ある。
