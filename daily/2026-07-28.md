### <a id="card-1"></a>🆕 “ランダムに見える”ことが免罪符になる、TLSハンドシェイクの隠し便——GREASE密輸術 〔move: サイドチャネル/副作用の利用 / 領域: ネットワーク/プロトコル〕

**事実**: TLSのClientHelloには、拡張やCipher Suiteの並び順そのものに意味はなく、サーバー側は順序を無視して処理することがRFC 8701（GREASE）で定められている。GREASEは本来、ブラウザや中間装置が未知の値を弾いてしまう「仕様の硬直化」を防ぐための仕組みで、Chromeなどはわざとランダムな拡張値を混ぜて送る。見落とされがちなのは、「並び順がランダムに見えること」自体がGREASE準拠のブラウザとしてはむしろ正常であり、ファイアウォールやDPIはこの順序のゆらぎを異常とはみなせない、という点。

**何ができる**: Cipher SuiteやExtensionのリストをそのまま並べ替え、その順列自体に意味を持たせれば、パケットの中身を一切書き換えずにデータを運べる。n個の要素の並べ替えは最大 log2(n!) ビットを表現できるので、22種類のCipher Suiteなら1パケットあたり約70ビット。TLSハンドシェイクとして完全に正規なパケットのまま、DPIやNGFWの検査をすり抜けてデータを外部へ持ち出せる——実際にKeysightの研究者が「HeLoL Tunnel」として実装し、既存の対抗手法SNICatより高いスループットを確認している。

**技術の魅力**: 暗号化やペイロードの中身を疑うのが普通のDPIの仕事だが、ここで運ばれる情報は「中身」ではなく「並び」にある。しかもその並びがランダムに見えることは、GREASE準拠の証としてむしろ歓迎される——検査官が「正常の印」だと思っているものが、そのまま隠し文字の運び屋になっているという非対称性が効いている。

**本来どこで使われてるか**: GREASEはTLSエコシステムの硬直化を防ぐための仕様で、ブラウザ実装がランダムな未知の拡張値を送り込み、サーバーや中間装置に「知らない値は無視する」実装を強制するために使われている。ChromeやFirefoxは通常のTLS接続で日常的にGREASE値を送っており、JA3のようなTLSフィンガープリンティング手法もGREASE値を除外してから処理するのが標準になっている。
出典: https://www.rfc-editor.org/rfc/rfc8701.html / https://github.com/Keysight/helol-Tunnel

### <a id="card-2"></a>🔍 UWBチップを1個も足さずに、BLEの位相のゆらぎだけで車の鍵をcm単位で当てる 〔move: 制約の極端化 / 領域: 無線/組み込み/ハードウェア〕

**事実**: Bluetooth Core Specification 6.0（2024年）で追加されたChannel Soundingは、専用のUWB（超広帯域）チップを積まなくても、既存のBluetooth LE無線だけでセンチメートル級の距離測定を可能にする機能。手法は2つあり、電波の往復時間を測るRTT（Round Trip Time）と、電波の位相のズレから距離を割り出すPBR（Phase-Based Ranging）。重要なのは、位相測定を1本の周波数だけでなく最大79チャンネルにまたがって繰り返すことで、屋内の反射（マルチパス）による誤差を打ち消せること。

**何ができる**: 新しいアンテナや専用測位チップを1つも足さず、ファームウェアの機能追加だけでスマホやイヤホンの内蔵Bluetoothチップを±10cm精度の測距センサーに変えられる。RTTとPBRを組み合わせれば、中継攻撃（リレーアタック——鍵の電波を離れた場所へ中継して盗む攻撃）にも耐えられる距離の下限保証つきの近接判定が作れる。自動車の「近づいたら解錠」も、UWBチップのコストや消費電力なしで実現できる。

**技術の魅力**: UWBが専用ハードウェアで解決してきた問題を、ほぼ全てのスマホ・イヤホン・タグに既に載っている汎用BLE無線の「位相のブレ」という副産物だけで肩代わりする。本来は通信するためだけの電波から、ハードウェア追加ゼロで位置情報を絞り出すという制約の極端化——「足すのではなく、今あるものの精度の限界まで搾り取る」方向に振り切っている。

**本来どこで使われてるか**: Car Connectivity Consortium（CCC）のデジタルキー規格が採用を進めており、自動車メーカーはUWBチップのコストと消費電力を避けつつ、鍵の中継攻撃耐性を確保する手段として期待している。Bluetooth SIG自身も、スマートロックや近接サービス、資産追跡といったユースケースを想定していると説明している。
出典: https://www.bluetooth.com/blog/bluetooth-channel-sounding-a-step-towards-10-cm-ranging-accuracy-for-secure-access-digital-key-and-proximity-services/ / https://www.bluetooth.com/learn-about-bluetooth/feature-enhancements/channel-sounding/

### <a id="card-3"></a>💡 リーダーもマスター時計もなしに、ホタルの明滅がセンサー網の時刻を合わせる 〔move: 異分野手法移植 / 領域: ワイルドカード(生物学×分散システム)〕

**事実**: 東南アジアのマングローブに群れるホタルは、誰か1匹が音頭を取るわけでもないのに、数千匹が完全に同期して明滅する。この現象を数理的に説明したのが1990年のMirollo-Strogatzモデルで、各個体を「自分の位相が一定値に達したら発光し、他個体の発光を見るたびに自分の位相を少し早める」だけの単純な振動子（パルス結合振動子）として表現すると、初期状態がバラバラでも有限時間で全体が同期に収束することを数学的に証明した。

**何ができる**: これを無線センサーネットワークの時刻合わせにそのまま輸入したのがReachback Firefly Algorithm（RFA）で、各ノードは「自分のタイマーが満了したら短いビーコンを送る」「他ノードのビーコンを受けたら自分のタイマーを少し早める」というたった2つのルールだけで、マスタークロックもリーダー選出も往復メッセージのやり取りも一切なしに、多ホップのセンサー網全体の発火タイミングを収束させる。ノードが電池切れで脱落したり新しく参入したりしても、中央の再設定なしに勝手に同期し直す。

**技術の魅力**: NTPやPTPのような時刻同期は「誰かが基準時刻を持ち、それを配る」階層構造が前提だが、ホタルのアルゴリズムには基準もリーダーもない。ノード同士がお互いの発火を見て少しずつ歩み寄るだけで秩序が生まれる、生物の創発的同期をほぼそのままメッセージプロトコルに翻訳したところが面白い。ネットワークトポロジが激しく変わる環境ほど、中央集権的な同期より頑健になるという逆転がある。

**本来どこで使われてるか**: TinyOSベースのモートを使った実機テストベッドで検証されており、30ノード規模のマルチホップ・低品質リンク環境でも同期が実証されている。クラスタリングを組み合わせたCFSA（Clustering Firefly Synchronization Algorithm）などの派生も研究されており、デューティサイクル制御や省電力な広域センサー網の時刻合わせの候補として学術的に検討が続いている。
出典: https://www.mdpi.com/1424-8220/17/3/544 / https://link.springer.com/article/10.1155/2009/186406
