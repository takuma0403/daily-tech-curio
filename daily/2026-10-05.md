### <a id="card-1"></a>🆕 文字を並べるためのフォントが、中にプログラムを抱えている——HarfBuzzのWasmシェイパー 〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: HarfBuzz 8.0 には実験的な「Wasmシェイパー」があり、フォントファイルに `Wasm` テーブルが入っていると、文字列→グリフ列の変換（シェイピング）をフォント内蔵のWebAssemblyが担当する。グリフの選択・配置・送り幅を任意のコードで決められる一方、アウトラインの改変や改行の制御はできない。標準のOpenType機能（GSUB/GPOS）だけでは書けない言語固有の組版規則を、フォント側に持たせるための仕組みである。ビルド時に有効化が必要で、ブラウザのデフォルトでは無効なため、ほぼ誰も触っていない。

**何ができる**: 「テキストを入れるとフォントが計算結果を描く」という、フォント単体で完結する小さな計算機が作れる。たとえば `12+34=` と打つと、フォントが `46` のグリフ列に化ける。既存の「計算用の小さなJS部品」1個だけをフォントに置き換え、HTMLにはテキストノードしか存在しない状態を作る。ローカルのHarfBuzz（`hb-view` / `hb-shape`）で5分で動く。

**技術の魅力**: 「フォント＝データ」という前提が崩れ、フォントが実行体になる。しかも入口はテキスト入力なので、アプリ側は一切ロジックを持たない。ロジックの置き場所が、誰も予想しない描画の最終段に移る非対称性が面白い。副作用として、「フォントを信頼してよいか」という問いが新しく生まれる（Wasmは境界を限定されたサンドボックスで動く設計）。

**本来どこで使われてるか**: 複雑な文字体系（インド系文字、アラビア文字など）の正確な組版のために、フォント作者が独自のシェイピング規則を持てるようにする目的で導入された。HarfBuzzは Chrome, Firefox, Android, GTK, LibreOffice などで使われる事実上の標準シェイピングエンジンで、Wasmシェイパーはその拡張点の1つ。
出典: https://github.com/harfbuzz/harfbuzz/blob/main/docs/wasm-shaper.md / https://github.com/harfbuzz/harfbuzz/releases/tag/8.0.0

### <a id="card-2"></a>🔍 パスワードを覚える代わりに、パスキーに「鍵を計算」させる——WebAuthn PRF拡張 〔move: 仕様の目的外利用 / 領域: セキュリティ/認証〕

**事実**: WebAuthnの `prf` 拡張では、サイトが渡した「ソルト」と認証器内部の資格情報ごとの秘密から、疑似乱数関数（PRF）の出力が返る。同じパスキーと同じソルトなら、毎回同じ32バイトが再現される。裏側はCTAP2の `hmac-secret` 拡張。認証（本人確認）のための仕組みが、副産物として「決定論的な秘密鍵の発生装置」になっている。

**何ができる**: そのPRF出力を鍵導出（HKDF）に通して、ブラウザ内の暗号化鍵にできる。メモ帳アプリの「マスターパスワード」1機能だけをパスキーのタッチに置き換え、鍵はどこにも保存されず、サーバーも知らないE2E暗号化が成立する。ソルトを変えれば用途ごとの別鍵も得られる。

**技術の魅力**: 認証の「成功/失敗」ではなく、その過程で認証器が計算する値を取り出すという視点の転換がある。覚えるものがゼロで、鍵はハードウェアの中にあり、ユーザーは指紋にタッチするだけで復号できる。

**本来どこで使われてるか**: パスキー対応のE2E暗号化サービス（パスワードマネージャーや暗号化ノート）の鍵導出に実際に使われ始めている。Chromiumは出荷意向（Intent to Ship）を出しており、セキュリティキーでは `hmac-secret` が基盤になる。ただし実装差があり、同じPRFが同期されたパスキー間で保証されるかは実装依存なので注意。
出典: https://github.com/w3c/webauthn/wiki/Explainer:-PRF-extension / https://groups.google.com/a/chromium.org/g/blink-dev/c/iTNOgLwD2bI / https://oblique.security/blog/passkey-prf/

### <a id="card-3"></a>💡 時計を配らず、ホタルの真似だけで全員の点滅が揃う——パルス結合振動子とReachback Firefly Algorithm 〔move: 異分野の手法移植 / 領域: ワイルドカード(生物×無線)〕

**事実**: ホタルの群れは指揮者なしで同時に光る。Mirollo-Strogatzのモデルでは、各個体は一定周期で位相が進み、閾値に達すると発光（パルス）し、他の光を見たら自分の位相を少しだけ前へ押す。このパルス結合振動子は、ほぼ任意の初期状態から全員が同期することが数学的に示されている。これを無線センサーネットワークに移植したのが、Werner-Allenらの Reachback Firefly Algorithm (RFA)。

**何ができる**: タイムスタンプ付きの同期メッセージも、基準時計も、GPSも使わず、「パルスを聞いたら自分の位相を少し進める」だけでノード群の送信タイミングを揃えられる。既存の「NTP/時刻同期」1機能だけを置き換え、電池駆動ノードが一斉に起きて短時間だけ通信し、また一斉に眠る協調スリープの土台になる。

**技術の魅力**: 同期のために情報を運ばず、パルスのタイミングそのものを情報にしている。ノードの増減や故障に強く、全体を管理する者が不要という点が美しい。実環境では電波の遅延やノイズで精度が落ちるため、RFAは過去のパルス情報を遡って反映する工夫を足している。

**本来どこで使われてるか**: 無線センサーネットワークの時刻同期・低消費電力化の研究分野で、実機評価が論文として積み重ねられている。複雑な無線ネットワークでの実機試験（Sensors誌）や、PCOの位相応答関数の設計による同期速度の改善など、応用研究が続いている。
出典: https://dl.acm.org/doi/10.1145/1315843.1315848 / https://doi.org/10.3390/s17030544 / https://arxiv.org/pdf/1209.0814
