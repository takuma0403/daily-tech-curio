### <a id="card-1"></a>🆕 腕時計の水晶は、温度計の顔をしている——32.768kHzの放物線を逆に読む 〔move: センサーの転用 / 領域: 無線/組み込み/ハードウェア〕

**事実**: RTCや腕時計に載っている32.768kHzの音叉型水晶は、温度で周波数が動く。その形はきれいな放物線で、頂点（ターンオーバー温度）は約25℃、そこから離れると周波数が ΔT² に比例して落ちる（係数は約 −0.034〜−0.04 ppm/℃²）。設計者にとってはただの誤差だが、「温度が決まれば周波数ずれが決まる」ということは、**ずれを測れば温度が逆算できる**ということでもある。しかも音叉型は“頭が下がる”だけで増えないので、ずれの大きさから離れ具合は分かる。

**何ができる**: 温度センサーを1個も載せず、水晶そのものを温度計にできる。基準にするのは、同じ基板のもう1つのクロック（MCUのメインクロックやGPSのPPS）。32kHzのパルスを数えて基準との差を ppm にし、放物線の式に入れて ΔT を出す。ネットもセンサーも使わず、電源を入れたまま放っておくだけで「今、基板が何℃離れているか」が1日の積分で出る。逆向きに、既知の温度（冷蔵庫・室温）で式を当てれば、個体ごとの頂点と係数をキャリブレーションできる。

**技術の魅力**: 誤差の原因を、そのまま測定量に裏返している点。「温度を測ってクロックを補正する」（DS3231などのTCXO）の逆で、「クロックのずれから温度を知る」。しかもセンサーの追加部品がゼロで、時間（周波数）は現代で最も精度よく測れる量なので、温度計としての分解能は伸びしろが大きい。

**本来どこで使われてるか**: 水晶温度計という分野として実在する。1965年にHPが出した 2804A Quartz Thermometer は、温度で周波数が直線的に変わる特殊な角度の水晶（約28.5MHz、1℃あたり約1000Hz）を使い、分解能0.0001℃、確度±40ミリ℃で標準器として使われた。一方、32.768kHzの音叉水晶のほうは「温度で時計がずれる」問題を抱えており、DS3231のようなRTCは内蔵の温度センサーでそのずれを補正している。
出典: https://en.wikipedia.org/wiki/Quartz_thermometer / https://ecsxtal.com/tuning-fork-crystal-frequency-and-parabolic-temperature-curve/

### <a id="card-2"></a>🔍 集合の食い違いを、中身を送らずに二分探索で見つける——Range-Based Set Reconciliation 〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: 2つの端末が持つ「IDの集合」の差分を見つけたいとき、普通は一覧を全部送るか、バージョン番号を持つ。Aljoscha Meyer の Range-Based Set Reconciliation（RBSR）はそれを、**ソート済みの範囲ごとの“指紋”**だけでやる。両者は全体の指紋を交換し、違えば範囲を半分に割って、半分ごとの指紋を送る。一致した範囲は捨て、食い違った範囲だけ割り続ける。指紋は要素のIDを足し合わせた値などで、順序に依存せず足し引きできるのがミソ。これが Nostr の NIP-77（Negentropy）で実際に動いている。

**何ができる**: 通信量が「全体の大きさ」ではなく「食い違いの数」に比例する同期ができる。ネット越しなら数KBで、100万件の集合の数件の差が見つかる。このメッセージは小さなバイト列なので、1往復ごとにQRコードやNFCに載せ、**サーバーも回線もなしに、すれ違った2台が紙とカメラだけで差分同期**できる。バッテリー切れの現場端末と、事務所のPCが「QRの往復3回」で、お互いに持っていないデータを知るなど。

**技術の魅力**: 「バージョンを管理する」代わりに「同じ内容かどうかを割って確かめる」という、データ構造そのものを持ち込まない同期。履歴も、サーバー側の状態も、誰が先に書いたかも要らず、ただ集合が同じかどうかだけを見る。ログ的に積み上がる系（Nostrの投稿、署名付きの記録）にはよく噛み合い、「差分を求める」問題が二分探索の問題に化ける。

**本来どこで使われてるか**: Nostrのリレー同士・クライアントとリレーの間の同期に、Negentropy（NIP-77）として実装され、strfry などのリレーで使われている。数万〜数百万件の保存イベントに対し、通信量を差分に比例する量まで落とすのが目的。論文は Meyer の「Range-Based Set Reconciliation」(arXiv 2212.13567)で、分散アプリ向けの設計でも参照される。
出典: https://arxiv.org/abs/2212.13567 / https://nips.4rs.nl/nips/77

### <a id="card-3"></a>💡 数字の「頭の桁」だけで、捏造が暴かれる——ベンフォードの法則を、センサーログの検算に移植する 〔move: 異分野の手法移植 / 領域: ワイルドカード(金融監査×ログ検証)〕

**事実**: 自然に出てくる数字（人口・帳簿の金額・川の長さ）の先頭の桁は、一様ではない。1で始まるものがおよそ30%、9で始まるものは約4.6%に偏る。これがベンフォードの法則（1930年代にフランク・ベンフォードが整理）。人が数字を捏造すると、この偏りが再現できず、頭の桁がほぼ均等になるか、特定の数字に寄る。

**何ができる**: 「帳簿が改竄されていないか」を見る会計監査の手法を、**自分のセンサーログやアプリのログの“整合性チェック”**に持ち込める。例えば、複数桁にまたがって動く量（消費電力・転送バイト数・応答時間のミリ秒値）の先頭桁の分布を取り、期待の分布とのズレをカイ二乗などで見る。手入力で補完したデータ、テスト用に貼り付けた偽ログ、固定値で埋めた欠損が、中身を見ずに分布の歪みとして浮く。手元のCSVだけで、通信もモデルも要らない。

**技術の魅力**: 中身の意味を一切知らずに「人が作った数字」と「現象が出した数字」を分ける点。検証にあたって必要なのは、正解のデータでも署名でもなく、桁の分布という“自然な偏り”だけ。基準が理論側にあるので、オフラインで完結する。

**本来どこで使われてるか**: 会計監査・税務の不正検出が代表例。マーク・ニグリーニは1992年の博士論文で、IRS（米国内国歳入庁）が脱税の検出にこの法則を使えると提案し、1999年の論文で会計の世界に広めた。第1桁・第2桁・下2桁の各テストを使い、エンロン事件などの事例が紹介される。ただし、金額が狭い範囲に収まる（値段が固定されたデータなど）場合は当てはまらず、「外れたら即不正」ではなく調べる合図として使う。
出典: https://en.wikipedia.org/wiki/Benford%27s_law / https://www.researchgate.net/publication/241401706
