### <a id="card-1"></a>🆕 「変更を記録するだけ」のトリガーが、SQLiteを衝突しないDBに変える——cr-sqliteのCRR化 〔move: 仕様の目的外利用 / 領域: データ/同期/ストレージ〕

**事実**: SQLiteにはCRDT(Conflict-free Replicated Data Type)のネイティブサポートはない。ロード可能拡張の`cr-sqlite`は、この穴を新しいデータ構造の発明ではなく、SQLiteが最初から持つ「トリガー」という地味な監査ログ機構だけで埋める。任意の既存テーブルを`CRR`(Conflict-free Replicated Relation)として登録すると、INSERT/UPDATE/DELETEのたびにトリガーが自動で列ごとのバージョンを裏で刻んでいく。

**何ができる**: 好きな既存スキーマをそのままCRR化するだけで、複数のSQLiteインスタンスが完全オフラインで独立に書き込みを続け、あとでマージすればアプリ側の衝突解決コードなしに自動でマージされる。同期は全内容ではなく差分(デルタステート)だけなので帯域も小さい。中央サーバーも、専用の同期言語も要らない。

**技術の魅力**: 普通CRDTは新データ構造をゼロから設計するトップダウンの仕事だが、cr-sqliteは「変更を捕まえて記録する」という監査ログ用途の仕組みを、スキーマ自体には一切手を触れずに被せるだけでボトムアップにCRDT化する。データ構造を変えずに変更検知層だけ差し替える非対称性が効いている。

**本来どこで使われてるか**: SQLiteのトリガーは元々、INSERT/UPDATE時に別テーブルへ監査ログを書いたり、非正規化した集計列を追随更新したりするための一般的な仕組みで、CRDTとは無関係に何十年も使われてきた。cr-sqliteはvlcn.ioがローカルファースト(local-first)ムーブメントの文脈で開発しており、Ink & Switchらが提唱する「サーバーを主とせず端末を主とする」設計思想の実装の一つとして位置付けられている。
出典: https://github.com/vlcn-io/cr-sqlite / https://vlcn.io/docs/cr-sqlite/intro

### <a id="card-2"></a>🔍 消してから数十バイトで生やす——AV1のフィルムグレイン合成という粒子の"種" 〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: AV1などの映像コーデックには「フィルムグレイン合成」という機能がある。エンコーダはあえて映像から粒子ノイズを除去してから圧縮し、ノイズの統計モデル(自己回帰モデルの係数など、たかだか数十バイト)だけをビットストリームに埋め込む。デコーダはその数十バイトから粒子ノイズをその場で再生成し、映像に重ねて表示する。人間の目はノイズそのものの完全な再現には鈍感なので、実際の粒子を送るより遥かに少ないビット数で"粒感のある映像"に見せられる。

**何ができる**: これは実質「数十バイトの種から、知覚的に自然なノイズパターンを画面いっぱいに生成する」ジェネレータでもある。映像の用途を離れて考えると、正規のフィルムグレイン用フィールドにわずかに違う係数を仕込むだけで、見た目のノイズ感をほぼ変えずに数十ビットの情報を運べる。圧縮のための正当な理由(映画らしい質感を保つ)がそのまま隠れ蓑になる。

**技術の魅力**: 圧縮効率のために設計された機能が、結果的に「安全に無視できる変化にこっそり情報を積める棚」を作ってしまっている。ノイズは本来"情報量ゼロ"に見えるものだから、そこに意味のある数十ビットを混ぜても違和感を持たれにくい。効率化の副産物が超低帯域の隠しチャネルになる非対称性が面白い。

**本来どこで使われてるか**: Netflixなど配信各社がフィルムグレインの強い映画・ドラマ(粒子感を売りにしたリマスター作品など)を配信する際、粒子をそのまま符号化すると帯域を食い過ぎるため、AV1/AVIFのフィルムグレイン合成で粒子を除去してから配信し、デコーダ側の再合成で質感を保ちつつビットレートを大きく(重いグレイン素材では最大50%程度)節約する目的で実運用されている。
出典: https://norkin.org/pdf/DCC_2018_AV1_film_grain.pdf / https://aomedia.org/docs/CWG-C051o_TR_AOMedia_film_grain_synthesis_technology_v2.pdf

### <a id="card-3"></a>💡 デフギアの摩耗対策とセミの13年が、同じ数式で衝突を避けている——素数周期という発想 〔move: 異分野の手法移植 / 領域: ワイルドカード(進化生物学×機械工学)〕

**事実**: 北米の周期ゼミ(Magicicada属)は13年か17年という、どちらも素数の周期でしか地上に出てこない。1966年にLloydとDybasが提唱した仮説では、これは偶然ではなく、天敵となる捕食者・寄生虫の(通常もっと短い)周期との発生年重複を最小化するための進化戦略だとされる。周期を素数にしておけば、どんな短周期の相手と組み合わせても最小公倍数(=次に重なるまでの年数)が最大化され、遭遇頻度が下がる。

**何ができる**: 同じ数論のトリックは、実は機械工学ですでに実用化されている。自動車のデフギア(リング&ピニオン)は歯数をわざと互いに素(coprime、例: 41対10)に設計する"hunting tooth"という手法で、特定の歯同士が繰り返し噛み合うのを避け、摩耗を全歯に均等分散させている。これを分散システムに輸入すると、複数サービスのポーリング・リトライ間隔を互いに素な秒数に設定するだけで、乱数ジッターも中央調停も使わずに、決定論的に衝突頻度を数学的に最小化するスケジュールが組める。

**技術の魅力**: 「衝突回避」というと乱数ジッターや中央調停が定石だが、互いに素な周期を選ぶだけで通信ゼロ・乱数ゼロで衝突を減らせるのが効いている。セミもデフギアも分散システムも、「繰り返す2つの周期がどれだけ重なるか」という全く同じ数論の問題を、それぞれ無関係な理由で独立に解いている。

**本来どこで使われてるか**: 周期ゼミの発生周期は昆虫学・進化生物学の研究対象で、米国では発生年ごとの「ブルード(Brood)」が長年マッピングされている。一方の互いに素な歯数によるhunting tooth設計は、自動車のデフギアや時計の歯車列など機械工学分野で摩耗の均等化・寿命延長のために古くから使われる標準的な設計原則である。
出典: https://www.nature.com/articles/srep14094 / https://shoppress.dormanproducts.com/hunting-tooth-gearsets/
