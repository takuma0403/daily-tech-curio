### <a id="card-1"></a>🖼️ ぼかしフィルタの中身が「レンダリング時間」ではなく"キャッシュの足跡"で喋る——Pixel Thief 〔move: サイドチャネル/副作用の利用 / 領域: フロントエンド/グラフィックス / レンズ: 5分で動くデモにできる〕

**事実**: CSSやSVGの`feGaussianBlur`のようなフィルタは、ソフトウェアでピクセルごとに演算するとき、ピクセルの中身（色や透明度）によって通るコードパスや参照するメモリ位置が変わる。2013年にPaul Stoneが指摘したのは、この"中身依存の処理時間差"を使えば、クロスオリジンのiframeの中身を1ピクセルずつ色として復元できるという穴だった。ブラウザ側は「レンダリング完了までの時間を一定にする」対策で塞いだつもりだったが、2024年のUSENIX Security論文「Pixel Thief」は、時間ではなくCPUキャッシュへのアクセスパターンというサイドチャネルにすり替えて同じ攻撃を蘇らせた。

**何ができる**: 攻撃者は自分のページに標的サイトを埋め込んだiframeを置き、その上に自作のSVGフィルタを重ねるだけで、iframeの中に表示された銀行残高やチャット内容など"見えないはず"のピクセルを外部から読み出せる。Pixel Thiefはこのキャッシュ挙動の空間分解能を上げたことで、画面のリフレッシュレートより速く1ピクセルを特定できるところまで到達し、既存の「時間を揃える」対策をすり抜けた。

**技術の魅力**: 攻撃者は画面を直接見ることも、ピクセル値を読むJavaScript APIを叩くこともしていない。ただ「自分が仕込んだフィルタの処理が何マイクロ秒でCPUキャッシュに載るか」を外から測るだけで、隣にあるはずのないデータを覗ける。ブラウザベンダーが"処理時間"という表の入口を塞いでも、"キャッシュ"という裏口がハードウェアの奥に残り続けているという非対称性が効いている。

**本来どこで使われてるか**: CSSの`filter`やSVGの`<feGaussianBlur>`などのフィルタは、画像にぼかし・色収差・ドロップシャドウといった視覚効果を加えるための日常的な描画機能で、あらゆるWebデザインで使われている。この研究はFirefoxとChromeの標準的なフィルタ実装（ソフトウェアラスタライズ処理）を対象に、キャッシュ挙動の脆弱性を実証した。
出典: https://www.usenix.org/conference/usenixsecurity24/presentation/oconnell / https://orenlab.sise.bgu.ac.il/p/PixelThief

### <a id="card-2"></a>🌳 「誰が作っても同じ形になる木」で差分同期を高速化する——Merkle Search Tree 〔move: 異分野の手法移植 / 領域: データ/同期/ストレージ〕

**事実**: 普通のB木やAVL木は、同じデータでも挿入した順番によって木の形が変わる。これは2台のレプリカが同じデータを持っていても、作られ方が違えば木構造が一致せず、ルートハッシュで丸ごと比較しても「違う」としか分からないという問題を生む。2019年の論文「Merkle Search Trees」は、スキップリストが使う"コイントスで階層を確率的に決める"balancing技法をMerkle木に移植し、キー自体のハッシュ値（例えば先頭に並ぶ0ビットの個数）だけで各ノードが何階層目に属するかを決定的に決めてしまう。

**何ができる**: 挿入順序に依存せず、同じキー集合からは常に同じ形・同じルートハッシュの木ができる。これにより2つのレプリカはルートハッシュを1回比較するだけで「完全一致」か「どこが違うか」を木を再帰的に降りるだけで特定でき、差分だけを送る効率的なアンチエントロピー同期が成立する。ネットワークの都合で分岐・再接続を繰り返す分散ノード同士でも、確定的な形のおかげで安全に収束する。

**技術の魅力**: スキップリストは「検索」を速くするための確率的な高さ決定だったが、それを「同じデータなら誰が組んでも同じ形になる」という同期の道具として転用したのが効いている。木の形そのものがデータの内容だけで決まる指紋になるので、"木の形を比較する"という一見遠回りな操作が、実は最小限の通信量で差分を見つける最短ルートになる。

**本来どこで使われてるか**: SNS基盤のAT Protocol（Blueskyの土台）は、ユーザーごとの投稿・プロフィール・いいねなどを1つのMerkle Search Treeに格納しており、SHA-256ハッシュの先頭ビットパターンでノードの階層（fanout 16）を決めている。サーバー間・クライアント間でリポジトリ全体を毎回送る代わりに、ルートハッシュの違いから必要な部分木だけをやり取りして同期する、まさに論文の狙い通りの使われ方をしている。
出典: https://atproto.com/specs/repository / https://inria.hal.science/view/index/docid/2303490

### <a id="card-3"></a>✋ 腕の骨を伝わる振動の周波数だけで、タップした指を当てる——Skinput 〔move: 人間/身体をプロトコルの一部にする / 領域: ワイルドカード〕

**事実**: 指で腕や手をタップすると、皮膚表面を這う横波（transverse wave）と、骨を通り抜けて他の部位でまた皮膚に染み出してくる縦波（longitudinal wave）という、伝わり方も速度も違う2種類の音響波が同時に発生する。骨は柔らかい組織よりずっと硬いので剛体のように振動し、皮下組織の量や骨との距離によってタップ位置ごとに特有の周波数特性が生まれる。2010年CHIでChris Harrisonらが発表したSkinputは、この身体組織そのものが持つ物理的な周波数フィルタとしての性質を利用する。

**何ができる**: 上腕に巻いた高感度振動センサーの配列だけで、腕のどこをタップしたかを機械学習で分類できる。5箇所のタップ位置なら95.5〜96%、前腕を10分割した実験でも実用的な精度でタップ位置を判別でき、腕自体を"指1本ずつ違うボタン"として扱える。小型プロジェクタと組み合わせれば、皮膚に投影したメニューをそのまま指でタップして操作する、画面もタッチセンサーも埋め込まれていない身体そのものの入力デバイスが作れる。

**技術の魅力**: 普通のタッチ入力はセンサーを"触られる場所"に敷き詰めるが、Skinputはタップされた場所には何も置かず、離れた1点（上腕）で音を聞くだけで済ませている。これができるのは、皮膚と骨という身体の構造そのものが、位置ごとに違う音を鳴らす楽器のように振る舞ってくれるから。身体を「配線」ではなく「あらかじめ位置情報が刻まれた伝送媒体」として使うところに、他のボディエリアネットワークとは違う一捻りがある。

**本来どこで使われてるか**: この研究はマイクロソフトリサーチとカーネギーメロン大学によるHCI（ヒューマンコンピュータインタラクション）研究で、スマートウォッチやスマホの画面が小さすぎる・取り出しにくいという課題への回答として、ウェアラブル機器の入力面積を身体そのもので拡張する目的で提案された。義肢やAR/VRのハンズフリー操作といった後続研究にも、身体表面を音響センシングする発想は引き継がれている。
出典: https://dl.acm.org/doi/pdf/10.1145/1753326.1753394 / https://en.wikipedia.org/wiki/Skinput
