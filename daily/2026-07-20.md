### <a id="card-1"></a>🆕 文字を綺麗に見せる仕組みが、丸ごとDOOMのレイキャストエンジンになる——TTF-DOOM 〔move: 仕様の目的外利用 / 領域: フロントエンド/グラフィックス〕

**事実**: TrueTypeフォントは、小さいサイズや低解像度でも輪郭が滲まないよう「グリッドフィッティング」という調整をグリフごとのバイトコード命令（hinting instructions）で行える。このバイトコードは1991年の仕様以来ずっとフォントファイルの中に埋め込まれていて、スタック・ストレージ領域・条件分岐・関数呼び出し（FDEF/CALL）を備え、実はチューリング完全であることが分かっている。つまりフォントレンダラーは気づかないまま、任意プログラムを実行できる小さなCPUを毎回起動している。

**何ができる**: 「TTF-DOOM」というプロジェクトは、この事実を利用してグリフ「A」の中に3Dレイキャスターを丸ごと実装した。プレイヤー座標はCSSの`font-variation-settings`で可変フォント軸（MOVX/MOVY/TURN）として毎フレーム注入され、フォント内のバイトコードがDDAレイキャスティングでタイルマップの当たり判定を計算し、SCFS命令でグリフ内の16本の縦棒の高さを動かして疑似3D視界を描く。生成された命令列はたった6.5KB。JS側はプレイヤー移動と敵・武器のCanvasオーバーレイしか担当しておらず、本当の「ゲームロジック」はフォントの中で動いている。

**技術の魅力**: フォントレンダラーはユーザー入力もゲームロジックも想定していないのに、「可変フォント軸の値に応じてグリフ形状を再計算する」という正規の機能だけで任意計算ができてしまう非対称性が効いている。おまけにMUL命令が`(a*b)/64`しか返さない、関数呼び出しスタックが64フレームまで、という素朴な制約の中で、専用のゲームエンジンを使わず動くゲームを組み上げている——制約それ自体が面白さの燃料になっている。

**本来どこで使われてるか**: hinting命令は本来、Windows GDIなど低解像度環境でArialやVerdanaのようなフォントの線の太さ・字間・ステム幅を画素グリッドに揃えて可読性を保つための地味な裏方機能で、Microsoft・Appleの各フォントベンダーが何千行ものhintingコードをVisual TrueTypeなどで手作業に近い形で書き込んできた。高DPI画面の普及で重要性は下がったが、命令セット自体は今も現行のTrueType/OpenType仕様にそのまま残っている。

### <a id="card-2"></a>🔍 「常にHTTPSで」という約束が、消せないCookieになる——HSTSスーパークッキー 〔move: サイドチャネル/副作用の利用 / 領域: セキュリティ/認証〕

**事実**: HSTS（HTTP Strict Transport Security）は、サーバーが一度「このドメインは常にHTTPSで接続しろ」とブラウザに指示すると、ブラウザがその指示を長期間（`max-age`、時に1年以上）記憶し、以後HTTPでアクセスしようとしても自動でHTTPSへ書き換える仕組み。重要なのは、この「覚えている/いない」という1ビットの状態がCookieとは別の保存領域にドメインごとに記録され、しかもプライベートブラウジングやCookie削除の対象になりにくいこと。

**何ができる**: 32個のサブドメイン（`bit0.example.com`〜`bit31.example.com`）を用意し、追跡したいユーザーに割り当てた32ビットIDの1が立っている桁のサブドメインだけHSTSヘッダーを送って「書き込む」。再訪時は同じ32個のサブドメインへ透明な1x1画像などを裏で読み込ませ、HTTPSへリダイレクトされたか（=1）/されなかったか（=0）を観測するだけで元のIDをまるごと読み出せる。Cookieを毎回消しても、シークレットモードで開いても、この32ビットのHSTS状態はブラウザのセキュリティ設定として生き残るため識別子は消えない。

**技術の魅力**: HSTSは本来「盗聴者にHTTPS接続を妨害されない」ためのユーザー保護機能で、それをそのまま「ブラウザの記憶領域」として読み書きする発想が逆説的で強い。Cookieのような明示的なストレージAPIを一切使わず、"HTTPSを覚えているかどうか"というブラウザの正常な振る舞いだけを1ビットのメモリセルに変換している——セキュリティ機能の副作用が、防ごうとしていたはずの追跡そのものに化ける非対称性が肝。

**本来どこで使われてるか**: HSTSは元々、公衆Wi-Fiなどでの中間者攻撃によるSSLストリッピング（HTTPSへのアップグレードを黙って握りつぶす攻撃）を防ぐために2012年にRFC 6797で標準化され、銀行やSNSなど主要サイトが軒並み採用している。このsupercookie技術は2015年にSam GreenhalghがPoCとして公開して注目を集め、以降複数の研究・実装（`pyn3rd/HSTS-SuperCookies`など）で再現された。Appleは2018年、WebKitでHSTSキャッシュのパーティション化と書き込み回数制限を行い、この悪用を塞いでいる。
出典: https://thehackernews.com/2018/03/hsts-supercookie-tracking.html / https://en.wikipedia.org/wiki/HTTP_Strict_Transport_Security / https://github.com/pyn3rd/HSTS-SuperCookies

### <a id="card-3"></a>💡 「1個の名前のロック」を取り合うだけで、タブたちが勝手にリーダーを決める——Web Locks API 〔move: 制約の極端化 / 領域: データ/同期/ストレージ〕

**事実**: Web Locks API（`navigator.locks`）は、同じオリジンを開いた複数のタブ・ワーカーが同じ名前のロックを取り合うための小さなAPI。exclusiveロックは同時に1つのコンテキストしか保持できず、保持中のコールバックが完了する（またはタブがクラッシュ・終了する）と自動的に解放されて次の待機者に渡る。サーバーもBroadcastChannelの常時通信もlocalStorageのポーリングも要らない、ブラウザが標準で持つ排他制御のプリミティブがこれだけで手に入る。

**何ができる**: 全タブが起動時に同じ名前（例: `'app-leader'`）のロックを`navigator.locks.request`し、そのコールバックをわざと解決しないPromiseにしてロックを握りっぱなしにする。ロックを取れたタブだけが「自分はリーダーだ」と自己申告し、WebSocket接続の維持やIndexedDBへの同期書き込みなど、1つのタブだけが担当すべき処理を引き受ける。リーダータブを閉じる・クラッシュさせると、ブラウザがロックを自動解放し、次に並んでいたタブが何もしなくても新リーダーに昇格する——ハートビートもタイムアウト監視も自前で書く必要がなく、2つタブを開くだけで数分で挙動を確認できる。

**技術の魅力**: 分散システムのリーダー選出は普通、生死判定のためのハートビートとタイムアウトのチューニングが面倒の種になる。Web Locks APIは「タブが死んだら、そのタブが握っていたロックはOSプロセスの終了と一緒に片付く」というブラウザの後始末を、そのまま故障検知に転用しているのが効いている。ロック自体はもともと「同時書き込みを防ぐ」ためのごく地味な排他制御機能で、リーダー選出のための機能では全くない——コールバックを終わらせない、という一捻りだけで恒久的な"占有"に化ける制約の極端さが面白い。

**本来どこで使われてるか**: 仕様がまず想定するのは、複数タブが同じIndexedDBに同時書き込みして壊さないようにする調整や、Service Workerでのキャッシュ更新時の排他制御。実務でも、複数タブで同じアプリを開いたときに1本のWebSocket接続だけを維持してBroadcastChannelで他タブへ配る「プライマリタブパターン」の実装に使われている。W3Cのweb-locks仕様（EXPLAINER）自身がこのパターンをユースケースの筆頭に挙げている。
