### <a id="card-1"></a>🆕 圧縮のための"ついで"データが、光学フローをタダで肩代わりする——動画コーデックの動きベクトル 〔move: サイドチャネル/副作用の利用 / 領域: AI/メディア処理〕

**事実**: H.264やHEVCの動画エンコーダは、フレーム間の差分を減らすため各マクロブロックについて「前フレームのどこから動いてきたか」を表す動きベクトルを計算し、ビットストリームに埋め込む。これは純粋に圧縮率を上げるための内部情報で、本来アプリケーション側が読む想定の値ではない。しかし復号器をフル稼働させずビットストリームを軽く解析するだけで、この動きベクトルの集合をフレームごとにタダで取り出せる。

**何ができる**: 本来アクション認識や監視カメラの動体検知には、フレームを完全にデコードしてから高コストな光学フロー(Optical Flow)を計算する必要がある。これを動きベクトルで置き換えると、フル解像度のピクセルへ触れずに「どこで何が動いたか」の粗い場が手に入る。計算コストは光学フローの数十分の一で、エッジデバイスや大量の監視カメラ映像でも"何かが動いた場所"だけをリアルタイムにふるいにかけられる。

**技術の魅力**: 圧縮効率のために生まれた副産物を、本来何百倍も重い別の計算(光学フロー)の代用品にすり替える非対称性が効いている。エンコーダは「動きを予測して差分を減らす」以外の意図を持っていないのに、その予測結果自体が「何が動いたか」の答えにほぼ一致してしまう。おまけとして出てくる数値が、本命の重い処理をまるごと飛び越えさせる。

**本来どこで使われてるか**: 動きベクトルはMPEG系コーデックの標準的な圧縮技術で、あらゆる動画ファイル・配信に日常的に埋め込まれている。この転用は学術的にも確立していて、圧縮領域(compressed domain)での群衆流動解析や監視映像のリアルタイム行動認識に実際に使われ、二流ストリーム方式の行動認識モデルで光学フロー入力を動きベクトル入力に差し替える研究群がある。
出典: https://www.sciencedirect.com/science/article/abs/pii/S156849461500441X / https://ieeexplore.ieee.org/document/6706430/

### <a id="card-2"></a>🔍 画像用の圧縮器を、画像じゃないデータの圧縮エンジンとして借りる——CanvasのPNGエンコーダ密輸 〔move: 仕様の目的外利用 / 領域: フロントエンド/グラフィックス〕

**事実**: `<canvas>`の`toBlob('image/png')`は、キャンバスに描いたピクセルをPNG形式でロスレス圧縮して返すブラウザ標準API。PNGの内部はDEFLATE(zlibと同じ可逆圧縮アルゴリズム)で、これはネイティブコードとしてブラウザに焼き込まれている。ここで見落とされがちなのは、圧縮対象が「本物の画像」である必要がないという点。任意のバイト列をピクセル(RGBA)としてImageDataに詰め込んでからtoBlobを呼べば、ブラウザ内蔵のDEFLATE実装をJS外部ライブラリなしで丸ごと借りられる。

**何ができる**: pako.jsやfflateのようなJS製zlib実装を1バイトも読み込まずに、任意のバイナリデータをブラウザネイティブのDEFLATEで圧縮できる。サイズ制限が絶対のjs13kGames(13KB以内でゲームを作るコンペ)のような場では、レベルデータやマップ情報をこの手口でPNGに変換してJSファイル内に埋め込み、実行時にcreateImageBitmapで戻して展開するという運用が実際に行われている。圧縮ライブラリの読み込みコスト自体をゼロにできるのが利点。

**技術の魅力**: 「画像を圧縮する」という一点特化のAPIから、圧縮という中身だけを剥がして持ち出す発想が効いている。ブラウザ側は相手が本物の画像かデータの塊かを一切区別しないので、フォーマットの皮(PNGヘッダ・チェックサム)というオーバーヘッドを払う代わりに、外部ライブラリのダウンロードとパースというもっと重いコストを消せる。圧縮アルゴリズムの実装を1行も書かずに手に入れる、という非対称性。

**本来どこで使われてるか**: Canvas 2D APIとPNGエンコーダは、画像編集・スクリーンショット保存・アップロード前のクライアント側リサイズ圧縮など、写真や描画データを軽くするための機能として設計・提供されている。転用先のjs13kGamesコミュニティでは、この「Canvas PNGトリック」が容量制限を突破する定番テクニックとして共有されている。
出典: https://jstrieb.github.io/posts/canvas-compress/ / https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob

### <a id="card-3"></a>💡 セキュリティのために葬られたはずの経路指定が、5G網の背骨として生き返った——SRv6という"送信元ルーティング"の蘇生 〔move: レガシー/廃止予定機能の蘇生 / 領域: ネットワーク/プロトコル / レンズ: サーバー不要〕

**事実**: IPには本来「パケットの送信元が経路そのものを指定する」ソースルーティングというオプション(IPv4のLoose/Strict Source Routing)が仕様として存在した。だが経路詐称やDoSの踏み台に悪用しやすいという理由で、2000年代以降ほとんどのルータ・OSがデフォルトで無効化し、事実上死んだ機能として扱われてきた。ところがこの「経路をパケット自身に書かせる」という発想そのものが、SRv6(Segment Routing over IPv6)としてIPv6拡張ヘッダ(SRH)の形でほぼそのまま蘇っている。

**何ができる**: SRv6では、ネットワークの中継ルータ(コア)が個々の通信フローの状態を一切覚える必要がない。経路(訪問すべきノードの並び)はすべて送信元がパケットのヘッダに書き込んでしまうため、コア機器は「今書かれている次のセグメントへ転送する」だけでよい。これにより、フローごとの経路テーブルをコアの何百台ものルータに配って同期させる集中コントローラや状態管理サーバーなしに、モバイル網のスライシングやトラフィックエンジニアリングを実現できる。

**技術の魅力**: 「危険だから殺した」機能が、名前を変え、悪用を防ぐ検証機構(境界でのSRH付け外しなど)を足しただけで正反対の主役に返り咲いた逆転劇が面白い。しかも復活の理由は懐古趣味ではなく、「経路の状態を送信者側に寄せてコアを軽くする」という設計思想がクラウド化・仮想化時代の要求とたまたま一致したから。かつての弱点(誰でも経路を書き換えられる)は、今は運用者だけが境界でSRHを操作する閉域運用によって塞がれている。

**本来どこで使われてるか**: SRv6はMPLSに代わる次世代のバックボーン技術として、通信事業者のコアネットワークや5Gのモバイルユーザープレーン(RFC 9433)で実運用されている。Ciscoなどの主要ベンダーが対応機器を出しており、フローごとの状態を持たずにトラフィックエンジニアリングやサービスチェイニングを行う手段として、大規模ISPや移動体通信網のコアで採用が進んでいる。
出典: https://datatracker.ietf.org/doc/html/rfc9433 / https://cloudswit.ch/blogs/what-is-srv6-and-why-it-matters/
