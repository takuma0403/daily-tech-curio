### <a id="card-1"></a>🆕 プログレスバーを「文字」として書く——COLRv1の可変カラーフォント 〔move: 制約の極端化 / 領域: フロントエンド/グラフィックス〕

**事実**: OpenTypeのCOLRテーブルのv1は、グリフの中に「ペイント・グラフ」（グラデーション塗り、変形、合成モード、他グリフの再利用）を持てる。しかもこのグラフは可変フォントの軸（ItemVariationStore）で値を動かせるため、グラデーションの停止位置や変形量がフォント軸の値で連続的に変わる。Chromeは98から対応しており、色パレットはCSSの `@font-palette-values` と `font-palette` で外から差し替えられる。「絵文字用の色付きフォント」という印象が強く、中身が小さな描画言語であることは見落とされがち。

**何ができる**: 「進捗」軸を1本持つ専用フォントを作り、`<span style="font-variation-settings:'PROG' 73">▮</span>` のような1文字で、73%まで塗られたバーを描く。DOMもSVGもcanvasも増えず、`transition: font-variation-settings` だけで滑らかに伸びる。スケルトンローダーやスパークラインを「1文字のフォント」に置き換えれば、テキストを選択・コピーでき、フォントサイズ指定でそのまま拡大縮小もできる。

**技術の魅力**: 「フォントは字形を並べる道具」という前提を、「フォントは軸付きの小さなベクター描画ランタイム」へひっくり返す点。レイアウトエンジンがすでにテキスト行として面倒を見てくれるので、位置合わせ・折り返し・ベースライン揃えが無料で付いてくる。非対称性の核は、JSも要素も使わず、必要なのは1つのバイナリ資産だけという点。

**本来どこで使われてるか**: 色付き絵文字や、Google Fontsに載った色付き装飾フォント（Bungee系など）の配信形式として使われ、パレットをCSSで切り替える用途が公式に推奨されている。仕様の経緯と実例はChromeの解説記事とcolorfonts.wtfにまとまっている。
出典: https://developer.chrome.com/blog/colrv1-fonts / https://www.colorfonts.wtf/

### <a id="card-2"></a>🔍 Luhnが見逃す「09↔90」を、群ではない表1枚で全部拾う——Damm algorithm 〔move: 異分野の手法移植 / 領域: ワイルドカード(数学×誤り検出)〕

**事実**: クレジットカード番号などで使われるLuhn検査は、隣り合う2桁の入れ替わりのうち「09と90」だけを見逃す。2004年にH. Michael Dammが博士論文（全反対称擬群）で示した検査桁は、10×10のラテン方陣（演算表）を1枚引くだけで、単一桁の誤りと隣接桁の入れ替わりを例外なくすべて検出できる。計算は「中間桁0から始め、各桁で表を引いて更新する」だけ。最後が0なら正しい。

**何ができる**: 注文番号・チケットID・手書き転記される整理番号など、既存のLuhnを使っている「検査桁だけ」を差し替えると、隣接入れ替えの取りこぼしがゼロになる。表は100バイト、ループは数行なので、マイコンのシリアル番号シールの検証にもそのまま入る。ただし先頭の0は検査桁を変えないので、可変長コードを混在させるなら桁数も一緒に検証する必要がある。

**技術の魅力**: 実務の誤り検出に、代数の「擬群」という普通は登場しない構造が効いている点。検出性能が表の性質（全反対称性）だけで保証され、証明も表の検算でできるので、仕様が「データそのもの」になっているのが美しい。VerhoeffやLuhnに比べ、置換表の山も剰余の特殊処理もいらない。

**本来どこで使われてるか**: 検査桁アルゴリズムの1つとして文献化されており、Pythonの `python-stdnum` ライブラリにもdammモジュールとして収録されている。PyPIの `damm` パッケージのように単体で配布もされている。
出典: https://en.wikipedia.org/wiki/Damm_algorithm / https://arthurdejong.org/python-stdnum/doc/2.0/stdnum.damm / https://pypi.org/project/damm

🔎 検索ワード: `Damm algorithm check digit` / `totally anti-symmetric quasigroup` / `Verhoeff vs Luhn transposition errors` / 「検査桁 隣接 入れ替え 検出」

### <a id="card-3"></a>💡 音声ケーブルの中の192ビットの空き部屋——S/PDIFのユーザービットを密輸路にする 〔move: 仕様の目的外利用 / 領域: 無線/組み込み/ハードウェア〕

**事実**: S/PDIF（TOSLINKや同軸のデジタル音声）は、192フレームを1ブロックとして流れ、各サブフレーム（32スロット）の末尾に妥当性・ユーザー・チャネルステータス・パリティの各1ビットが付く。音声データの隣に、ブロックごとに192ビット分の「ユーザーデータ」と「チャネルステータス」の枠が毎回用意されているのに、ほとんどの民生機器は読み飛ばす。信号はバイフェーズマーク符号なのでクロックが信号自体に乗っており、受信側は別線の同期線なしで読める。

**何ができる**: マイコンで、音声ストリームの裏ビットにテキストや時刻コード、メタデータを乗せて音声と同じ光ケーブルで運べる。たとえば演奏中の音声と一緒に「次の曲名」や「照明のキュー番号」を同期状態で同報でき、音声が途切れない限りデータも同時刻に届く。STM32F4/F7/H7はSPDIFRXの周辺機能を持ち、ユーザービットも受信側で拾える。

**技術の魅力**: 「音を運ぶ配管に、音と完全に同期した別の管が並走している」というところが効く。専用線もプロトコル追加も要らず、既存の光ファイバー1本が低速なデータ回線を兼ねる。ほとんどの機器が無視するので、挿しても何も壊れない。

**本来どこで使われてるか**: 規格（IEC 60958）では、チャネルステータスにコピー保護フラグやサンプリング周波数などが入り、ユーザービットはCD由来のサブコードなどの伝送に使われてきた。STMicroelectronicsのアプリケーションノートAN5073がSPDIFRXの受信手順を解説している。
出典: https://www.mikrocontroller.net/articles/S/PDIF / https://www.st.com/resource/en/application_note/an5073-receiving-spdif-audio-stream-with-the-stm32f4f7h7-series-stmicroelectronics.pdf / https://wiki.hiby.com/knowledge/audio/dai/spdif
