### <a id="card-1"></a>🆕 「消した」つもりのSQLiteの行が、フリーリストの中で生き続けている——DELETEは何も消さない 〔move: サイドチャネル/副作用の利用 / 領域: データ/同期/ストレージ / レンズ: オフライン完結〕

**事実**: SQLiteはDELETE文を実行しても、B-treeリーフページ上の該当セル(レコード)のバイト列を消去せず、「フリーブロック」として印を付けるだけで放置する。ページ丸ごとが空になった場合もページ単位でフリーリストに繋ぎ替えられるだけで、内容は新しいデータで上書きされるまでそのまま残る。WALモードならコミット前の変更履歴自体がWALファイルに平文で並ぶ。`secure_delete`プラグマをFULLにしない限り、これがデフォルトの挙動。

**何ができる**: 押収したスマホやPCから取り出したSQLiteファイル(SMS、ブラウザ履歴、チャットアプリのローカルDBなど)を一切改変せず、フリーリストページとフリーブロック、WAL/ロールバックジャーナルの残骸だけをバイト単位で走査すれば、アプリのUI上は「削除済み」の会話や閲覧履歴を復元できる。FQLiteやBelkasoft、bring2liteといった法科学ツールは、レコードヘッダのシリアルタイプ列を手がかりにこの走査を自動化しており、上書きされていない限り何ヶ月も前に消えたはずの行がそのまま出てくる。

**技術の魅力**: 「消す」という言葉の意味を、アプリ層(UI表示)とストレージ層で食い違わせているのが効いている。ユーザーからは消えたはずのデータが、ページの再利用を遅らせて書き込みコストを下げるという、ごく素朴な省エネ設計のせいで意思と無関係にディスク上へ残留し続ける。暗号化していないDBならこれは特別な脆弱性ですらなく、SQLiteの一番地味な最適化がそのまま情報の残留を生む非対称性がある。

**本来どこで使われてるか**: フリーリストによるページ再利用の先送りや、フリーブロックの遅延コンパクションは、ディスクI/Oを減らして書き込みを速くするための、ごく普通のストレージエンジン最適化。デジタル・フォレンジック業界はこれを逆手に取り、iOSのSMS.db、ブラウザのHistory DB、メッセージアプリのローカルDBなどから削除済みメッセージや閲覧履歴を復元する定番手法として確立している。

### <a id="card-2"></a>🔍 雷が地球規模で鳴らす"鐘"に便乗して、GPSなしで雷の位置を当てる——WWLLNのVLF sferics 〔move: 物理現象へのピギーバック / 領域: ワイルドカード(電波伝搬)〕

**事実**: 雷放電が起きた瞬間に発生するごく短い電磁パルス(sferics)は、3〜30kHzのVLF帯の電波として、地表と電離層に挟まれた「地球-電離層導波管」の中をほとんど減衰せず何千kmも伝わっていく。送信機も電源もアンテナ設置計画も要らない、自然現象がタダで鳴らす巨大な電波パルス源。World Wide Lightning Location Network(WWLLN)は世界70か所以上の受信局を並べ、このsfericsが各局に届く時刻だけを拾い集めている。

**何ができる**: 各受信局はGPSタイムスタンプでsfericsの到達時刻を記録するだけでよい。中央サーバーが複数局間の到達時刻差(TOA)から双曲線の交点を計算し、雷1発ごとの発生位置と時刻を、海上や極域を含む地球上どこでもリアルタイムに特定する。GPSは「衛星の位置が分かっているから自分の位置が分かる」仕組みだが、WWLLNは逆に「発信源の位置が分からないからこそ、複数観測点の到達時刻差だけで発信源自身の位置を割り出す」という向きの測位を成立させている。

**技術の魅力**: 誰も設計していない、地球という導波管そのものをタダで借りているのが良い。本来は無線通信にとってただのノイズ源でしかない雷放電を、位置が未知のまま測位の主役に据える発想転換だけで、専用の送信インフラなしに全球規模のリアルタイム観測網が成立してしまう。受信専用の安価な局を並べるだけで済むという非対称性が効いている。

**本来どこで使われてるか**: WWLLNはワシントン大学が運用してきた研究インフラで、山火事の着火源特定、航空機の落雷回避判断、雷活動の長期気候トレンド観測のために使われてきた。近年は太陽系外惑星の大気中の雷放電探索の比較対象としても引用され、2004年の稼働開始から20年以上、全球雷マップを配信し続けている。
出典: https://wwlln.net/ / https://angeo.copernicus.org/articles/24/3197/2006/angeo-24-3197-2006.html

### <a id="card-3"></a>💡 データ線を1本も持たない"充電専用ケーブル"が、実は全二重の通信路を隠し持っている——USB PDのCC線 〔move: 仕様の目的外利用 / 領域: 無線/組み込み/ハードウェア〕

**事実**: USB Type-Cの信号線のうち、D+/D-はUSB 2.0のデータ用、CC(Configuration Channel)はもともと「ケーブルの向き検出」「電力の役割ネゴシエーション」だけを担う脇役ピンだった。ところがUSB Power Delivery(PD)は、この電力交渉のためだけにCC線1本の上へ300kbpsのBMC(バイフェーズマーク符号、差動マンチェスタ符号)でパケット通信を丸ごと乗せてしまった。「データ転送非対応」を謳う急速充電用ケーブルの多くは、D+/D-を省く一方でCC線だけは配線されており、通信線として生きたまま残る。

**何ができる**: PD対応の充電器やモバイルバッテリーとデバイスの間では、USBのデータピンが物理的に存在しなくても、CC線を流れるPDメッセージ(Vendor Defined Message = VDM)を読み書きできる。つまり"データは通らない"と信じられている充電専用ケーブルでも、CC線1本だけでベンダー定義の任意データや機器の識別情報をやり取りする隠し経路が作れる。防御側から見れば逆に、公衆充電スタンドがCC線経由でPD対応デバイスの情報を盗聴・改ざんする経路にもなり得るということでもある。

**技術の魅力**: 「電力を安全にネゴシエーションするための、ただの制御信号」という建付けのピンが、フルスペックのパケット通信プロトコルをまるごと隠し持っているという二重性が効いている。ユーザーもエンジニアの多くも「データ線がない=データは通らない」と信じているが、それは"USBのデータ線"の話であって、電力交渉用のCC線自体が別のプロトコルスタックを走らせていることには誰も注目していない。

**本来どこで使われてるか**: この仕組みは本来、ノートPCとドック・モニタの間で「どちらが電力を供給するか」「何ワット・何ボルトを流すか」を安全に自動交渉するために標準化された、USB-IFのUSB Power Delivery仕様そのもの。電子的にマークされたケーブル(e-marker)はCC線経由で自分のケーブル定格をホストに申告し、DisplayPortなどのAlternate Modeへの切り替え交渉もすべて同じCC線上のPDメッセージで行われている。
